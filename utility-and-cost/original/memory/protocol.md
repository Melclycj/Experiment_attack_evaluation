**这份协议管什么。** 各列问什么、哪些列实测，以结果文件 [sota-utility-scalability-rest.md](../../Thesis/Work/Submission/sota/sota-utility-scalability-rest.md) 第 1 到 3 节为准；本文件只写怎样测其中四列：每个 agent 的额外内存、启动时间、每请求延迟、并发表现与上限。对象名单在第 9 节。执行步骤与进度见 [sota-measurement.plan.md](../../.goals/plans/sota-measurement.plan.md)。

**结果能支持什么。**
- 这是一台机器上、一套固定配置下的部署比较，不是架构排名。
- 同一侧（第 2.1 节）的对象之间可以直接比；跨侧只直接比内存的整体边际成本（第 3.1 节），其余列并列给出、注明虚拟化层次。
- 上游在本机，结果不含真实外网条件。
- **归因只按第 3.4 节写定的负载响应检验写**：检验做了且结果明确才写归因，否则写"未证"。
- 只有试跑数据才能回答的事实，列在第 11 节，第 8 步试跑时核对；核对结果若推翻本协议的某个做法，按第 11 节写定的退路处理。

**与列定义的三处差别**（用户 2026-10-30 定，保持现状）：
1. 每请求延迟一列的定义是"单个请求或操作"。本协议只同机测网络请求；文件读写、程序执行一类操作的开销不同机测，照抄各篇原文的数并注明。
2. 计划原写本论文分四段计时（接入、核章、核心决策与排队、连上游）。现有 E-09 记录分不出四段，本协议只报两段加判定口排队采样（第 3.3、3.4 节），不在 engine 里加计时点。
3. 计划原写并发启动报 p99。每轮只有 4 到 8 个样本，本协议报中位与最大值。

另有一处与计划的差别：计划原写负载发生器、上游、engine 分到不同的 CPU 核。本协议把发生器 k6 放在单位内、用单位的配额（第 1 节），因为它是 agent 一侧的负载；上游仍单独占核。

## 1. 被测配置与"一个 agent"

**配置分三类。**
- **不加系统**：同一个 agent 作为普通进程直接运行，没有沙箱或代理。服务器上只有一份（第 2.1 节）。内存与延迟的列值相对它算；启动时间与并发报各对象的绝对值，同时并列它的值。
- **本论文**：一个 agent 等于一次 execution，即一个隔间，加隔间外的一个 connector 实例与一个文件 worker，加隔间内的一个 HTTP 前端、一个 MCP server 和一个 pty 转发进程；核心与简易 PDP 全机各一个（engine 留档版本 v4 的构成，第 9 节）。整晚固定登记、测量中不改：放行目的地与模型 API 登记为"不问"的记录过允许，不限方法与路径；拒绝目的地与 Claude Code 会联系的其他主机（试跑与 engine 的 7.2 门记录列出：platform.claude.com、claude.ai、downloads.claude.ai）登记为"不问"的记录过禁止。不登记兜底拒绝：engine 先看有没有覆盖该请求的拒绝记录、有就拒，再看允许（engine 的 matching.py，K-43 第一步），兜底拒绝会连模型 API 一起拒掉（2026-10-31 实测，runs/20261031T024500Z-engine-mode-probe）。v4 给每个工作区默认带一条兜底条目（任何主机的 GET 记录过允许、不问），每遍登记时删掉它，其余主机一律拒绝，与其余对象只放行模型 API 相同（用户 2026-11-06 定）；每个工作区登记完正好是这四条，驱动核对条目数。每遍起核心之后、读第 2 个基线读数之前，经 engine 调一次模型 API（Claude Code 以 print 模式答一句），E-09 记录里 POST /v1/messages 放行、凭据已放、上游 2xx 才开测；这是第 2.2 节"经对象自己的路径调一次模型 API"在本论文上的做法。engine 只对"每次都问"的条目提问，这套登记里没有，所以不会提问；驱动仍接上 engine 的管理口作保险：任何提问在 1 秒内自动答"只拒绝这一次"，不写记录、不改规则表，出现提问就判为配置错误，停掉该块。每次提问随该次重复的记录写进运行目录。被拒的其余主机请求不重跑（与其余对象拒绝未放行的主机相同），分析时从 E-09 逐遍统计。每次核心运行实际登记的规则命令、模型检查的结果、E-09 记录与核心日志、部署与种子清单，在核心停下时存进运行目录。
- **竞争者**：按形态定义"一个 agent"。VM 型：一台 VM 加它在宿主侧专属的部件。容器型：一个沙箱容器加它专属的部件。同内核进程型：一个会话，即一个受限进程树加它专属的 supervisor 与代理。内核钩子型：一个受管的进程组（cgroup）。与 agent 数无关、全机一份的部件，是共用部件。各对象的具体构成见第 9 节。

**负载对象相同。** 每个单位里放：
- **真实 agent**：Claude Code，所有配置同一个固定版本，同样的配置、工作区内容，不装插件；所有对象用同样的环境设置关掉 Claude Code 的非必要联网（开关在第 8 步试跑核实）。Claude Code 只在第 3.1 节的"常驻"与"跑过负载后"两个状态和第 3.4 节乙里起；第 3.2、3.3 节与第 3.4 节甲里，单位内只有探针与 k6。
- **探针与请求发生器**：同一个程序的同一份静态构建（第 2.3 节）。

**配额。**
- 每个单位 2 个 vCPU、4 GiB 内存，测量中不改。
- **统一规则**：每个单位专属的部件都放进该单位的 cgroup，用 `cpu.max` 与 `memory.max` 设配额。放不进的（例如容器的 supervisor 容器），单列它的 CPU 与内存，结果里标明不受配额。VM 型按 VM 的 vCPU 与内存配置设。
- k6 在单位内，用单位的配额，这是部署成本的一部分；每请求 CPU 秒里扣除 k6 自己的 CPU（第 2.4 节）。
- **本论文**：engine 自己不建 cgroup（2026-10-30 查 engine-v2 代码，2026-11-05 查 v4 相同）。驱动按 uid 认出每个单位隔间里的进程（每次 execution 一个 uid），把它们移进该单位的 cgroup；隔间外的 connector 与文件 worker 按命令行移入：spawner 启动它们时把该行的 uid 与 execution id 作为最后两个参数传给它们（engine 不在记录或行列表里给出它们的进程号）。只在 engine 之外操作。每个单位从起来到移入完成用了多久，逐单位记下；移入之前已经起来的进程同样要移入。定下放法后，先在这种放法下重跑 engine 的集成检查；通过了才用这种放法。不通过时，本论文不设配额照测，四列的数都单列，不进同预算的同侧比较与跨侧的整体边际成本比较，相关假设记"不可检验"。cgroup v2 把进程移进新 cgroup 时，已计入的内存不随之迁移，移入前的分配不受 `memory.max` 约束；这不影响 PSS 列值，结果里记明。

**每个对象用它文档里最严、又能让固定负载跑通的配置**：凭据走它的代管路径，网络按目的地放行，只放行本协议的上游与第 2.2 节的模型 API。配置文件原样存进运行目录。不用任何测试专用的放行捷径。某项保护在本机内核上起不了作用或换了实现路径，照样测，结果里标明。

## 2. 共同环境

### 2.1 机器

- AWS EC2 `m8i.4xlarge`，us-east-1，按需实例：16 个 vCPU（Intel Xeon 6975P-C），61 GiB 内存，193 GB 系统盘，Ubuntu 24.04.5，内核 7.0.0-1014-aws；Landlock ABI 为 8；EC2 嵌套虚拟化已打开，`/dev/kvm` 存在；无 swap（2026-10-30 实测）。所有对象都在这一台宿主上，只有一侧，所有列都可直接比。
- 这台机器本身是 VM：VM 型对象是嵌套虚拟化，结果标"嵌套"，不代表 VM 型在裸机上的表现；其余对象跑在这台 VM 的内核上。同一实例的邻居负载不可控，干扰判据（第 4 节）只看本机的外部进程。
- **驱动以 root 跑在服务器上**，用 `setsid nohup` 与 SSH 会话脱钩。所有长连接（Claude Code 会话、探针）由一个常驻进程拿着；驱动与它自己都放进 `sotamem/harness` cgroup，算测量设施。
- 原来的本机（i7-13700KF，Windows 11 加 WSL2）只用于驱动试跑，不出结果。

### 2.2 上游、解析与模型 API

- **一个上游程序**：nginx，固定版本，TLS 1.3，回固定 1 KiB 正文，证书由本次测量自建的测试 CA 签发。它服务三个测试域名：甲类放行目的地、乙类带凭据目的地、拒绝目的地。乙类在上游核对请求里是否为真值。
- **访问日志**逐请求记：时刻（`$msec`）、请求耗时（`$request_time`）、连接号（`$connection`）、该连接上的第几个请求（`$connection_requests`）、TLS 会话是否复用（`$ssl_session_reused`）、协议版本、路径、状态、乙类的核对结果。
- **地址**：上游放在 WSL 里一个单独的网络命名空间，经 veth 接出，用全局形态的地址，因为本论文的 connector 只连全局可路由、又不是本机接口的地址（条款 7），有的竞争者也拦内网地址。测量期间本机到这个地址真实主人的流量会被截下，测完删掉路由与命名空间。每次重启 WSL 后，重建命名空间、上游与 DNS，并跑一次不加系统的探针确认可达。
- **解析**：同一个命名空间里放一个权威 DNS，作为所有对象的解析器。它答三个测试域名；模型 API 的名字转发到真实解析器；其余名字答不存在。对象不允许指定解析器的，记下它实际走的解析路径。
- **模型 API**：所有对象整晚放行，与本论文的固定登记一致。Claude Code 还会联系的其他主机，由第 8 步试跑列出；这些主机在本论文登记为记录过禁止，在其他对象拒绝，所有对象相同。真实 agent 一项开跑前，在每个对象的一个单位里经该对象的路径调一次模型 API，得 200 才开跑。
- **Windows 一侧**：在 Windows 上放一份同程序、同证书、同正文的上游和解析器，地址放法在第 6 步按该对象的出站过滤定，并记下与 WSL 一侧的不同。
- **逐对象核对路径**（第 6 步）：解析、代理、过滤、TLS 与实际路由各走哪条代码路径，记进第 9 节；与真实部署不同的，结果里标明。
- **时延对照**：在 WSL 一侧上游的 veth 上用 netem 加 20 ms 往返，只对第 3.3 节做一遍。它也会延迟 DNS 应答；只作 WSL 一侧的对照。
- **上游单独监视**：记 nginx 各 worker 的逐线程 CPU 与连接数。

### 2.3 探针与请求发生器

- **请求发生器**：k6，固定版本，静态构建，所有对象用它。若有一种单位跑不通，整个协议换一个所有单位都能跑通的发生器，不按对象换。
- **固定的请求行为**：HTTP/1.1，不重试，不跟随重定向；请求超时、开环的 VU 上限（按速率乘超时预分配）写进配置，所有对象相同。
- **计时以墙钟为准**：每次迭代只发一个请求，取 k6 的迭代时长 `iteration_duration`，它从迭代开始到正文收齐，含建连、代理握手与 TLS 握手。建连、TLS 握手与 `http_req_duration` 之和只作核对（第 11 节）。
- **逐请求唯一路径**：`/<单位编号>/<序号>`，用来把客户端、上游日志与本论文的 E-09 记录逐条对上，也用来定请求的先后。
- **记账**：开环时记计划发出、实际发出、丢弃（`dropped_iterations`）、完成、超时的数量，以及发出时刻相对计划的迟延。
- **分位数**：一律用最近秩法，在原始样本上算。

### 2.4 CPU

- WSL 里用 `taskset` 分开：上游与 DNS 占 vCPU 0–3，采样器占 vCPU 4，被测对象与单位占其余。WSL 的 vCPU 怎样映射到性能核与能效核，本机控制不了。Windows 一侧的 VM 不受 taskset 约束，Windows 上的上游用进程亲和性固定。
- **电源计划设为高性能**（第 8 节）。每个测量块开始前跑一次固定的 CPU 校准（单线程固定计算 5 秒），记下耗时；偏离当夜中位 10% 以上的块标出。
- **每请求 CPU 秒**：逐对象记被测部件在负载期间用掉的 CPU 秒，含 VMM 的 vCPU 线程、核心、connector、前端，扣除 k6 自己的 CPU，按完成的请求数折算。k6 的 CPU 单列。
- **配额节流**：每个单位记 cgroup 的 `cpu.stat` 里的节流次数与节流时长。

### 2.5 内存读数

- **宿主用量**（整体边际成本的口径）：`/proc/meminfo` 的 `MemTotal − MemAvailable`，即实际占用的物理内存。并列记 `Committed_AS`（提交量）与可用内存，分开报，不相加。原来在 Windows 上用的"已提交内存"在 Linux 上没有同义的量，`Committed_AS` 只作参照。
- **按部件归属的 PSS**（非共享一列的口径，第 3.1 节）：每个进程读 `/proc/<pid>/smaps_rollup` 的 PSS，每秒一次。进程按 cgroup 归组：单位、共用部件、测量设施（`sotamem/harness`），其余算外部。VM 型取 VMM 进程的 PSS，它含 guest 已触及的内存。容器型的容器进程就在宿主的 PID 命名空间里，按 Docker 给每个容器建的 cgroup（`system.slice/docker-<id>.scope`）读；服务这些容器的 containerd shim 按命令行里的容器号归入单位。Docker 的守护进程（dockerd、containerd）归共用部件。读数窗口里有单位进程的 PSS 读不到，这个读数标"PSS 不全"，不进剔除后的数。
- **稳定判据看哪个读数**：宿主用量。阈值都是 max(20 MB, 5 MB × 单位数)，单位为 MiB。
- **swap**：服务器没有 swap；swap 用量大于 0 即越线（第 4 节）。

### 2.6 时钟

- 两侧各有一个时钟记录器，每 100 ms 记一对（单调时钟，墙钟）。所有墙钟时间戳（上游日志、k6、E-09 的 `wall_time`）都按同侧的这条记录换算到同侧的单调时钟上；墙钟跳变在记录里是一个台阶，换算时扣掉。
- 正好跨过一次跳变的测量（一次启动、一个延迟组合、一个开环档），重测一次；重测仍跨过的单列，不进主比较。
- **上游的到达时刻**取 `$msec − $request_time`，`$msec` 本身是写日志的时刻。
- **VM 型单位里的 k6 用 guest 的时钟。** guest 里同样每 100 ms 记一对（单调时钟，墙钟），覆盖 guest 自己的跳变。偏移用独立的双向校时求：两侧的上游旁边各放一个校时服务（放行目的地之一），guest 发出时刻 t1，服务回它自己的单调时刻 t2，guest 收到时刻 t3；偏移 = t2 − (t1 + t3)/2，误差界 = (t3 − t1)/2。启动测量里，在观察窗口结束之后做 20 次，不推迟探针；取往返最短的一次；下一个单位开始前再做一次作对照。误差界并入用到 guest 时刻的区间与分辨率；误差界超过 25 ms 的，依赖 guest 时刻的那一项退出主比较。
- **先后顺序**：唯一路径里的序号只用来把客户端、上游与 E-09 的记录对上，不代表先后（并发的请求会乱序）。先后按换算到同侧单调时钟后的时刻判；两个时刻之差小于两者误差界之和的，记为先后不定。

## 3. 四列的测法

### 3.1 每个 agent 的额外内存

- **顺序**：内存是该对象测的第一项。档位从小到大。
- **两个基线读数**，每个都同时记宿主用量、可用内存、`Committed_AS` 与按部件归属的 PSS：
  1. **对象未启动**（用到 Docker 的对象，Docker 的守护进程也未启动）；
  2. **只起共用部件**。
- **每档开建前核对并读数**：与第 2 个读数比，宿主用量与可用内存都回到 300 MiB 以内才开建；开建前的这一刻再记一个读数。等待上限 20 秒。等不到，就清一次页缓存（`drop_caches`），再与**原来的**第 2 个读数比；仍差 300 MiB 以上，这一档记缺测；同一对象发生两次，停掉该对象本晚的内存一项。不以重读基线代替恢复。
- **三个状态**：每档建 N 个单位，依次读三个状态，每个单位都由持有进程拿着一个连接：
  1. **空载**：单位已就绪，只有探针常驻空闲；
  2. **Claude Code 常驻**：每个单位起一个交互式 Claude Code，伪终端由 `script` 提供，停在等待输入；本论文的伪终端由 spawner 给每行建、由隔间内的 pty 转发进程拿着，读数窗口内没有客户端附接，提示符证据在窗口之后附接几秒读取（附接用 40×120 的终端，尺寸变化让 Claude Code 整屏重画）；
  3. **跑过负载后**：每个单位跑完一遍第 3.3 节甲类、keepalive 的延迟负载。负载过程中另记占用的峰值。
- **档位与次数**：N = 1、2、4、8、16，每档 3 次。档位由第 4 节的逐档推算决定跑不跑。
- **等待与读数**：每个状态先等最短时间，再等稳定（最近 10 秒变化小于第 2.5 节的阈值），最多 180 秒，然后读 10 秒。"Claude Code 常驻"的最短等待要盖住它启动后的第二次上涨，时长由第 8 步试跑在每个对象上各量一次，取各对象的最大值，所有对象统一使用；试跑都没观察到第二次上涨的，取 60 秒。其余状态最短 15 秒。读数窗口内变化超过阈值的标为不稳定，剔除前和剔除后两套数字都报。
- **怎样算，三个量分开报**：
  1. **非共享的额外内存**（本列的列值）：每档每个状态，把各单位独占进程的 PSS 加总、除以 N，得每个单位的独占占用；减去"不加系统"在**同档、同状态**下每个 agent 自己进程的 PSS（PSS 会把共享的程序页摊到所有映射它的进程上，所以随 N 变，只能同档相减）。报逐档的值。比较与假设甲只在共同档位上逐档判；表里取共同档位中最高一档的值，并注明是哪一档。"不加系统"那一次重复带标记时，不作参照，改用它在该档无标记各次的平均。
  2. **共用部件**：固定成本 = 第 2 个读数 − 第 1 个读数；每档另报共用部件那组进程的 PSS，随 N 增长的部分单列。
  3. **整体边际成本**：在该对象实测到的档位上，用宿主用量（相对第 1 个基线读数）拟合 used(N) = a + b·N；"不加系统"用同一状态、同样的档位拟合，得 b₀；报 b − b₀。另用"本档读数 − 本档开建前读数 + 共用部件固定成本"再拟合一份，"不加系统"也按同一公式拟合基准，两份并列，相差超过 20% 的标出。
  - 区间：三次重复按重复序号配对（第一遍的两次是 1、2，第二遍的一次是 3），各自算出上面的量，报最小到最大的范围。一次重复因干扰重跑过的，取最后一次。
  - 读数带以下任一标记即不进剔除后的数：不稳定、等稳定超时、受干扰、PSS 不全、常驻时有单位不在输入提示符。
  - 有效档位少于两个，不拟合；逐档增量明显不成直线时，只报逐档增量，不报斜率。
- **主比较全体固定用"Claude Code 常驻"**，只代表这一负载下的占用。某个对象在这个状态下的稳定读数不够半数，它的主比较记"未证"，不换状态。"跑过负载后"全体另列一张表，含峰值。
- **回收**：服务器上不另做回收实测。每档开建前的核对（上面）与对象结束后的清理核对（第 5 节）就是回收的检验，每次的等待时长与是否清过页缓存都记进记录。

### 3.2 启动时间

- **起点**：同侧启动器发出创建命令的时刻。每个对象"创建并在单位内运行探针"的命令序列，第 6 步写进第 9 节。
- **探针循环**，单位一起来就同时开始，都是开环：每个循环固定到达速率每秒 50 个，请求超时 1 秒，预分配并发数 = 速率 × 超时，在途的请求各用自己的连接，一个请求挂起不影响下一个发出。所有对象用同样的速率；速率定得低，是为了让并发启动时各单位的探针加起来不压住被测对象，并让本论文一轮并发启动的请求数放得进一次核心运行的记录额度（第 3.4 节）。放行循环与凭据循环在各自第一个请求成功到达上游后就停发，观察窗口里只剩拒绝循环。拒绝循环每个请求新建连接（k6 的 `noConnectionReuse`），使在建连时执法的对象与逐请求执法的对象受同样的检验。每轮记下所有单位探针的总速率；第 8 步试跑核对 N = 8 并发启动期间本论文的判定口接收队列不持续增长、核心 CPU 低于一个核的 50%，不满足就所有对象统一再降速率。
  - **放行循环**：请求甲类放行目的地；
  - **拒绝循环**：请求拒绝目的地。拒绝目的地也由同一个上游服务，所以请求到没到上游能在上游日志里看到；
  - **凭据循环**：只对有凭据代管的对象，请求乙类目的地，用于"凭据代管就绪时间"。
  每个请求都带该单位的唯一路径。
- **可服务时间**：起点到上游日志里该单位第一个放行请求的时刻。
- **拒绝循环里每个请求的判定**：
  - **泄漏**：它出现在上游日志里；
  - **确认被挡住**：只认该对象策略部件发出的拒绝信号（例如它的代理回的特定状态与正文），或该对象自己的策略日志里有这条请求的唯一路径。每个对象认哪一种、长什么样，第 6 步写进第 9 节；
  - **无法判定**：其余一切，包括本地的连接被拒、解析失败、超时。
  泄漏与无法判定从起点开始都计，报次数与首末时刻。
- **策略就绪时间报成区间**：
  - 下界：最后一次泄漏的那个请求的发出时刻（取发出而不取到达，是因为策略可能在它过了策略点之后、到达上游之前才生效）；没有泄漏时取起点。无法判定的请求不提供下界；
  - 上界：在下界之后、第一个确认被挡住的请求的拒绝被记下的时刻，即客户端收到拒绝信号的时刻，或对象策略日志里的时刻，取两者中较早而又可用的那个，换算到同侧单调时钟（第 2.6 节）。看不到请求路径的对象（隧道代理、connect() 钩子），该单位、拒绝目的地、下界之后的任意一条拒绝日志都可以当上界。
  - 列值取上界，区间宽度一并报。
- **观察窗口**：可服务时间之后再观察 10 秒，然后停止发出，等在途的请求全部结束（最多 1 秒超时）。窗口内没有确认被挡住的请求、窗口末尾仍有泄漏，或区间算不出来，策略就绪时间记"未证"。只会静默丢弃、又没有策略日志的对象，策略就绪时间因此记"未证"。
- **分辨率**：逐对象报各循环在终点附近实际达到的发出间隔。
- **时钟**：起止换算到同侧的单调时钟上（第 2.6 节）。
- **不适用的情形**：
  - "不加系统"只报可服务时间，策略一项写"不适用"；
  - 不能按目的地拒绝的对象，策略就绪写"不适用"。若它有凭据代管，另报凭据代管就绪时间（凭据循环里第一个到达上游时已带真值的请求），这一项不与其他对象的策略就绪时间并列比较。
- **串行**：两遍扫描各做一组，每组先热身 2 次，再连续 10 次，每次建好、测完、删掉、核对清理干净后才建下一个。每组报中位与 p90，不报 p99。
- **并发**：同时建 N 个，N 取 4 与 8 里该对象安全可行的档，可行的不到一档记缺测；每档 3 轮。报每轮每个单位的两种时间（中位、最大值），以及从第一个发出到最后一个就绪的总时长。轮与轮分开报，不当作 N 个独立样本合并。
- 镜像与模板事先缓存好。第一次冷启动单独测 1 次，单列。失败与超时计数，与成功的分开报。

### 3.3 每请求延迟

**engine v4 这一轮（用户 2026-11-06，计划 engine-v4-request-latency，驱动 driver/latency.py）。** 只测本论文与直连，其他对象不测，它们的延迟引原文的数。与下面写法的差别：服务器 16 vCPU（32 vCPU 是并发列要的）；3 遍，每遍起一次新核心，组与两臂的先后按种子打乱；上游 nginx 在单独的网络命名空间，条目用 --address 点名它的非全局地址，connector 用 --ca-file 信任测试 CA，第 2.2 节的全局形态地址不再需要；不加 netem 对照；不开完成记录开关，它每个请求多写一条记录，那就不是默认路径，请求成不成功看 k6 与上游日志；加一组大请求（POST 64 KiB，回 1 MiB，带凭据、复用连接），上游读完整个请求体才回应；直连的 k6 以普通用户跑在同样配额的 cgroup 里。另做一次落盘对照：只跑带凭据、复用连接一组，记录放内存盘一次、放磁盘一次，部署建好后等写回稳定；内存盘不是部署方式，只用来量等落盘占多少。

- **请求**：单位内的 k6 经该对象的路径向上游发 GET，回 1 KiB 正文，同一时刻只有一个请求在途。
- **两类目的地**：
  - **甲类**：不带凭据的放行目的地，所有对象都测；
  - **乙类**：带凭据的目的地，请求里放占位值，由该对象替换成真值，上游核对。不支持凭据代管的对象，乙类记"不支持"。"不加系统"的乙类直接带测试用的真值，完成同样的认证。
- **三种连接方式**：
  1. **keepalive**：客户端复用连接；
  2. **客户端冷**：客户端每个请求新建 TLS 连接、不复用会话，上游照常允许 keepalive；
  3. **客户端冷、上游冷**：在 2 的基础上，上游关掉 keepalive 与会话复用。
  对象内部各跳是否复用连接，是它自己的行为，本协议不去拉平。逐跳记录：客户端侧的握手数与会话复用（k6 记）、上游侧每个请求新建的连接数与会话复用（上游日志记）。跨对象比较按实际部署的成本，不声称各对象做了同样多的握手。
- **次数**：每个组合先热身 100 次，再测 1000 次。做两遍，分在两遍扫描里（第 4 节）。每遍内"经该对象"与同侧"不加系统"交替各跑一组。
- **列值** = 经该对象 − 同侧"不加系统"，中位与 p99 分别相减，写作"分位点差"，它不等于新增耗时本身的 p99。每遍各报一次，两遍的差照实报。不报合并样本的区间：同一遍里的请求彼此相关，不能当独立样本。
- **本论文另报三段**，只读 E-09 已有记录，不改 engine，只用来看量级，不相加，不当作端到端的分解：
  - **核心判定时间**：同一请求的 `request_decided` − `request_admitted`。准入时刻是核心读到这一帧时盖的，不含之前在判定口的排队；v4 的放行记录在放行之前写，放行要等它落盘，所以这一段不含落盘等待；乙类还含读取凭据的时间；
  - **PDP 往返**：`pdp_answered` − `pdp_requested`；
  - **放行记录到上游记完**：上游的 `$msec` − `request_decided` 的 wall_time，同一台机器的钟，上游日志到毫秒。含等放行记录落盘、connector 发出与上游处理。
- **停顿不剔除**：超过本块中位两倍的样本计数报告，留在结果里。

## 4. 档位、停止、干扰与调度

- **停止线**（服务器）：可用内存低于 3 GiB、宿主用量超过总内存的 90%、swap 用量大于 0、系统盘剩余低于 5 GiB，任一条触发就停止加档。停止线每秒判一次；正在跑的一档越线，立刻中止这一档并清理。
- **逐档推算**：每档开跑前，按已测档位直线外推并乘 1.25，推算会越线就不跑这一档，记"推算拦下"。
- **三类进程的边界**：
  - **测量设施**：驱动、启动器、持有进程、采样器、时钟记录器、上游、DNS；
  - **被测部件**：该对象的进程、VM、容器，以及单位内的负载；用到 Docker 的对象，Docker 的守护进程也算它的共用部件；
  - **外部**：其余一切（系统服务、SSM 与 CloudWatch 一类的云代理、内核）。外部读数 = 三组之外所有进程的 PSS 之和。不用"宿主用量 − 三组 PSS"：PSS 也计入可回收的文件页（例如 VMM 映射的镜像），宿主用量不计，两者之差不是外部进程（2026-10-30 试跑实测，Docker Sandboxes 因此每个读数都被误判为受干扰）。页缓存与内核的变化不算干扰，由收尾核对的原始比较照实记录。
  只有外部进程的变化算干扰：内存变化超过 300 MiB，或负载阶段 CPU 比基线高出 5 个百分点。受干扰的一轮自动重跑，最多 2 次；仍受干扰的数据只放附录，不进主结果。本论文出现过 engine 提问的块，也按干扰处理。
- **不测时停掉不用的东西**：Docker 的守护进程（dockerd、containerd 与 docker.socket）只在测用到它的对象时运行（第 9 节），从第 1 个基线读数之后起、到该对象清理时停，它是否已停纳入清理核对。判断它在不在跑只看 systemd，不调 docker 命令，因为调用会把停着的守护进程经 socket 拉起来。
- **两晚，按列分**：每一列的全部对象在同一晚测。
  - 第一晚：内存（第 3.1 节）与启动时间（第 3.2 节）；
  - 第二晚：延迟（第 3.3 节）与并发（第 3.4 节）。
- **实际排法（用户 2026-10-30 定）**：先测内存一列的前两个状态（空载、Claude Code 常驻），对象是当天装得上的，第 9 节名单里本论文、Gondolin、Kairos 不在内；这一轮的数算正式结果。原定在本机夜里跑，改为在服务器上白天跑（第 2.1 节），无人值守，不需要清场。内存的"跑过负载后"状态挪到延迟那一轮，所有对象一起测，因为它要用第 2.2 节的整套上游。本论文与这一轮没赶上的对象另一轮测；那一轮重测"不加系统"与一个 VM 型对象作对照，两轮之差照实报，作为跨轮漂移的量级。Gondolin 与 Kairos 的那一轮在 2026-10-31 晚测（计划 sota-memory-gondolin-kairos），同轮重测只放行模型 API 的不加系统与 Docker Sandboxes 两个锚点；与 10-30 那轮相比，前者各档相差不超过 0.4 MiB，后者 2–16 档不超过 4.3 MiB（runs/20261101-memory-analysis-vm）。不同实例之间的差也算在这个漂移里，所以两轮尽量用同一台实例（停机不终止）。
  - **OpenShell 补测（用户 2026-10-30 同意）**：2026-10-30 的全规格内存测量里，OpenShell 建第一个单位就出错（gateway 留着下午常驻曲线实测时的同名沙箱记录，报"already exists"），按第 5 节整轮跳过。驱动改为 gateway 起来后、读第 2 个基线之前先删遗留沙箱，主测量结束后在同一台实例、同一份配置下单独补测 OpenShell（两遍，2 次加 1 次）。它不与其他对象穿插排序，结果单列"补测"。
  - **只放行模型 API 的不加系统（用户 2026-10-30 同意）**：全规格测量里 nono 与 Connection Escrow 比不加系统低 13–19 MiB，推断是因为不加系统的 Claude Code 能连上 GitHub 与 downloads.claude.ai，其余对象都拒了。补测一个对象 bare-api-only：与不加系统相同，只是单位的用户只能连模型 API（启动时解析出的地址的 TCP 443）与回环，其余连接立即拒绝（iptables 按 uid 匹配，规则随共用部件起停）。同一台实例、同一份配置单独补测，结果单列；分析时两种不加系统各作一次基准。
- **两遍扫描**：每晚做两遍，每一遍都覆盖全部对象。第一遍按固定随机种子排出的顺序，第二遍倒过来。需要重复的项，在两遍之间这样分：内存每档 3 次，第一遍 2 次、第二遍 1 次；串行启动两遍各一组；并发启动每档 3 轮，同样 2 与 1；延迟两遍各一遍；真实 agent 的 N = 1 三轮，同样 2 与 1。第二遍里每一档要么全做，要么全不做。
- **日程**：脚本按以上规则预先生成整晚的日程，写进运行记录。单个对象的时限按第 8 步试跑实测的时长乘 1.5；超时的项记"缺测"，不重排。

## 5. 每个对象的流程

1. 起：读第 3.1 节第 1 个基线读数，再起共用部件，等健康检查通过，读第 2 个基线读数；本论文另核 E-09 剩余额度（第 3.4 节；内存一列每遍只有几百个请求，不核）；
2. 测：按本晚的列，依次做各节；
3. 清理：放在必执行的收尾里，出错也执行。删掉全部单位与共用部件；
4. 核对清理干净：进程、VM、容器都已消失，用到 Docker 的对象 Docker 已停；宿主用量与可用内存回到第 1 个基线读数 300 MiB 以内，比之前先扣掉外部进程（第 4 节）自第 1 个基线读数以来的变化，原始的比较结果一并记录。等待上限 180 秒。核对不过，清一次页缓存后再核一次；仍不过，**整轮停跑**，写明残留什么，因为之后的对象读数会被污染。

某一步出错，记下错误和当时的状态，执行清理与核对，跳过该对象本晚剩下的项，接着跑下一个对象。全部跑完写汇总。

**2026-10-30 服务器上的搭建与冒烟结果**（各对象的确切命令与报错原文在 [setup/](setup/) 各笔记的"服务器"一节，驱动的适配在 driver/objects.py）：
- **所有对象的 Claude Code**：同一版 2.1.312，同一个原生二进制（sha256 4f4178ce…），停在输入提示符；每个单位在常驻读数之后读一次屏幕，结果记进该次读数（OpenShell 只读第一个单位，接入要约 10 秒并会重绘终端）。key 的交法按对象能走通的取：
  - 不加系统、nono、Connection Escrow 用同一个预置脚本（/opt/sota-setup/common/seed-claude-home.sh）与同一组环境变量，key 经 `apiKeyHelper` 读环境变量；nono 给沙箱的是每个会话现生成的占位令牌，事先无法批准，只能用这种；
  - OpenShell 与 Agent Vault 走各自的凭据代管：容器里只有占位值，真 key 由它们的代理注入。
  这三个进程型对象的单位以普通用户 jerry（uid 1001）运行。拿着单位 stdin 的进程（`sleep`、`script` 与它们的 shell）一律算测量设施。k6 空载脚本：除 OpenShell 与 Agent Vault 镜像里那份等效写法外，所有对象同一份。
- **单位之间还有的差别**：OpenShell 的常驻单位是新建的沙箱，不是空载时那一个（它的主进程在创建时定），Agent Vault 同样每个状态起一次新运行；不加系统能连上 GitHub 与 downloads.claude.ai，其余对象会拒绝，Claude Code 启动时会去连这些主机，连没连上对常驻内存的影响未核实。
- **Docker 的守护进程**：OpenShell 与 Agent Vault 的共用部件，按第 4 节只在测它们时运行；Docker Sandboxes 不用它。
- **nono**（v0.80.0）：服务器内核的 Landlock 到 ABI 8，代理模式在内核层生效（实测：沙箱里按 IP 直连任何地址都被拒，只有代理端口能连）。不再是本机 WSL 上的降级模式。
- **Connection Escrow**（commit 90124bf3，单机模式）：16 个预先登记的槽位 cgroup，起单位不含登记时间；不代管凭据。只挂了 `connect4`：槽位里经 IPv6 socket 连 `::ffff:<IPv4 地址>` 能直接连上外部主机，拦截器没有任何记录（实测，只试了一个目的地）。这一条进安全那几列，内存一列不受影响。
- **NVIDIA OpenShell**（v0.1.6，默认网络模式：supervisor 容器用宿主网络，workload 容器没有网络）：一个单位是两个容器加各自的 shim；配额只能用 `docker update` 设在 workload 容器上。原生 Linux 是它官方支持的平台。
- **Agent Vault**（v0.40.2，容器模式，自建镜像只把 Claude Code 换成固定的 2.1.312 二进制）：它把每次运行的转发器绑在那次新建的 Docker 网络的网关上，而容器里的 `host.docker.internal` 固定指向 docker0（172.17.0.1），它的防火墙也只放行这个地址，所以按原样连不上自己的代理（实测）。测量时加一条宿主 nat 规则（用户 2026-10-30 同意），把容器发往 172.17.0.1 的 TCP 连接转到所在网桥上的转发器，结果里标"绕行"；规则随共用部件起停。宿主上的 `vault run` 与 `docker run` 客户端由驱动移进单位的 cgroup，容器用 `docker update` 设配额。
- **Docker Sandboxes**（v0.46.0，Docker 的 apt 仓库；用户用自己的 Docker 账号登录）：不依赖 Docker 的守护进程。全局网络策略为全部拒绝、只放行模型 API；凭据走它的代管路径（代理注入，沙箱里只有占位值），本机上这条路返回 401，服务器上能用。一个单位在宿主上是一个 VMM 进程，配额是 VM 自己的 2 CPU / 4 GiB；沙箱在没有会话时会自己停掉，切换状态时先开新会话再关旧会话。
- **Gondolin**（v0.14.0）与 **Kairos**（commit 52563455）：2026-10-31 搭建、冒烟与补测，搭建命令、遇到的问题与冒烟结果在 setup/gondolin.md 与 setup/kairos.md 第 2 节，驱动的适配在 driver/vm_objects.py。两家各 16 个单位起得来；常驻曲线 300 秒没有第二次上涨，常驻最短等待照旧 150 秒。
- **本论文**（2026-11-05 起测 engine 留档版本 v4，即 ExperimentLab/engine-v3 @ a9eff999，prove/baseline 的 v4；10-31 那轮测的是 engine-v2-go commit 91217a10，搭法在那轮运行目录的驱动快照里。驱动的适配在 driver/engine_object.py 与 driver/engine_deploy.py）：照 engine 自己的门部署。部署根是 root 所有的 btrfs 回环镜像，16 个工作区各一个子卷，存储属工作区专用属主（uid 70997）、0700，内容在固定子目录里；hook 目录属 engine uid 与 PDP 组；目录里显式写运行时放法。执行 uid 区间 512 个（engine 同一次启动内不复用 uid，一遍最多起 124 行）；种子是 7.1 那套（Claude Code、bash、Go 前端、MCP server、pty 转发进程、ldd 补库）加 k6；不登记宿主文件，Claude Code 不接 MCP，与其他对象相同，MCP server 与文件 worker 照 v4 每行都起。简易 PDP 在核心之前以它的专用 uid 起，核心带测量开关（engine-v3 README"完成记录开关"）起：v4 只在这个开关下记请求的完成，模型检查要的上游状态码从那里读。经 sudo 起的进程 core 硬上限是 0，核心起前设为 unlimited（child.c 要把 core 上限设为 1）。建部署后清缓存、等整机已用稳定再读第 1 个基线读数。v4 自己的检查在服务器内核上都过（engine-v3/runs/20261105T1*-server-*）；驱动的 cgroup 放法下 engine 的集成检查与 7.1 门两种放法也都过，门的那一行 6 个进程都移进了同一个单位 cgroup（engine-v3/runs/20261105T121*-server-*-placed）。

## 10. 时间预算（推算，第 8 步试跑后按实测重估）

每晚可用约 7 小时。下表按 VM 型的较慢情形估一个对象；进程型、内核钩子型与"不加系统"远快于此。

| 第一晚的项 | 时长 |
|---|---|
| WSL 重启、基线、共用部件、清理与核对 | 6 分钟 |
| 内存：5 档 × 3 次 × 3 个状态（VM 型多半只到 4 或 8 档） | 35 到 50 分钟 |
| 启动时间：串行两组各 12 次，并发 2 档 × 3 轮，每次含 10 秒观察窗口 | 15 分钟 |
| **合计** | **约 55 到 70 分钟** |

| 第二晚的项 | 时长 |
|---|---|
| 起、清理与核对 | 5 分钟 |
| 延迟：2 类 × 3 种连接 × 2 遍，与"不加系统"交替；netem 对照 1 遍 | 15 分钟 |
| 压测：开环约 8 档 × 30 秒 × 2 种连接，闭环 6 档 × 30 秒，上游加倍检验 2 档 × 2 次 | 18 分钟 |
| 真实 agent：N = 1 三轮，N = 4、16 各一轮 | 25 分钟 |
| **合计** | **约 62 分钟** |

按 9 个配置、其中 5 个是 VM 型或容器型估计，每晚约 6 到 8 小时，可能超出。第 8 步试跑后若仍超出，按以下顺序删减，所有对象一致，写进配置文件后冻结：
1. 内存的"空载"状态只测 N = 1 和最高档；
2. 闭环压测去掉 32 档；
3. 仍超出则加第三晚，按列拆分，不按对象拆分。

真实 agent 一项要调模型 API，费用在第 8 步试跑后按实测估算报用户。

## 11. 交第 8 步试跑核对的事实

下列事实只有数据能回答，第 8 步试跑时逐项核对，结果写进试跑记录。核对结果与本协议的假定不符时，按"退路"一列处理，处理结果随第 9 步交两家审脚本。

| 要核的事实 | 怎样核 | 退路 |
|---|---|---|
| k6 的迭代时长等于请求的完整时长 | 在"不加系统"、一个隧道型对象、一个终结 TLS 的对象上，对两种冷连接方式，用包住调用、读单调时钟的脚本对照；比的是"经该对象 − 不加系统"的差，不比绝对值 | 两种取法的差超过 1 ms 的，改用脚本计时，所有对象一起换 |
| 经 CONNECT 代理时，代理握手算在迭代时长里 | 同上，看隧道型对象的差 | 同上 |
| HTTP/2 已关掉 | 客户端一侧看 k6 记录的协议版本，上游一侧看访问日志；终结 TLS 的对象两段都要看 | 找到可用的关闭办法；找不到的组合记缺测，换发生器则全部重验 |
| 各对象的回收时长 | 第 3.1 节的回收实测 | 10 分钟内回不到，改为每档每次重启 WSL |
| 各对象安全可行的最高 N | 逐档推算加小规模试跑 | 定各侧共同档位与各项的可行档 |
| Claude Code 常驻第二次上涨的时长 | 每个对象各一个单位，记录内存随时间的曲线 | 取各对象的最大值作"常驻"的最短等待，所有对象统一；都没观察到的取 60 秒 |
| Claude Code 联系哪些主机，非必要联网的开关是否生效 | 常驻与跑任务时，记下解析器收到的全部名字 | 按第 2.2 节登记或拒绝；开关无效则所有对象都不用它 |
| 容器进程的 PSS 能否读到 | 在容器型对象上，从能看到容器进程的命名空间读 `smaps_rollup` | 读不到的，该对象的非共享一列记缺测；cgroup 的内存计数只作描述，不进比较与假设判定 |
| k6 在最高计划速率下的常驻内存 | 单位内量 k6 的 PSS | 超过单位内存配额的 25%，所有对象一起改用小预分配加上限；到上限而丢弃的档按第 3.4 节停止加档 |
| 各对象的拒绝信号或策略日志 | 拒绝循环里看各对象拒绝时回什么、日志里记什么 | 写进第 9 节作"确认被挡住"的依据；两样都没有的对象，策略就绪记"未证" |
| 校时服务能否从每种单位里访问 | 起一个单位，做 20 次双向校时 | 访问不到或误差界超过 25 ms 的，依赖 guest 时刻的项退出主比较 |
| E-09 每个请求的记录字节数 | 跑 1000 个请求，量记录文件 | 按实测值重算每块的额度与"写盘上限截断"的块 |
| engine 在驱动的 cgroup 放法下能正常收尾 | 重跑 engine 的集成检查 | 本论文不设配额，四列都单列，不进同预算比较与假设判定 |
| 两侧的时钟记录器可用 | 连续记录一晚长度的（单调时钟，墙钟）对 | 不可用的一侧，启动时间记缺测，假设乙记"不可检验" |
| 各对象每晚的实际时长 | 小档位整体试跑 | 按第 10 节删减 |
