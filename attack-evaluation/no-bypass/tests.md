# 1.1 不可绕过 — 测试规格

这是 1.1 隔离论证的验证测试：对本机上、由本次运行从固定版本编出的沙箱，确认越权的尝试被挡住；目标是本次运行自建的诱饵；不研究、也不记录任何绕过方法。

## 0 本文件

**用途。** [attacks.md](attacks.md) 里 28 个攻击各自怎样测、怎样判：目标、判据、对照、事后核对，以及不设防配置下怎样判；另有三个正对照。攻击做什么、预期挡住它的机制，以 attacks.md 为准，这里不重写。harness 的共用做法见 [harness 设计](../harness/README.md)，结果四类见 [METHOD](../METHOD.md) 规则 4，判据、对照与事后核对的写法沿用反向测试规则 §1。

**状态。** 第三稿（2026-10-31）：按两轮两家 review 改过；用户定改完不再复审，由第 6 步的代码 review 与第 7 步的试跑接着查。

## 1 共用约定

### 1.1 由哪种程序去做

ZTAC 按"经什么去做"把攻击分成四类；本文的文件读写与程序执行不经 engine 代办，四类只是换了程序，同一份代码在两种配置下跑。

| ZTAC 类别 | 本文由什么程序做 | 攻击 |
|---|---|---|
| fs（经文件工具） | bash：读用 `$(<路径)`，写用重定向；不建上级目录 | NB-01、02、03、07、08、09、12、15 |
| exec-py | python3.12；网络用 socket 模块的普通 TCP、UDP 与 Unix socket，不读环境里的代理变量 | NB-04、10、16、19、21、24、25、26、27、28 |
| exec-git | git | NB-05、11、13 |
| direct | 本次运行编译的静态 C 探针，直接发系统调用 | NB-06、14、17、18、20、22、23 |

NB-21、NB-24 属 ZTAC 的 direct 类，这里用 python：NB-21 要说管理口的帧格式，NB-24 要在隔间的 pid 1（运行器）里做。

**bash 与 git 的观察。** 它们不报 errno。运行器记下退出码与 stderr，要求 stderr 里有点名目标路径的那一行，没有就记无效；errno 取这一行末尾的出错文本，如 No such file or directory。git diff --no-index 读不到文件时只说 Could not access，不带出错文本（git 2.43.0，2026-10-31 实测），这时以同一路径 stat 一次取 errno。其余情况 stat 只作交叉核对，与出错文本不一致记无效。

### 1.2 诱饵、哨兵与外部事实

- **哨兵。** 每个诱饵含一个随机哨兵串。每个攻击跑之前，harness 把它要读或要写的诱饵重写一遍，换成只属于这一次的新哨兵，路径、属主与权限不变；只找这一次的哨兵，前面攻击留下的不干扰。engine 自己的对象（工作区表的磁盘镜像、E-09 记录）不重写，只记基线；NB-20 的诱饵凭据由 harness 经管理口重新登记，换新哨兵。
- **跑前核对目标。** 诱饵存在，记下设备号、inode、大小与 sha256；监听端在监听（看所在 netns 的 socket 表，不去连）；目标进程在，记下 pid、uid 与启动时间，harness 对它开 pidfd。
- **读出算不算成功。** 每个读的步骤把拿到的全部字节写进 work0 里本攻击的捕获文件（git 取 stdout），与观察文件分开。本次哨兵出现在捕获文件里，或出现在测试上游本攻击窗口内的请求记录里，就是成功。扫描只读这两处，不跟随 symlink：work0 里预置的 symlink 指向宿主诱饵，扫描跟着走会自己读出哨兵。
- **写入算不算成功。** 诱饵的内容（sha256）或身份（设备号、inode）变了，或目标路径上出现了新文件，就是成功。
- **连接算不算成功。** 看诱饵服务与监听端的记录，记录里有对端凭据与收到的字节。只取本次尝试开始时的记录游标与结束标记之间的条目：窗口过后，harness 自己向用到的每个监听端发一个带结束标记的连接（UDP 发一个报文；受害 execution 的监听在它自己的 netns 里，harness 进入那个 netns 去发），标记出现在记录里才读。标记不出现，或服务不响应，记无效。诱饵服务认得出结束标记，把它记作结束标记，不为它建标记文件（NB-27）。
- **信号与网卡。** 分别看目标进程的状态、诱饵 netns 的网卡列表。
- **窗口。** 本文 engine 配置下行关闭之后，不设防配置下攻击进程及其子进程全部退出之后，再等 1 秒取外部事实；用到监听端的，另等结束标记。隔间的 pid 1 退出时，内核收掉整个 pid namespace 的进程。例外两处：NB-21 等发往诱饵主机的请求有最终结果；NB-26 在攻击进程还活着时观察。见各条。
- **同步文件。** 要等 harness 观察或确认的攻击（NB-21、NB-26），运行器写"已发出"或"完成"，等 harness 写放行文件再往下走。这些文件按运行、配置、攻击与重复次数唯一命名，内容带本次随机串；跑前核对不存在，harness 观察或确认完才写放行。
- **万一调用成功了。** 路径类攻击只打开已存在的路径、不建上级目录，隔间里的预期观察是 ENOENT。若某个调用在隔间里返回成功，核对它作用到的对象（设备号、inode）是不是那个诱饵；不是就不算成功，按观察到的机制归类。

### 1.3 观察对应哪个机制

记的是第一个失败步骤的观察。机制在 v2 里的位置见第 3 节。

| 观察 | 记为 |
|---|---|
| 打开宿主上的诱饵路径、另一个工作区的路径或 engine 状态目录下的路径，得 ENOENT | 文件视图 |
| 同上得 EACCES | 文件权限 |
| 继承的 fd 只有 pty 与控制 socket，以它们为锚点 openat 得 ENOTDIR | 文件视图（交付的 fd 不指向目录） |
| 连 lo 以外的地址得 ENETUNREACH | net namespace |
| 连宿主上在监听的 127.0.0.1 端口或抽象名得 ECONNREFUSED，而同一段代码连自己开的同类监听成功 | net namespace |
| 隔间的 /proc 下没有这个宿主 pid，kill 得 ESRCH | pid namespace |
| kill 得 EPERM | uid 不同 |
| unshare 带 CLONE_NEWUSER 得 EPERM，clone 带 CLONE_NEWUSER 得 EPERM，clone3 得 ENOSYS | seccomp 过滤器 |
| 建网卡的 rtnetlink 请求：sendto 返回整长，内核应答（NLMSG_ERROR）里是 -EPERM | 无 capability |
| 系统调用本身返回 EPERM（白名单外的调用，如 sendmsg） | seccomp 过滤器 |

seccomp 的 EPERM 是系统调用本身的返回值；缺 capability 的 EPERM 在 rtnetlink 的应答里，两者按上表分开记。unshare 的 EPERM 记为 seccomp 的依据：同一进程先调 unshare(0)，内核对参数为 0 一律放行，它也得 EPERM，就只能来自 seccomp（unshare 不在 workload 白名单里，白名单外的调用一律 EPERM）。

### 1.4 不设防配置下的成功是前提

本文 engine 配置下记"挡住"，要求同一次运行里、同一份攻击脚本与同一份请求（work1 里的目标换成该配置自己的工作区，见 1.7）在不设防配置下成功；不设防配置下没成功的，engine 下的结果先记无效，查清原因再定（用户 2026-10-31）。不设防配置是全部机制都不设防，不是拆掉一个部件的消融。

理由：隔间里的很多观察，如 ENOENT、ECONNREFUSED、建网卡得 EPERM，与攻击代码自己写错了长得一样；只有同一份代码在什么都不设防时确实达成了效果，才能排除后者。各攻击自己的对照步照旧要做：对照说明攻击代码在隔间里跑得起来，这一条说明它确实能达成效果。

按目标要求：一个攻击打几个目标（几个地址、几条路径、几个进程、几支做法）的，每个目标在不设防配置下各自要有预期结果，engine 下才可对它记挡住；没有的，engine 下对它记无效，不由同一攻击的其他目标代替。隔间里得到的 ENETUNREACH、ECONNREFUSED、ESRCH 与目标值无关，请求里某个目标写错，隔间里也会得到预期的 errno，逐个要求才排除得了。不设防下的预期结果多数是成功；NB-23 的 spawner 与 connector 是"启动时间对上之后得 EPERM"，这同样证明请求里的目标是对的。

不设防配置的身份见 1.7，不是隔间里本行的 uid；除了信号（NB-23）与文件、socket 的权限，这些攻击的调用与 uid 无关。

### 1.5 无效的共用条件

对照步失败；运行器没读到请求；观察文件缺失或不完整；跑前核对目标失败；超过 30 秒；外部事实读不出；监听记录的结束标记没出现；1.4 的前提不满足。每个写原因（规则 4）。

### 1.6 重复

28 个攻击都不依赖时序：没有竞态、换址、撤销时的流式响应或崩溃注入。各跑一次，即规则 7 的 R = 1。同一 engine、harness 与脚本下跑出不同结果时，按 harness 设计第 6 节改为重复 R 次报。

### 1.7 不设防配置

同一份攻击代码、同一份请求，以 uid 1000、gid 1000 并带 uid 1000 的附加组，直接在宿主上跑（harness 设计第 5 节）：cwd 是本次运行在临时目录下另建、属宿主用户（uid 1000）、0700 的不设防 work0，HOME 指向诱饵 home。"另一个 execution"的工作区同样另建为不设防 work1，它的受害程序也直接以 uid 1000 在宿主上跑，与攻击在同一个 net namespace 里。v4 起部署里的工作区归专用 uid 70997、根目录 0700，宿主用户进不去；不设防即现状，agent 的工作区就是宿主用户自己的目录（METHOD 规则 3）。判定方式不变。

- 请求里宿主一侧与 work1 的目标给绝对路径；work0 里的对照目标只给相对名，由运行器按 cwd 拼成绝对路径。work1 的目标按配置给各自的绝对路径：engine 配置给部署里 work1 的两条路径，不设防配置给不设防 work1 的两条路径；跨配置比对请求时，按工作区、路径种类与相对路径认作同一个目标。其余部分两配置共用。
- 请求里每条宿主路径的每一级上级目录，uid 1000 都能进入。跑前 harness 以 uid 1000 身份逐条核对，不满足就不跑，记无效。

### 1.8 跑前建的诱饵

位置说明：NB-19/27 的路径 socket 实际为 `scratch/nb-decoy-<name>/socket`；连接目录属 root、0755，宿主 uid 1000 可进入但不能改写其证据。不是上文用于普通诱饵文件的 uid 1000 所有的 `host/` 目录；socket 自身的属主、权限、两配置前提与各攻击判据不变。

## 2 逐个攻击

### 2.1 读宿主上的诱饵私钥（NB-01–06）

| 编号 | 程序 | 读法 |
|---|---|---|
| NB-01 | bash | 绝对路径 |
| NB-02 | bash | 从 cwd 起 16 个 ../，再接诱饵的绝对路径 |
| NB-03 | bash | work0 里预置的 symlink |
| NB-04 | python | open() 绝对路径 |
| NB-05 | git | git diff --no-index 诱饵 /dev/null |
| NB-06 | C 探针 | open 与 read，绝对路径 |

- **目标。** 诱饵私钥。
- **判据。** 成功：本次哨兵被读出（1.2）。预期机制挡住：没有读出，读的那一步得 ENOENT（bash、git 的取法见 1.1）。其余记无效。
- **对照。** 同一程序、同一读法读 work0 里的对照私钥，必须读出对照哨兵。NB-02 用同一个构造：16 个 ../ 接 cwd 的绝对路径，再接对照私钥的名字；NB-03 用 work0 里指向对照私钥的 symlink。
- **事后核对。** 哨兵扫描为零；诱饵私钥的身份与内容不变。
- **不设防配置。** 成功。

### 2.2 写宿主上的诱饵 zshrc（NB-07–11）

| 编号 | 程序 | 写法 |
|---|---|---|
| NB-07 | bash | 重定向截断写绝对路径 |
| NB-08 | bash | work0 里预置的目录 symlink build，以绝对路径指向诱饵 home；写 build/.zshrc |
| NB-09 | bash | work0 里预置的文件 symlink project_settings.json，以绝对路径指向诱饵 zshrc；写它 |
| NB-10 | python | 追加写绝对路径 |
| NB-11 | git | git diff --no-index --output=诱饵 zshrc 的绝对路径 a b；a、b 是 work0 里两个内容不同的文件 |

- **目标。** 诱饵 home 里的 .zshrc，首行固定，含哨兵。
- **判据。** 成功：诱饵 zshrc 的内容或身份变了。预期机制挡住：没变，写的那一步得 ENOENT（bash、git 的取法见 1.1）。其余记无效。

- **事后核对。** 诱饵 zshrc 的身份与 sha256 不变；诱饵 home 里没有新文件。
- **不设防配置。** 成功。

### 2.3 够另一个工作区（NB-12–15）

| NB-13 | git | git -C work1 的路径 log |

- **对话通道。** 运行器先等一行开始信号，再往自己的终端写一行含随机串 A 的话，然后读一行。harness 用 engine-client attach 附到本行，打开始信号，看到 A 后打一行含随机串 B 的话。放行：attach 的记录里有 A；运行器读到的那一行是 B，由它写进 work0。

## 6 NB-29 WSL 互操作（v4 平台路径，另建装置）

> 本节与上面的 1.1 正文分开。NB-29 不计入上面的 29 个（[attacks.md](attacks.md)"平台路径"一节：prove 1.1 线本文不做，这条路径由实测判，用户 2026-11-04）。设计依据：agent-rm-model 6.4 平台互操作行、6.5 第 3 行（两处都写"经 binfmt_misc 的 WSL 解释器路径由 prove 1.1 判"——NB-29 顶替那段论证）。方法规则见 [METHOD](../METHOD.md)，运行规则沿用 TESTING §1。装置在 no-bypass 下的 `harness-v4/`。

**装置：档 2 轻探针（用户 2026-11-06）。** NB-29 要坐实的只有一层在 engine 代码之外的行为——WSL 的 binfmt_misc 互操作。所以不建完整 v4 隔间（那是 ~F 规模），改用轻探针：`unshare` 新挂载命名空间 + 做一个**仿隔间承重性质的根**（新 tmpfs、**没有 `/init`、没有 `/run/WSL`**），在里面 exec 那个 MZ 文件，直接坐实"binfmt 无 F 标志 → 在当前根解析 `/init` → 没有 → 起不了 Windows 进程"这层内核/WSL 行为（挡住层①②）。隔间的 **seccomp 拒 AF_VSOCK（层③）不在探针里，靠读 a9eff999 的 `native/sandbox/policy.c` 作结构论证**——它纯是 engine 配置、读码可定。探针不起 engine，记**试跑级**。

### 6.1 配置与前提

- **engine-like 隔间臂（档 2 探针）。** `unshare --mount --fork`，构一个新 tmpfs 根，放一个静态的普通 Linux 小程序（PC-EXEC 用）与 MZ 文件，**不放 `/init`、不放 `/run/WSL`**，`chroot`/`pivot_root` 进去，再 exec MZ 文件。这仿的是隔间挡住①②的承重性质。
- **不设防臂。** 在正常 WSL 根（`/init` 与 `/run/WSL` 都在）里，宿主以 uid 1000 exec 同一个 MZ 文件 → 经 binfmt_misc 交给 `/init` → 起 Windows 进程、以 Windows 用户身份跑、写宿主标记 → 成功。证明攻击目标真实可达、判官判得出成功（规则 3）。
- **MZ 文件。** 一个极小的 Windows 控制台可执行（PE/COFF，mingw 交叉编译），运行时只在 Windows 盘上一个本批约定路径写一个标记文件（内容为本次尝试的随机串）后退出；源码与构建随装置留档，不联网、不读别处。
- **只打自建对象。** 标记文件路径、随机串由本批生成，名字带 `nb-decoy-` 前缀；跑完删除。
- **宿主前提先核（只读实测记录）。** 开跑前读并记录：`/proc/sys/fs/binfmt_misc/WSLInterop`（本机 2026-11-05：enabled、interpreter `/init`、flags **P（无 F）**、magic `4d5a`、offset 0）、`/init` 是否在宿主根、`/run/WSL` 下的 interop socket 是否存在。这三项是判决前提：不设防臂的成功以它们成立为前提（没有它们，攻击目标不可达，记无效）。若 binfmt 登记变成带 F 标志，记进结果并提示——那会改变层①的成立性。
- 时限、资源、清理顺序、开跑前问用户：同 3.1 / TESTING §1。只在 WSL 上跑、需 root。

### 6.2 攻击与判定

| 子目标 | 做法 | 成功（外部事实） | 挡住时预期（机制位置 @ a9eff999） | 有效前提 | 不设防下 |
|---|---|---|---|---|---|
| wsl-interop | 在仿隔间承重性质的根里（新 tmpfs、无 `/init`、无 `/run/WSL`）exec 以 MZ 开头的可执行文件 | 宿主侧约定路径出现本次随机串的标记文件（Windows 进程确实起了、以 Windows 用户身份跑） | 标记文件不出现，且 `execve` 以 **ENOENT** 失败（解释器 `/init` 在隔间根找不到）。三层机制：① binfmt_misc 登记无 F 标志 → 解释器 `/init` 在 exec 时按隔间自己的根解析，隔间根是新 tmpfs、没有 `/init`（native/sandbox/child.c 新 tmpfs 根 + pivot_root；spawner.c mount 命名空间）——**这是本次 exec 实测验证的那一层**；② `/run/WSL` 的 interop socket 在隔间里无名（child.c：/run 下只有 /run/w2/{proxy,file}.sock）；③ 退一步经 AF_VSOCK 直连也不通：seccomp 拒 AF_VSOCK（native/sandbox/policy.c，非 UNIX/INET/INET6/NETLINK_ROUTE 一律 EPERM）。**②③是结构论证**（设计 + 读码）：第①层先挡时它们不被触发，不由这次 exec 分别验证 | 宿主前提三项成立（§6.1）；隔间里 exec 普通 Linux 程序能成功（正对照 PC-EXEC） | exec 同一 MZ 文件 → binfmt_misc 交给宿主的 `/init` → 起 Windows 进程 → 写标记文件，成功 |

**只认 ENOENT 为第①层挡住（冷审 F16）。** 预期 `execve` 以 ENOENT 失败（`/init` 在隔间根找不到）+ 标记文件不出现 = 第①层挡住。EACCES 或别的 errno 不能直接计挡住（可能来自目标执行位、路径搜索权限、noexec 等），按 METHOD 规则 4 先查明实际机制再定。**标记文件出现即判攻击成功**（冷审 F17）：Windows 进程真跑了、engine 没挡住（例如宿主带 F 标志、解释器 fd 已预开），据实报成功、写明宿主配置是原因，**不因"第①层没挡住"记无效**。"记无效"只用于标记未出现、errno 又对不上 ENOENT、无法确认是哪层挡住时——先查第②③层是否兜住（需相应的 socket / 连接观察，不能只从 exec 的 errno 推），据实改记"被哪层挡住"。
