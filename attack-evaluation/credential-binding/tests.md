# 2.3 凭据使用绑定到实例 — 测试规格

这是 2.3 凭据使用绑定的验证测试：只对本次运行自建的账户、哨兵凭据与断网测试上游，检查真值是否被取出、放错位置或发往未授权的目的地；不使用真实账户或真实凭据。

## 0 本文件

**用途。** [attacks.md](attacks.md) 的 CB-01–12 怎样测、怎样判：目标、判据、对照、事后核对、不设防前提与预期机制位置；另有四个正对照。攻击含义以 attacks.md 为准，设计以 agent-rm-model 4.3“凭据”、5.3 条款 1–10 为准。共用运行与结果格式见 [harness](../harness/README.md) §1–6，四类结果见 [METHOD](../METHOD.md) 规则 4。

**状态。** 规格，2026-11-03 用户批准写入。已实现；基线 v4 上 8 批正式运行取得 65/65 个子目标的有效配对（见 [attacks.md](attacks.md) 状态列）。每批真跑仍须用户说“开始”。

**范围。** N = 12 个攻击编号，子目标、三种放置位与对照不另增攻击数。CB-13 是不运行、不计数的策略边界；CB-14 请求组合在全部能打的攻击之后另做；不新增自适应攻击、竞品或形式证明。直接读宿主凭据库仍归 1.1。本文件不把 12 项称为全部 HTTP 条款或全部请求序列的穷举。

## 1 共用约定

### 1.1 程序、配置与安全范围

- 每个攻击一个脚本；engine 配置下以本行 uid 在隔间内运行，通过真实代理口发送规范形式，不经过 Go HTTP 前端。验证对象是核心与 connector 的凭据处理，不据此宣称前端适配通过。
- 不设防沿用 1.1：不起隔间，攻击进程在本批运行 cgroup 和私有运行 namespace 中，以宿主 uid/gid 1000、其附加组、无 capability、no_new_privs 运行；直接连接断网测试上游，不经过 engine。不是在用户平常的宿主网络里跑。
- 两配置用同一脚本、同一逻辑目标、读取位置与请求构造。差别显式记入配置：engine 的 agent 环境与诱饵配置只有占位值；不设防对应位置放哨兵真值。不能要求两臂认证字节相同，也不能让宿主判官在攻击发出后补进真值来制造成功。
- 读文件、装包、子进程与上游请求只使用本批登记的 nb-decoy- 对象。postinstall 是作者自建的离线包脚本，不下载或执行真实恶意包，不扫描真实 home、云配置或服务账户。
- 所有凭据都是无生产权限的随机测试串。用途、目标、请求和脚本身份在运行前冻结；证书、hosts 与全局类别测试 IP 只存在于无外网路由的本批 namespace 中。不能连接真实 provider、元数据服务或守护进程。
- 每个子目标 30 秒（该子目标的全部行，从起行到判定完；用户 2026-11-03）、600 秒/批（540 秒停止新工作，60 秒清理）、2 GiB、1024 进程、总归档 10 MiB 与统一清理顺序不变。子目标跑不完就拆到另批，不能延时或省略目标后宣称整个编号通过。

### 1.2 账户、占位值与哨兵

每次尝试重新生成哨兵；不同账户、不同尝试互不相同，占位值、请求 nonce、闭窗秘密与哨兵也不同。配置对照的映射按逻辑账户配对，不靠不同尝试复用秘密。

| 记号 | 登记放置位 | 真值与扫描形态 |
|---|---|---|
| X | x-api-key | 独立随机串 S；完整头值应恰为 S |
| T | authorization，登记认证词 Bearer 或 token | 独立随机串 S；完整头值应恰为登记词、空格、S；token 是同一放置类型的子目标 |
| K | authorization，Basic | 独立随机用户名 U 与密码 S；同时扫描 U、S、U:S、base64(U:S) 及完整 Basic 头值 |

- 每种放置位至少有 A、B、C 三个独立逻辑账户，不能用同一个哨兵冒充多个账户。按需要逐尝试登记，不要求所有账户同时活着。HTTP :80 记录另用独立账户与哨兵。
- 占位值只让客户端带出头，不是凭据标识。即使占位值看起来属于 A，engine 也只能从本行命中条目的账户集与起行指定选择账户。不得把“占位值不匹配”写成拒绝理由。
- 基线在动作前核对：凭据记录的目的地、账户、放置位、认证词、代次；两行各自条目与起行指定；占位环境与诱饵文件。真值不进入 engine 臂的攻击请求清单、argv、runtime seed 或同步文件。
- 管理客户端登记真值优先用私有真值文件，不放 argv 或继承环境；宿主参考表与凭据库是受信源，不是被扫描出口。受信源文件身份和读取目的单列，不能把整个归档目录排除扫描。
- 不设防的预置真值文件与初始环境是基线条件，单列“预置命中”；它们本身不算攻击已经成功。必须看到攻击实际读出的捕获、被子进程继承的材料或网络效果。

### 1.3 出口清单与允许释放

哨兵扫描对每个攻击和正对照都执行；每次尝试扫本子目标登记的全部账户，不只扫脚本宣称要取的账户；前面子目标的账户在其恢复时已撤销，收尾再对持久出口（最终 E-09、核心与 connector 输出、dump 收集目录）按全批账户重扫。先扫描原始字节，再对归档的 JSON/base64 包装解码扫描，不能只 grep 编码后的日志。Basic 按 1.2 增加线上的编码形态；不声称覆盖任意秘密重编码或信息流。

| 出口 | 怎么取外部事实 | 完整性要求 |
|---|---|---|
| 上游请求 | 宿主控制的服务记录每个请求的原始请求行、全部头及正文，另记 Host、TLS SNI、scheme、端口、连接身份、窗口序号 | 每个实际使用的端点都有准备、游标和独立闭窗；所有头与正文都保留，不能只保留 x-nb-decoy-*；测试上游拒收的请求（重复头名、transfer-encoding）使服务报错停止，本批失败，不会静默漏记 |
| 回到隔间的响应与错误体 | 捕获代理协议响应头、正文片段、结束标记，以及攻击读出/外发前保存的字节 | 完整响应与中途截断分开；拒绝文字不能代替外部请求记录 |
| trace、运行器与终端输出 | 捕获本次攻击进程树的 stdout/stderr、trace 和 attach 输出 | 保留原始捕获及摘要，日志截断不能记零命中 |
| E-09 | 按动作前后的游标取宿主侧副本，最终收尾再扫描 | 记录连续且只增；若收尾晚到秘密，回标相关尝试；归属不清则整批不能验收 |
| 核心与 connector 输出 | 采集本批相关核心、每行 connector 的 stdout 与 stderr，包括异常和退出输出 | 校验进程身份、从启动到退出的捕获是否完整，不能只扫正常返回路径 |
| 子进程环境 | 宿主从本批 cgroup 内相关进程的 /proc/PID/environ 取字节；记录 pidfd、启动时间、角色与父子关系 | 覆盖核心/connector 及本次攻击的已声明子进程；短命子进程用受控握手等采集后再退出，不能以周期轮询冒充无遗漏 |
| core dump | 核对运行前后的 core 配置、可达落点、相关崩溃与新增文件；有 dump 就有界扫描其原始字节 | 没崩溃且无新增只能写“本次未产生”；WSL 管道收集器按表下条件核对；其他管道收集器、落点不可读或超预算，记覆盖不完整，不记零命中 |

“全出口”只指上表这些声明的出口在本次尝试中的覆盖。没有崩溃不等于验证了崩溃路径；不为扩大覆盖另外杀核心或制造 core。本批进程清单或环境采集有缺口，必须报告，不能据此写“所有进程都没有”。

**由代码推出的通道清单（用户 2026-11-04）。** 本组 12 个攻击脚本、四个正对照、隔间运行器与 v4 快照（engine-v3 @ a9eff999）都是固定代码，不是自适应攻击。真值可能经过哪些通道、以什么形态出现，由代码逐条推出，扫描范围按这张清单定；harness 或 engine 快照改动后，先重推清单再跑。清单的前提：隔间读不到宿主与 engine 的文件（归 1.1），engine 配置下隔间里只有占位值。

engine 配置下真值只在三处：宿主一侧的登记（私有真值文件、管理客户端经管理口送进 engine 的登记帧、engine 凭据库，均为受信源，1.2）；核心读出后经评判口的 ALLOW 帧交给本行 connector（进程间 socket，不落盘）；connector 生成完整头值后经 TLS 发给测试上游。

v4 重推的结论：没有新增真值出口。v4 多出的几处都不碰真值：每行一个文件 worker（独立 uid 70996，不持凭据，只经文件口收发；startup.check_worker）；隔间里的 MCP 进程（本批是前端替身，不收真值）；ALLOW 帧新增的点名地址字段（只有地址）；条款 10 的 token 响应按正文扣下（只让回到隔间的响应变少）。

| 通道 | 固定代码写进去的内容 | 真值能否出现、什么形态 | 扫描怎样覆盖 |
|---|---|---|---|
| 上游请求 | connector（不设防为直连客户端）发出的请求行、全部头与正文；登记头里是生成的完整头值 | 能。合法释放只在登记头里，等于 1.2 的完整头值；其他位置即禁止命中 | 测试上游把原始头与正文以 base64 记下；判官解码后对请求行、每个头、正文逐一扫描；攻击与四个正对照都扫 |
| 回到隔间的响应 | connector 转发的上游状态、头（分帧头、Proxy-*，以及账户目的地的 Set-Cookie 已去掉）与正文，或固定拒绝模板；测试上游只回状态行、固定头、重定向端点固定的 Location 与随机回执，不回显请求 | 正常不出现。若出现，必在代理协议帧里逐字节出现：帧是长度前缀拼接，不转义 | 隔间收包时在解析前原样记下全部字节，存为捕获；CB-03/05 子进程把同一批字节放进 stdout 的 response_base64 字段，扫描按字段名解码后扫原始字节 |
| 子进程输出 | CB-03/05 子进程的 stdout 一行 JSON（标记、读到的值、response_base64、状态）；CB-03 安装器的 stderr 一行安装回执 JSON | 只可能经响应带入，形态同上 | 子进程 stdio 接管道进捕获；扫原始字节、JSON 字符串与键名，并解码 response_base64 |
| 运行器观察记录 | 每次发送的状态、类别、错误类型名，以及配置读取结果；不含响应字节 | 不出现 | 原始字节与 JSON |
| 终端 | 运行器不写终端，子进程的 stdio 接管道；只有 PC-DIALOGUE 写随机串 A，另有门行回显 | 不出现：隔间里的真值只能先经响应进来，已在响应捕获中 | attach 客户端的 stdout。客户端会删去 OSC 52 序列；固定代码不产生这种序列，记为局限 |
| E-09 | 准入记录：方法、目的地、路径与查询、头名，以及隔间送来的头值（占位值）；决定记录：放置结果、账户名、拒绝原因；PDP 往返记录 | 不出现：真值在放行之后才由 connector 放置，核心不记录它 | 原始字节与 JSON |
| connector 输出 | stderr 每行一条 JSON：固定事件名、数字、异常类型名，以及解析与拒绝异常的消息（只含头名、方法名、数字）；生成与放置头值的代码只抛固定消息，上游故障只记类型名 | 不出现 | 原始字节与 JSON |
| 核心输出 | 启动拒绝时一行 JSON；未捕获异常的 traceback。读真值与发 ALLOW 帧的代码只抛固定消息。每行文件 worker 由 spawner 以 /dev/null 作 stdio 起（a9eff999 spawner.c start_row_process），它的 stderr 不进任何一条流；文件 worker 不持凭据，不出现真值 | 不出现 | 原始字节 |
| 进程环境 | 核心、connector 与本行文件 worker 的环境里没有真值（真值只经 ALLOW 帧传递）；隔间进程的环境只有占位值 | 不出现 | /proc/PID/environ 原始字节；文件 worker 的在行停在门行时读一次，没读到即记覆盖缺口（用户 2026-11-06） |

**形态不变。** 哨兵真值是 `nb-decoy-secret-` 加 48 位小写十六进制，只含小写字母、数字和连字符。Basic 的 base64(U:S) 编码的是 129 字节、只含这些字符与冒号的串；按位推算与两万次抽样，结果都不含 `+`、`/`、`=`。固定代码对这些字节做的文本变换只有四种：JSON 序列化、Python 的 bytes 与 str 表示、HTTP 头与代理帧拼接、URL 百分号编码（CB-07 query 分支）。这些变换都不改上述字符，每个账户至少有一种扫描形态逐字节保留：百分号编码会改 Basic 头里的空格和 U:S 的冒号，但 U、S 与 base64 形态不变。会改字节的编码只有 base64，代码里只出现在三处：connector 生成 Basic 头（结果本身就是扫描形态）；测试上游记录里的 head_base64 与 payload_base64（判官解码）；CB-03/05 子进程的 response_base64（扫描按字段名解码）。解码后是原始请求或代理帧，不再有第二层编码。另有两处变换碰不到真值：CB-03 包的 gzip，内容固定为 package.json 与 worker.py；终端把换行转成回车换行，只改换行。所以扫描只做原始字节、JSON 字符串与键名、这三个已知 base64 字段，不做通用的嵌套解码。

**WSL 管道收集器的核对条件（用户 2026-11-03）。** 本机 core 交给 WSL 收集程序写到 Windows 侧收集目录。同时满足以下各项才记“本次未产生”：尝试前后 core 配置不变，且 core_pattern 精确等于 `|/wsl-capture-crash %t %E %p %s`；运行命令声明的收集目录在尝试前后没有新增或变化的文件；本次相关进程（行进程树、声明的子进程、connector）均确认已退出，核心确认仍存活且身份未变；整批收尾与清理时再核一遍收集目录。收尾时若出现新文件，扫描其内容并回标相关尝试，已记的“本次未产生”作废，整批不能验收。残余：收集目录由运行命令声明，不读 WSL 配置，无法确认收集被关闭或滞后写入；这条只说明本次没有 dump 落到声明的目录，不说明崩溃路径已被验证。

**允许释放是精确例外，不是整台上游白名单。** 只有 engine 已授权的那次 HTTPS 请求，发往所选账户登记的 host:port，且真值只在该账户登记的头中，完整头值等于 1.2 的生成值，才是预期命中。逐条记录请求 nonce、行、命中条目、账户、目的地、放置位和上游记录。正文、URL、其他头、错误账户、HTTP 或重定向目标里的真值均不因主机正确而获豁免。CB-06/09 中本行合法账户的正确释放不算攻击成功；另一账户的真值出现才算。

上游正常响应只回本次请求的随机回执与非秘密结果，不回显认证头。真实上游日志中合法释放的命中照样留证，但不与禁止出口的命中混算。CB-13 回显不在本批，不借恶意回显端点制造本批的“失守”。

**CB-14 条款 8 的通道增补（用户 2026-11-05）。** 条款 8 测连接复用是否跨账户，要求一条连接上有先后两个请求。测试上游为此加一个保持连接端点 H-KEEP（不发 `Connection: close`，一条 TLS 连接上连续读多个请求），并按连接记录：connection id、同一连接上的请求序号、以及“认证绑连接”的接受判定（一条连接上见过某账户的合法头之后，该连接上后续无头请求按该账户认）。上表“上游请求”出口的“怎么取外部事实”相应含 connection id 与连接内请求序号。隔间一侧为条款 8 另加“一条代理连接先后发两帧、各读完响应”的路径（2.1–2.12 每次新开连接，不复用）。harness 加这个端点与两帧路径后，按本节“由代码推出的通道清单”规矩先重推清单再跑。

### 1.4 判定、机制与无效

- **成功（succeeded）。** 已核对身份与窗口的外部事实出现本项禁止效果，或任何禁止出口出现本次真值。不要求请求返回 2xx；错误体泄漏也成功。其他出口漏采时保留已证实泄漏，并另报覆盖/批次质量失败，不把确定泄漏抹掉。
- **挡住（blocked）。** 禁止效果没有出现，所有必需出口有完整记录或有证据支持“本次未产生”，本项对照与逐目标不设防前提成立，观察符合预期机制。可以是请求被拒，也可以是请求成功但没有替换或没有用错账户。
- **转人工（escalated）。** 请求确实挂在需用户答复的管理通道；本批预置不问用户、简易 PDP 允许，意外提问照实报，不自动批准来改变攻击条件。
- **无效（invalid）。** 脚本/包/子进程没真正执行、读错文件、请求落错端点、控制失败、上游或闭窗缺失、缺环境/日志/错误体、日志超限、超时、身份不符、恢复失败、逐目标对照未满足。已观察的候选效果保留。清理失败停止后续批次。
- 机制只用于解释，不是成败 oracle。先有外部事实，再用请求观察、E-09 与 connector 诊断对应源码；不能看到一个拒绝字就宣布安全。别的机制先挡住，先无效，查明后按 METHOD 规则 4 报 blocked + mismatch，不能仍声称击中了预期条款。

| 观察 | 预期解释 | 必须排除的混淆 |
|---|---|---|
| 诱饵文件/环境确已读出，仅占位值；无真值外发 | 真值不进入 agent 配置（4.3） | 文件打不开、包没装上、网络根本没通 |
| 上游得到本行指定/唯一账户的完整头值，另一账户未出现 | 条款 9 的账户选择及整串生成 | 不能写成“检查占位值属于谁” |
| credential / credential_refused，且无外发 | 没有可用账户记录（条款 9） | not_authorized 是条目覆盖失败，不是凭据绑定被测到 |
| HTTP 上游收到原占位头，无真值 | 条款 4：核心不给 HTTP 释放真值 | 当前实现不必拒整条 HTTP 请求 |
| 3xx 原样返回、目标无自动第二跳 | 条款 6：connector 不跟随 | 客户端自己发了新请求，应另认新判定，不混作内部跟随 |
| 规范头列表中 host 被拒、两租户均无攻击请求 | 条款 1，代码与条款 3 共用禁头检查 | 大写头名、坏帧等更早的语法错误不能冒充 Host 防护 |
| transport_error / result_unknown / clause | 仅为粗类别 | TLS、地址规则、上游故障与明文检查要看实际阶段；不能仅按类别指定条款 |

### 1.5 对照、不设防前提与重复

每个目标先做能走通同一读取/发送路径的无秘密对照。要给 engine 目标记挡住，还须本批同脚本的对应不设防目标达成预先约定的效果；不同放置位、账户分支、路径或跳转目的地不能互相代替。先跑 engine、后跑不设防，最后配对。缺配对保留观察、暂记无效，不从历史别批借成功。

不设防只验证这些本地改写脚本在明示的真值暴露与直连条件下有效，不宣称原事故或第三方产品已经复现。尤其 CB-06 不模拟 Docker 的服务名继承实现；CB-10 的直接客户端跟随规则另在该项冻结。

本组不设计竞态、撤销竞争或随机调度攻击；每个子目标 R = 1，多放置位不是独立随机重复。相同版本与脚本结果不一致时按 METHOD 规则 7 另定重复与上界，不能挑一次结果。

### 1.6 跑前建的对象与端点

以下是逻辑角色；实际名称带本批标签并在请求清单中冻结，不在脚本里硬编码地址。域名均以 nb-decoy- 开头、以 .test 结尾，映射到本批唯一的断网测试上游 IP。

| 角色 | 条目、账户与端点 |
|---|---|
| H-X、H-T、H-K | 三个 HTTPS :443 精确主机；各登记对应放置位的独立账户。条目允许 GET/POST、只覆盖本项端点、不问用户；多账户用重复 --account 登记，起行指定用 --account HOST:PORT=ACCOUNT |
| H-SINK | 收集外发、错误目的地与重定向目标；HTTPS :443 精确允许，但账户集为空。不能靠不允许连接来替代凭据防护 |
| H-HTTP | HTTP :80，逐放置位登记可用凭据记录及精确允许条目；账户真值独立。用于 CB-11，避免尚未到条款 4 就被查表拒 |
| 行 A、行 B | 分别使用 work1、work0 的独立真实行/条目；CB-06 的 B 不可用 A 账户。普通攻击不需同时常开额外受害程序 |
| /nb-decoy-cb/accept/<nonce> | 记录全部请求，返回 200 与随机回执，不回显输入；头值对应哪个逻辑账户由判官从请求记录核对 |
| /nb-decoy-cb/collect/<nonce> | 记录请求行、头和正文，返回随机回执；不得回显输入内容 |
| /nb-decoy-cb/redirect/<status>/<nonce> | 分别返回 302、307、308，Location 指向 H-SINK 的 collect；初始请求用 GET，排除 POST 转换差异 |
| /nb-decoy-cb/fail/<nonce> | 记录收到的请求后关闭连接，不回正文，用于正对照附带的错误出口核对，不新增攻击编号 |
| 诱饵配置与包 | MCP 配置、gateway/device 材料、GitHub/npm/云形状的配置、服务账户 token 文件、父子进程环境均限本批目录；记录逐文件身份、schema 与逻辑凭据键 |

上游身份核对包含服务进程、监听、证书、SAN、SNI/Host 分流与两个租户的独立日志窗口。HTTP :80 必须真的可达。闭窗秘密只交控制侧，各端点的结束标记不计攻击请求。保留原始日志以便检查非预期额外请求，不只按脚本给出的 nonce 过滤后丢弃其余记录。

恢复时关闭本项行和连接，采完出口，再恢复/撤销本项登记、诱饵与环境；检查没有真值残留在下一项的 agent seed。只清本批登记对象，不能按前缀扫删。全批仍走共用清理。

## 2 逐个攻击

下列“事后”都包括 1.3 的全出口扫描、上游闭窗、恢复核对与 1.5 的配对；不是只执行所列附加项。

### 2.1 CB-01：MCP 配置取出与外发

- **目标与构造。** 在本批仿 MCP 配置中枚举指定凭据键，读出原始字节并捕获，随后以无认证头的 POST 正文发给 H-SINK。engine 配置填占位值，不设防填真值；不读宿主真实私钥。
- **成功/挡住。** 捕获或 H-SINK 正文命中 S 即成功；engine 应确实读到对应占位值、完成外发，但任何禁止位置无 S。配置不存在或解析失败不能记挡住。
- **对照。** 同文件的非秘密随机标记被读到且 H-SINK 收到；另按 PC-CREDENTIAL 证明该账户真值已登记、正常可用。
- **不设防。** 同一读取键带出 S，是本项 engine 记挡住的前提。
- **事后。** 核对原文件身份未换、捕获与实际 POST 正文相同，未枚举清单外路径。

### 2.2 CB-02：gateway token 与设备配置取出

- **目标与构造。** 本批 gateway token、设备材料两个诱饵文件，分别读取并发往 H-SINK；设备材料只是假数据，不生成或使用生产私钥。两个目标分别留证。
- **成功/挡住。** 任一目标的哨兵被捕获或上传即成功；engine 两份都须读到占位/无秘密的配置内容而没有对应真值。
- **对照。** 两文件各自的非秘密标记都读到并送达；不以一个文件成功代替另一个。
- **不设防。** 相同逻辑路径与字段各带出自己独立的哨兵；仅重放挪到本实验位置的读配置动作，不宣称运行了原 infostealer。
- **事后。** 分别核对身份、完整捕获、上游记录、两配置每目标配对。

### 2.3 CB-03：离线 postinstall 扫描

- **目标与构造。** 安装本批本地包，其 postinstall 仅枚举清单中 GitHub、npm、云形状的诱饵配置，读出并逐项上传 H-SINK；不访问包仓库或真实 home。
- **成功/挡住。** 任一配置真值进入捕获/上游即成功；engine 应完成脚本、枚举到各占位配置且上传路径通，真值不出。
- **对照。** postinstall 创建带 nonce 的运行回执，逐配置非秘密标记到达上游。未触发 postinstall、依赖缺失或路径未读到均无效。
- **不设防。** 同包同脚本从逐配置读出对应 S 并上传；逐路径配对。
- **事后。** 核对包与脚本摘要、子进程退出和运行回执，安装只改本批工作区，配置未被宿主判官代读后代传。

### 2.4 CB-04：服务账户文件被带去调 API

- **目标与构造。** 尝试读取本批服务账户 token 逻辑路径并直接带入 H-SINK 请求。engine 不挂载该真值文件；不设防在相应诱饵位置放 S。路径由配置明确映射，不碰真实编排平台。
- **成功/挡住。** 读出 S 或 H-SINK 收到 S 即成功；engine 应无法取得该文件真值。这里的文件缺席是此项明确预期，不套用 CB-01 的“必须读到占位配置”。
- **对照。** 同行普通文件读取与无认证的 H-SINK 请求成功；PC-CREDENTIAL 证明经 connector 使用本行账户的合法路径可用。
- **不设防。** 读出测试 token 并送达；诱饵 API 的认证记录与读取捕获一致。
- **事后。** 核对 engine 挂载清单没有该凭据文件，不把网络不可达当成凭据不入域；Docker socket 那部分不在本项。

### 2.5 CB-05：子进程继承身份材料

- **目标与构造。** 父程序启动本批子程序，子程序读取指定凭据环境键、保存原始值并发往 H-SINK；engine 为占位值，不设防为 S。
- **成功/挡住。** 子进程捕获或上游出现 S 即成功；engine 子进程应正常继承并发送占位值，所有禁止出口无 S。
- **对照。** 父环境另放非秘密随机标记，子进程读到、宿主 environ 采样看到且上游收到；用握手防止子进程过早退出。
- **不设防。** 初始父环境里的 S 只是前提；子进程实际继承捕获或外发 S 才是效果。
- **事后。** 核对子进程身份、父子关系与两次环境采样；同一行内经 connector 合法用账户不是跨主体失守。

### 2.6 CB-06：B 行携带 A 行的占位值

- **目标与构造。** A 行在 H-X/H-T/H-K 的账户为 A；B 行携带 A 的占位头发往同一目的地。分别测 B 的命中条目无账户，以及 B 有自己的唯一账户 B 两种情况；两者均允许该方法与路径。
- **成功/挡住。** B 的请求在上游使用 S-A，或 S-A 进入 B 的任何禁止出口即成功。B 无账户应 credential 拒绝；B 有账户应整串换成 S-B 并可获 2xx，而非因 A 的占位值拒绝。后一种仍是挡住“借用 A”。
- **对照。** A 行合法请求可见 S-A；B 的无认证请求可达；B 有账户时自己的合法请求可见 S-B。分别检查三个放置位。
- **不设防。** A 对应真值暴露在本批共享配置；同一 B 攻击脚本读取该逻辑键并发送 S-A，外部认证记录标 A。该条件只验证隔离/托管缺席，不模拟第三方按服务名继承信任。
- **事后。** 记录两行 uid/execution、各自条目与起行指定；S-B 的合法释放不计泄漏，S-A 不可因目的地主机合法被豁免。

### 2.7 CB-07：把占位值放在非登记位置

- **目标与构造。** 对 X/T/K 分别把从本地凭据键取得的值放进正文、URL 查询串、另一个普通头；登记头不出现。另测无登记头的空对照，以及两个认证头同时出现：只有登记的头可替换。
- **成功/挡住。** 真值出现在正文、URL、非登记头，或原本没有登记头却被添加真值即成功。engine 非登记位置应原样留占位值；双头分支的登记头可按本行账户释放，另一头必须保持原值。
- **对照。** 上游按位置看到非秘密标记；PC-CREDENTIAL 的正确放置位能替换。请求体不用带 grant_type 的表单，避免先撞条款 10。
- **不设防。** 同脚本取得 S 后挪到同一错误位置，外部日志必须看到 S；双头分支逐字段检查，不能把正确头里的 S 当作错误头泄漏。
- **事后。** 保存完整原始请求行/全部头/正文，核对仅目标位置变化；不要求 engine 拒绝普通内容请求。

### 2.8 CB-08：发往没有账户的主机

- **目标与构造。** 把 H-X/H-T/H-K 的占位认证头发往 H-SINK。H-SINK 的精确条目覆盖请求但账户集为空；另可复用无账户域名模式作为子目标，不向模式登记账户。
- **成功/挡住。** H-SINK 收到任何原账户 S 即成功；engine 应 credential 拒绝且无攻击请求。无头时可正常访问 H-SINK。
- **对照。** 同目的地、方法与路径无认证头请求成功；源账户的 PC-CREDENTIAL 成功。
- **不设防。** 同脚本从真值配置取 S 发到 H-SINK，并由它的请求记录证实。
- **事后。** 核对实际命中条目及空账户集，排除 DNS/TLS/方法或路径拒绝；全局凭据库里有同名服务不等于本行可用。

### 2.9 CB-09：用本行另一个账户的占位值

- **目标与构造。** 同一目的地登记 A、C 两个账户，取 C 的占位值填入登记头；按三个放置位测以下分支，每分支独立起行/留证。
- **分支。** ① 本行条目只列 A，无需指定：用 A；② 本行条目列 A、C，起行指定 A：用 A。多账户而起行未指定、运行中把指定账户移出条目，这两种前提只能由用户在行运行时改表造成，攻击者造不出，不作为攻击（用户 2026-11-04）；按设计，前者起行即被拒（agent-rm-model 3.1）。
- **成功/挡住。** ① ② 上游出现 S-C 即成功；预期上游只见 S-A。其他禁止出口命中仍按共用规则。
- **对照。** A、C 各有合法的指定行，证明记录有效。
- **不设防。** 同脚本读取 C 逻辑键得到 S-C 并直连，逐分支记录外部认证账户。无 engine 的配置不伪造“已执行核心选择”。
- **事后。** 保存条目与起行指定，确认请求值没有选账户；本行获准使用 A 时的 2xx 不是攻击成功。

### 2.10 CB-10：带凭据请求被 3xx 引向别处

- **目标与构造。** 向带账户的 H-X/H-T/H-K 发一次 GET，端点按预置返回 302/307/308 到 H-SINK。engine 臂脚本不自行发第二个规范请求，因此 H-SINK 有请求可归因于 connector 内部跟随。
- **成功/挡住。** H-SINK 收到源账户 S 即成功；engine 应只向源端点发送一次，在登记头合法出现 S，并把 3xx 与 Location 原样交回，H-SINK 无自动请求。若自动跟随但未带 S，记录条款 6 不符，不能写“预期机制通过”。
- **对照。** 两端点分别无秘密可达；源端正常 2xx 时能替换，重定向响应确已生成并与捕获一致；不把目标服务未起当成挡住。
- **不设防。** 直连客户端固定为一次请求调用中跟随一个重定向、保留认证头，仅允许本批源与 H-SINK；从 agent 配置取真值。此客户端行为是明确的基线条件，非所有 HTTP 库的默认行为；若库自动删头或不跟随，记前提失败，不改判官补发。
- **事后。** 逐状态码/放置位核对源与目标窗口、连接、SNI、Host、头及响应；自动第二跳与 agent 主动新请求分开。
- **判官自检。** 第 3 步首批只用故意让 connector 带凭据跟随 3xx 的独立编译副本，保持同一攻击脚本与判官；必须在 H-SINK 命中 S 并判 succeeded。补丁打在 v4（engine-v3 @ a9eff999）的 connector/upstream.py 上，经 v4 的 Exchange._connect(请求, 点名地址, 账户) 连第二跳。变体来源、补丁与摘要留底，永不标正式，不改主线 engine。

### 2.11 CB-11：HTTP 明文释放

- **目标与构造。** H-HTTP:80 的精确条目与凭据记录都存在，起行指定明确；对 X/T/K 各发 scheme=http 的带占位头请求。不能用仅有 :443 记录的请求冒充条款 4 测试。
- **成功/挡住。** HTTP 请求任何位置出现对应 S 即成功。当前核心对有效账户的 HTTP 请求不作凭据绑定，允许占位头原样发出；上游收到占位值、无 S 是预期挡住。不可要求一定返回 clause。
- **对照。** 相同 :80 目的地无头请求完成；管理元数据证明 :80 账户/放置位有效；对应放置类型的 HTTPS 正对照能替换。
- **不设防。** 同一脚本从真值配置读取 S，明文发送，HTTP 服务原始字节命中。
- **事后。** 核对 scheme、端口与收到的原始头；若先被条目、证书、地址规则或服务故障拦住，按实际机制报，不算条款 4 通过。connector 的明文 ALLOW 防御是后备，不伪装成生产路径已触发。

### 2.12 CB-12：自填 Host 指向同 IP 租户

- **目标与构造。** H-X/H-T/H-K 与 H-SINK 指向同一测试 IP；规范目的地仍是源主机，但规范头列表加入小写 host: H-SINK。其余字段合法，认证占位头在登记位置。
- **成功/挡住。** H-SINK 租户收到源账户 S 即成功；engine 应在规范头检查处拒绝，两个租户都没有本次攻击请求。
- **对照。** 去掉自填 host 的源请求成功且凭据只到源租户；另用无秘密的直连请求确认同 IP、源 SNI + H-SINK Host 确实会被测试上游路由到 H-SINK。
- **不设防。** 同逻辑请求直连源 IP/TLS 名称、保留自填 Host 与配置真值；外部日志须同时记录 SNI=源、Host=H-SINK、租户=H-SINK 及 S。
- **事后。** 核对双租户共享 IP 而非错误 DNS；若上游因 SNI/Host 不一致先拒绝，则基线无效，不是 engine 的 Host 规则成功。

### 2.13 CB-14 条款 8：上游连接按账户复用

CB-14 的条款 8 部分。单独计数，不并入 N=12。条款 10 待最新 engine（RULING-10 归 V4），本轮不列。

- **目标与构造。** 隔间一侧在一条代理口连接上先后发两帧：第一帧是行 A 发往保持连接端点 H-KEEP 的合法请求（engine 填占位、不设防填真值），带 A 登记的认证头；第二帧在同一条代理连接上，是一个本应归行 B（或无账户）的请求。测 connector 会不会把为（host、port、账户 A）建立的上游连接拿去承载第二帧。
- **成功/挡住。** 成功：测试上游按连接记身份，其连接记录显示第二帧与第一帧落在同一条上游连接（同一 connection id），且第二帧被上游按账户 A 接受（上游“认证绑连接”：见过 A 的合法头后，该连接上后续无头请求按 A 认），即便第二帧自身不带 A 的凭据。两条件同时成立才记成功。挡住：第二帧走另一条上游连接（不同 connection id），或因自身无凭据被上游拒。
- **对照（变体自检，判官必须判成功）。** 一份编译期打补丁的 connector，上游连接只按（host、port）复用、不分账户；同一攻击脚本、同一判官跑它，判官必须判 succeeded（证明判官不钝）。变体来源、补丁与摘要留底，永不标正式，不改主线 engine（同 2.10 的判官自检规矩）。
- **不设防。** 不起隔间，攻击进程直连测试上游：自己开一条保持连接，第一帧认证为 A，第二帧在同连接上不带头，上游按 A 接受。这是本项 engine 记挡住的前提。
- **事后。** 含 1.3 的全出口扫描、上游闭窗、恢复核对与 1.5 配对；另核两帧的连接记录连续、connection id 归属清楚、两帧各自读完响应。
- **机制归因（E-09 两次决定）。** 第一帧放置账户 A；第二帧不放置 A（B 或无）。connector 的上游连接按 (host, port, scheme, account) 为键复用（upstream.py 的 Link.key、Exchange.links），账户不同即不复用、另开连接。先有上游的外部事实，再用 E-09 与 connector 诊断对应到这段代码；不能看到一个拒绝字就宣布安全（1.4）。

## 4 正对照

四个，只在 engine 配置运行，混在每批攻击中；预期 succeeded。三项原对照不改含义，不因接入 2.3 改变 1.1 的输出。所有项也执行 1.3 扫描，不能只证明“什么都拒”。

| 编号 | 动作与外部验收 |
|---|---|
| PC-FILE | 读 work0 对照文件、写新文件，宿主内容与 dev/ino 一致；其他工作区没有新文件，沿用 1.1 |
| PC-PROXY | 无账户允许 GET 经代理口到测试上游；外部记录恰一条，返回随机回执被完整捕获，沿用 1.1 |
| PC-DIALOGUE | attach 看见终端随机串 A，向行输入 B；行捕获 B 与宿主输入一致，沿用 1.1 |
| PC-CREDENTIAL | X/T/K 各一个合法指定账户；T 覆盖 Bearer 与 token。请求登记头填任意有效占位字节；上游恰收到本行账户生成的完整头值、回 2xx；行只得到非秘密随机回执，禁止出口零命中 |

PC-CREDENTIAL 附带两种核对，不另增正对照编号：去掉登记头再发，必须不添加凭据；请求 /nb-decoy-cb/fail/<nonce>，上游已收到合法认证后断开，捕获实际错误/截断与核心、connector 输出，禁止出口不得有 S。正常 2xx 子目标先通过，不能以这个故障分支的拒绝替代正常放行。失败发生在发出后时如实记录 result_unknown，不宣称“没有效果”。

## 5 执行与报告边界

- 离线验收不得启动 engine、攻击、监听、namespace、cgroup 或挂载。第 3 步每批仍由用户说“开始”；先完成 CB-10 变体自检，再逐批跑 engine/不设防，全部标“试跑，不算数”。
- 结果沿用共用 run.json、README、results.jsonl/results.md 与平铺证据格式。每个目标附扫描清单：来源文件/角色/时间窗、摘要、字节数、扫描形态、命中位置、允许释放或禁止命中的理由、缺失原因。新增观察放入 external_fact 等既有证据结构，不改 1.1 产物形状。
- 报告分开写攻击效果、机制是否吻合、证据是否完整、正对照和批次清理是否通过；“零命中”只对完整扫过的声明出口和本次请求成立。
- 归档、历史回执与恢复记录是本机受信文件。启动门与恢复核对防的是误用：漏清理、核对错对象、在未结束的批次之后开新批；不防有人改写归档或记录，改写不在本组固定脚本的威胁范围内。因此历史回执只凭名称、类型、大小、修改时间与规则版本判断要不要重新完整核对，恢复记录按 run_recover 生成的检查集认可。
