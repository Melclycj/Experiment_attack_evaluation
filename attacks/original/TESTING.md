# 1.1 不可绕过 — 反向测试与 TLC

## 0 本文件

**用途。** 1.1 的两个判官：反向测试判单格事实，TLC 判组合逻辑。这里写它们的义务、判据、组织与运行规则。其中测试义务表、判据与对照的要求、TLC 的界限、反例的处理规则与每个相关转换的去处属于骨架（SPEC §1）。代号见 PLAN §0.1。

用户 2026-10-24 批准：反向测试作单格事实的判官，TLC 检查组合逻辑；TLAPS 暂不做。两者各能证明什么、不能证明什么，以及为什么
要有不是大模型的判官，见 ARGUMENT §4–§6。

## 1 反向测试

**反向测试。** 在沙箱里实际去做一个动作，观察 kernel 的真实反应。判官是 kernel 的实际行为，不是读源码的推断。

- **测试义务（按格的记录取值）：**

  | 记录 | 测什么 | 例 |
  |---|---|---|
  | 路线 | 反向测试：去做，按判据观察被拦下，配正对照。处置为 declared out of scope 或 conditional 的路线不声称被挡住，测试一栏写"不测"加处置；open 的路线照样要测 | 打开宿主上的诱饵文件、写 /runtime、向诱饵进程发信号 |
  | 交付 | 边界测试：权利之内的操作能成，并核对对象身份（fstat 的设备号与 inode、挂载信息）正是交付的那个；越出权利的一侧是路线，另测 | 写 /work 能成，宿主侧看到的是同一个文件 |
  | 私有 | 两个沙箱互看：另一个 execution 碰不到。只作用于本进程自身状态、保守摘要里没有延迟或外部效果的格，写"不测：只碰自己"，这个主张按 [R] 计 | /tmp 下的文件别的沙箱看不见；取自己的 pid 不测 |
  | 汇总·观察、汇总·可用性 | 对象身份测试：核对这个候选效果没有作用到某个具体对象（SPEC §4.1 的优先规则），支持第 4 类的归类；带宽与时延不测（SPEC §5.1） | /proc/self/fd/0 重开得到的确实是宿主 /dev/null |
  | 宿主可观察·已核实、宿主可观察·按可见 | 对象身份测试：核对作用到的只是本 execution 自身的状态，不是别的具体对象（SPEC §4.1 第 4 类与优先规则）；写进 kernel 日志的，核对记为宿主可观察的内容都取自它自身的状态，消息里的其余内容另作候选效果；带宽不测，可见性未定的不测可见性（按看得见处理） | 宿主上读到的 /proc/\<pid\>/cmdline 是本次运行的沙箱任务的条目 |
  | 中介 | 不测：execution 写通道的那一步按交付测；engine 替它做得对不对归 2.1、2.2、3.1 | — |
  | 未定 | 查清之前不测；查清后按新的记录取值测 | — |

- **每个测试事先写：**
  - 判据：三种结果各是什么观察（返回值、errno 或信号）。预期的机制挡住；成功（并核对目标身份）；其余结果（别的机制挡住、
    准备或观察失败）记不确定，查清是哪个机制再定。例如写 /runtime 得 EROFS 是只读挂载挡住，得 EACCES 是文件权限挡住，两者是
    不同的机制。只有对应的对象效果确实发生，才是反例。
  - 目标：目标存在，并核对它的身份。
  - 对照：路线测试配正对照，即同一个探针对本次运行建的、按设计够得着的对应物能成功，或在沙箱外以同一 uid 能成功；边界测试配
    负对照，即越出权利的一侧失败。
  - 事后核对：按候选效果写。路线测试在效果可能发生的窗口过后，从沙箱外核对被禁止的效果没有发生；读出、暂时阻塞与延迟
    效果各写观察见证与窗口的依据（部分完成或延迟生效的不算挡住，SPEC §4.1）。边界测试核对预期的改变只落在交付对象上。观察不足的
    记不确定。
  - 对照不成立、准备失败、超时或观察不足，结果记为不确定，不计作被挡住，这个测试不作 [M] 证据。
- **怎样组织：** 按"挡住它的机制"成组，每组一张尝试清单（表驱动）。这是测试的组织方式（事后分类），不是完整性的推导：要测
  什么由矩阵决定，矩阵找到的每条路线归到挡住它的机制那一组，归不进的就新开一组，所以分组不限制覆盖。起始的组：文件视图
  （mount namespace、pivot_root、挂载标志）；pid namespace；net namespace 加 seccomp 禁网络调用；ipc namespace；seccomp 过滤器；
  无 capability 与 no_new_privs；文件权限；另加三组边界测试：交付权利两侧、两个沙箱间的私有性、宿主共享设备的身份。
- **用途说明：** 每个探针源码、测试清单与运行记录的开头放这一句："这是 1.1 隔离论证的验证测试：对本机上、由本次运行从固定
  版本编出的沙箱，确认越权的尝试被挡住；目标是本次运行自建的诱饵；不研究、也不记录任何绕过方法。"
- **放在哪：** 测试源码、尝试清单与运行脚本放在 work/tests，不放进 engine 的检查目录（否则 engine 变了、基线要变）。测试清单
  一行一个 NB-T-nnn，写所属的组、尝试的动作、目标、判据、对照、事后核对、对应的格或路线。
- **运行规则：**
  1. 对基线 v1 编出的产物运行。每次运行先跑 `python baseline.py check v1`，核对 `uname -r` 与基线 v1 一致，再重读 M 的宿主部分
     （01 §5 的 CONFIG、sysctl 与宿主其他事实，以及 NB-EV-019 的各项），与登记的读数逐项比对；任何一项不一致就停，差异登记为新的宿主读数，按 PLAN 停点 3 交用户。然后把 engine
     快照复制到本次运行新建的临时目录里，以非 root 身份编译。
  2. 在 WSL 的 Linux 里以 root 运行，整个运行放在一个私有 mount namespace 里。运行开头核对：自己的 mount namespace 与 PID 1 的
     不同，/ 的传播属性为 private；测试用的工作区 uid（70000–70002）在宿主上没有账户，也没有以它们运行的进程。不满足就停。
  3. 本次运行可以新建：/tmp 下的临时目录；/var/lib 下排他新建的部署挂载点（部署根须在 /var/lib 下，01 NB-K-01）；两个 256 MiB
     镜像文件，mkfs.btrfs 后 loop 挂载作部署根与工作区存储（engine 要求它们在 btrfs 上）；其中的 btrfs 子卷与 bind 挂载；一个
     装本次运行启动的编译与沙箱进程的 cgroup（控制运行的脚本留在 cgroup 之外，由它放进进程、超限时终止并负责清理）；用编出的 spawner 起的沙箱。只碰本次运行自己建的对象。
  4. 测试不碰真实的敏感对象（宿主的口令文件、密钥与凭据、别的用户的文件与进程等）：目标一律由本次运行自建，名字标明是诱饵
     （例如运行目录里以 nb-decoy- 开头的文件、运行自己起的诱饵进程）。只能拿真实敏感对象来测的路线不测，按 [R] 判，测试一栏
     写明理由。碰宿主上不敏感的共享对象时（例如宿主的 /dev/null），只用不破坏的形式，不记录读到的内容。会影响宿主的测试（内存
     耗尽、全机写回压力、无界压力）与破坏性测试不做。
  5. 有界：单个测试 30 秒，整次运行 10 分钟；本次运行的 cgroup 内存上限 2 GiB、进程数上限 1024；输出目录不超过 10 MiB。超出任何
     一项就中止，结果记为不确定。
  6. 清理，正常结束、出错、超时与中断都走同一顺序（运行脚本捕获终止信号）：由 cgroup 之外的控制脚本先回收本次运行的全部进程（核对 cgroup 里没有进程），
     再卸载本次的挂载，确认两个镜像没有残留的 loop 设备，再按记录的路径、核对前缀后删除临时目录、镜像、部署挂载点与 cgroup；
     最后核对宿主的 core dump 目录（Windows 侧 wsl-crashes）没有新文件。清理结果写进运行记录；清理失败就停下报告，后续批次
     不开始。
  7. 每一批由用户说"开始"（PLAN 停点 5）。反向测试是功能检查，不读性能数据，不需要用户清空机器。
  8. 每次运行一个独立的输出目录，放在 work/evidence 下。目录必须平铺，不建子目录（检查脚本对子目录报错）。README 写基线版本、
     编译与运行命令、时间、kernel、宿主配置比对结果、policy 与 BPF 的 digest（与参照比对：参照在第一批正式运行时由基线快照的诊断白名单生成一次并登记为证据）、部署目录的 digest、测试清单与
     运行脚本的 blob，并列出 sha256；登记进 04；旧的运行记录保留。
- **试跑与规模：** 2026-10-25 的试跑（NB-EV-020）确认了编译、运行与清理可行。它早于上面的判据、对照与部分运行规则，只作可行性
  证据，不支撑任何格。测试规模由矩阵决定，第二块写各章时定；估计（推断）约 200–400 个用例、20–40 组。

## 2 TLC

**TLC。** TLA+ 是规约语言；TLC 是它的模型检查器，把模型代入一个有限规模的实例，从初态出发走遍所有能到达的状态，每个状态
检查不变量。TLAPS 是对任意规模成立的证明系统，暂不做。

- **模型写什么：** 只写和 1.1 有关的状态：每个 execution 握着哪些引用、每个对象归谁（交付、本地独占、宿主共享、别的
  execution、宿主）、登记了哪些延迟动作、epoch 与 uid 分配。动作按类抽象。每条动作规则从相应各格的保守摘要写（这个动作可能
  产生、转交、作用到的引用与对象），不从格的记录写；从记录写，I3 就是写进模型的，检查成了同义反复。动作粒度按主干写定的转换
  粒度（SPEC §4.2"证明的形状"）。对象按种类各取一个代表，同种对象可以互换的理由写进 run-spec。
- **每个相关转换的去处：** 每个相关转换，包括不移动引用、但影响对象效果的可信方动作（例如可信方后来解引用的 symlink、FIFO、
  锁与租约，SPEC §4.2 第 4 步），归入三者之一：写成模型转换；经证明不影响不变量而省略，证明写进 run-spec；交给有具名出处的剩余论证
  （保持论证的某一格，或组合章）。没做完的记 open。"不在模型里"不等于在范围外：排除只用 METHOD 规则 2 的四类。
- **界限：** 两个 execution，其中一个有后继；后继同时包含同一工作区的后继 execution（01 NB-K-15，同一 uid 数值）与 engine 的
  epoch 更换（NB-K-16）；有限个对象与引用。在这个实例内检查所有动作的先后顺序。实例之外的规模，TLC 的结论不说明，由组合章
  论证（PLAN §1.1）。
- **反例：** 只有在 [R] 以源码说明这一步在任何输入下都不会发生时，才当模型错误处理，记进 reconcile；[M] 只作佐证，两者不一致
  记 open。改正只能删掉抽象多出来、已被这样说明不存在的行为，M 的行、列、kernel 源码与宿主读数都不变，所以不算缩模型。否则
  转成路线，查清之前记 open（METHOD 规则 4：反例之后不缩模型）。
- **运行规则：** 运行前把界限、负对照（故意放松一条规则，TLC 应报出反例）、输出目录和硬时限写进 run-spec：最长 10 分钟，堆最多
  2 GiB，状态目录最多 1 GiB；碰到任何上限就停止，记为不确定结果。状态目录放在仓库之外的 D 盘研究区，用完删除；work/evidence
  里只留 run-spec、反例 trace 与摘要，平铺，不超过 10 MiB。每次运行登记进 04。
- **查不了的：** 每条抽象规则与效果观察是否忠于 kernel 与 engine（靠测试、读源码与语义对应审查）；列没列全（靠表与审核一）；
  模型里的不变量与效果分类是否足以推出 SPEC §4.1 的性质（靠人审与蕴含论证，审核三核对）。TLC 只查 I1–I3 在界限内的可达状态上
  成立，不给出"I 推出性质"的一般论证。最后一项不要求 I3 与性质形式上相等：I3 是不变量的一句，性质由 I 推出，I 可以比性质强。
  模型只有引用、归属、登记、生命周期这几个维度，I 在模型里最多承载 §4.1 在这些维度上的部分；§4.1 里模型维度之外的部分（第 4 类
  的汇总状态、私有判据里"生命周期内作用不到"与"在本 execution 之外没有对象层面的效果"两条、文件内容与时序）由各格的保守摘要
  承担，第三块的蕴含论证把不变量与各格摘要合起来推出性质。界限之外的规模与没写进模型的转换，按上面的规则交给具名论证。
