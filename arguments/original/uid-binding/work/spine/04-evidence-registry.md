**Tags (exactly one per row).**

- `[M]` measured — a lab run observed it. The row carries the report file and section, the run date and the
  substrate string as the report states it. Rows observed under the 2026-09-11 *diagnostic* seccomp policy
  (not the production allow-set) say "diagnostic policy" in the note.
- `[R]` source-read — a fact read from kernel source, a man page, an external record cited by a source, or
  a design/derivation text. Kernel items carry the tree, the tag and `path/file.c:line` exactly as the
  source note gives it. The pinned tree is Microsoft `WSL2-Linux-Kernel`, tag `linux-msft-wsl-6.6.87.2`;
  `kub` records its files as byte-identical to upstream `v6.6.87`, and `fdsurvey`/`desc9` pin commit
  `427645e3db3a8896714f22a3d3fe0c3f7b317ad4`. Where the source note names only a function, the row gives
  the function and the note says "line not given in source note"; no line number is supplied here. Kernel
  facts that a source cites from an external record — a historical commit, a CVE or NVD entry, a
  mailing-list post, a project bug — are *external kernel records*: the fact or note column carries the
  record's own identifier (commit id, CVE number, list or issue reference) and the date column the record's
  date where the source gives one; they carry no pinned-tree file:line (EV-22, EV-23, EV-27, EV-28, EV-36,
  EV-87; counted in §4; EV-28's source gives no message id). Added after R2 F-09; wording after the recheck
  (N-04); EV-28 and EV-87 added to the class after the cross-family addendum (F-05).
- `[S]` stated requirement — a design statement about engine or spawner behaviour that is not built or not
  exercised: a specification, not evidence that an implementation exists. `[S]` here means the same as the
  `[U]` tag used in `option-b-workload-per-engine.md` and `scope-and-boundary.md`.

**Rules.**

1. *Reclassification by meaning.* A row's tag follows what the fact is, not the label of the section it
   sits in. A section that mixes kernel semantics and unbuilt engine behaviour is split into `[R]` and `[S]`
   rows. Every row whose tag differs from the source's own (or implied) label is listed in §2.
2. *Nothing assigned.* No row names an attack route of this line, credits a design item, or states a
   disposition. Source terms such as "route A" (kub §6.1) are the source's own names, quoted.
3. *One fact, one primary row.* A fact present in two sources is registered once, from the primary
   source, and the second location is named in the note.
4. *Dates.* `[M]` rows carry the run date stated in the report; where a derivation text dates the same
   measurement differently, the report's date is used and the note records the other date. `[R]`/`[S]`
   rows carry the date the source gives for that passage, or "source undated; read 2026-10-14" (the date
   the row was read, at the blobs named in §3).
5. *Substrate.* Copied from the report's own setup line; "substrate not stated in source" where none is
   given. `[R]` rows carry "source reading; kernel tree and tag in the source column" for pinned-tree items
   and "source reading; no run (external record, man page or derivation text)" otherwise; a measurement known
   only through a listed source, whose report is outside the list, carries "source reading of <source>; <report>
   is outside this registry's source list" (EV-15, EV-32); `[S]` rows carry "design text; not built or exercised".
6. *Staged configurations.* Observations made on a staged configuration (arm3 m1, where execution A could
   reach execution B) are recorded as what they measured there, not as results about the adopted
   configuration.
7. *Excerpts* are quoted from the source with Markdown emphasis removed; at most 25 words.
8. *IDs* are two digits (three from EV-100, version 4), append-only, assigned in source order, with no gaps.
