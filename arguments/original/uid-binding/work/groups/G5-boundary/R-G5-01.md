# R-G5-01 — A uses a software kernel defect to alter observations/protected state, or reads through it then takes an additional attribution-changing step.

## 1 What the adversary does
A uses a software kernel defect to alter observations/protected state, or reads through it then takes an
additional attribution-changing step.

## 2 How it would produce false attribution
- **Preconditions:** a kernel defect reachable from the agent's syscall face under the deployed allow-set —
  N1 of the exclusions ledger (tm D3), the software path of the kernel-breach paragraph — yielding an
  arbitrary kernel-context read, write or execute. The adversary is arbitrary code at u inside the envelope
  from T-11 on; the model's capability is not an input (AA-12). Configuration: all three (C-LS / C-LP /
  C-R) under the common abstraction of the frozen revision, since the defect is reached through the agent ↔
  engine leg's syscall face, identical in all three; S2 narrows that face without changing the branch.
- **Transitions traversed:** T-11 → T-66 (the disturbance, 01 §3.5) → one of four write forms, each landing
  in a normal-flow receive: (w1) the sending task's own credential rewritten to u_B → T-20 (a) stamps u_B →
  T-21 … T-24, accepted at row B if the bytes arrive on B's channel (A-07, or a write of the engine's own
  descriptor table) or at row A if the row's `expected_uid` is rewritten as well; (w2) the queued skb's
  control block rewritten after capture (I-02) → T-21 … T-24; (w3) engine memory rewritten — the row's
  `expected_uid` (I-05, C-03 p33), the Channel → Session association (C-05 p51), a `UidLease` state or
  `membership_empty` (C-06 p61; IG-03, IG-06), a `RequestEntry`'s context (C-08); (w4) a task moved between
  pid namespaces or P_X's membership structure altered (C-06 p62; IG-02, IG-05). The read form: T-66 as a
  read alone changes no stamp, rendering, row association or membership (02 §4.2); the trace then needs a
  second step, which is either one of w1–w4 (then it is the write form of this same route) or an in-model
  action using what was read. A leaked engine-end descriptor number, socket cookie or session-table entry
  is not a reference and confers no access (EV-94); a leaked engine secret is not an attribution input; what
  remains is the A-07 acquisition footing, which is R-G2-09's subject and U-04's, not a read-alone false
  attribution. The additional attribution-changing step the ledger sentence asks for is therefore a write
  (w1–w4) or the in-model route that consumes the read, and the latter keeps its own file.
- **Sufficient condition violated:** any of C-01 … C-08, by B(R-G5-01) = H ∧ N1 ∧ (Bad_acc ∨ ¬C-08) (02 §4):
  the history obtained the forbidden kernel-defect access and holds an accepted event whose label names an
  execution other than a contributing byte's Exec(b), or a carry failure. The label is wrong because an
  input the chain of 02 §3 relies on — the stamp, its rendering, the comparand, the row, the lease or the
  membership — was written by the adversary instead of produced by the pinned kernel semantics.

## 3 What stops it
Declared exclusion: the kernel-breach paragraph of scope-and-boundary.md §Boundary Defence (N1, the
software path) — the first non-goal is "an assumption that no kernel breach occurs, stated by effect and by
path"; by effect "any read, write or execution the adversary obtains through a kernel defect … the
assumption covers all three; no read/write distinction narrows it"; by path, "N1 is the software path (a
kernel defect reached from the agent's syscall face)" — under the non-goals list of the same section
(compromised host kernel · malicious hypervisor · broken sandbox implementation · fully-malicious engine ·
cross-domain hardware read/write) and the supervisor's acceptance recorded there (2026-10-04) that the
exclusion may be stated as an assumption. The preservation row T-66 records that no guard of I survives the
disturbance; no mechanism of the frozen design is claimed against it.

**What the exclusion buys.** Every condition C-01 … C-08 and every guard IG-01 … IG-13 is stated about
values the pinned kernel produces and protects: the per-skb stamp of the sender's real uid on every write
path (EV-07, EV-10, EV-11), its rendering in the engine's namespace (EV-13), the write-time map rule
(EV-21), the zap ordering behind `pid1_reaped` (EV-17), and the engine's own memory. The preservation
arguments of G1–G4, and of T-61 and T-62 in this group, hold only relative to a kernel that executes those
semantics and keeps engine memory and pid-namespace state intact (02 §0.3; AA-04). The exclusion is what
makes a "supported under stated premises" disposition a kernel-semantics conclusion at all; without it the
property is not stated.

**Width check (kub §8).** The derivation requires the exclusion to cover arbitrary write and code
execution, not merely "credential tampering": the SoK corpus it re-counted (EV-45) tags a minority of the
published exploits as credential overwrite and the majority as general control-flow hijacking, and a kernel
write that never touches `struct cred` falsifies the binding just as well — the skb stamp (w2), the
comparand (w3) and the membership (w4) above are each a non-cred write. The paragraph as frozen covers "any
read, write or execution", so it is wide enough; a narrower exclusion would leave the majority technique
class inside scope while the guards fall to it equally. The read half additionally needs §2's second-step
clause: a read alone is not an attribution change (02 §4.2), so the read form is out of scope only as the
precondition of a write or of an in-model step, and the in-model step keeps its own route.

**What the exclusion does not do.** It does not absorb legitimately acquired privilege: a path the kernel
permits under the deployed configuration — the paragraph's own instance is `unshare(CLONE_NEWUSER)` restoring
capabilities where S1 is absent — is a configuration failure against S1–S14 (T-67), carried by R-G5-03,
R-G5-04 and R-G5-07, never here. And it is an assumption whose cost is owed as evidence (W2's kernel-TCB
residuals, SUB-14's read paths), not an argument that the kernel is sound.

mechanism is claimed. The disposition does not rest on the two-valued property (EV-29), which assumes an
intact kernel.

## 5 Disposition
**declared out of scope** (the same value as the `disposition:` field).
- Premises that must hold: the kernel-breach paragraph as frozen (no kernel breach; read, write and execute
  alike; N1 the software path), under the non-goals list of scope-and-boundary.md §Boundary Defence and the
  supervisor's acceptance recorded there; S2's deployed allow-set narrows the reachable face but does not
  change the disposition; the common abstraction of the frozen revision (all three configurations).
- Evidence limit (configuration, substrate, run dates): the exposure items EV-27 and EV-86 are source readings
  at the pinned tag `linux-msft-wsl-6.6.87.2` (2026-09-07, 2026-09-28), not assessed for reachability under the
  diagnostic or the production policy.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).

## 6 What remains
- Residual: the exclusion is an assumption, not a result; what it costs is owed as evidence by W2
  (kernel-TCB residuals with their exposure on the actual build) and by SUB-14 (read paths), per the
  paragraph itself. Two exposure items at the pin are named above, and neither has a reachability
  assessment under the channel's socket type and the deployed policy; whether EV-27's OOB path is reachable
  when the receiver treats OOB as fatal (EV-90) is an open question. The read-then-act refinement — whether a
  permitted leak can reach a write of binding state — is U-04 (02 §5.2) and stays open. No new ID.
- Design obligations surfaced for the engine: none from this route — every obligation presumes the kernel;
  the only item is the one the substrate note already carries, that a deployment states its build and the
  exposure items at it (tm D8; T-66).
- Cross-references: R-G5-02 (N9, the hardware path, declared beside this one); R-G2-09 and A-07 (the
  in-model second step of the read form); R-G5-03, R-G5-04, R-G5-07 (lawful privilege and configuration
  failure, which this exclusion must not absorb); preservation row T-66. C1–C4 and obligations #1–#6 all
  presume kernel integrity (scope §Trusted Components; kub §8, "the whole binding is coextensive with kernel
  integrity"); obligation #6 (the engine as a reference monitor) is the one the route touches by name, as a
  tamper-resistance premise it does not discharge.
