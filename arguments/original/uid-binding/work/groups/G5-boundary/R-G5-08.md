# R-G5-08 — A foreign task holds the row uid during its allocation by a cause not yet classified as a prior survivor, pre-existing holder or lawful later acquisition.

## 1 What the adversary does
A foreign task holds the row uid during its allocation by a cause not yet classified as a prior survivor,
pre-existing holder or lawful later acquisition.

## 2 How it would produce false attribution
- **Preconditions:** the branch is the explicit remainder of D_62: a live task outside P_Xr has real kernel
  uid u_r at some t in J_r, and the trace contains none of the three named facts — it is not a survivor of a
  prior allocation of u_r (q24, R-G4-01), it did not already hold u_r at J_r's reservation (q25, R-G5-06),
  and it did not become a holder through a documented lawful uid change, namespace map or credential-bearing
  task creation (q26, R-G5-07). 02 §4 calls this an unresolved causal refinement slot that must not gain a
  supported disposition because its predicate is total; since version 7 it carries a stated property that
  empties it once it holds (02 U-02, U-05; ledger row). What the cell can still hold, by the letter of the
  other predicates: a task of P_Xr's descendant pid namespaces is a member, not foreign (D-GT); a clone this
  engine's spawner launches at u_r for a record with another uid is p53 (D_53 → R-G1-06, ordered before
  D_62); a second allocation of u_r by this engine is p61 (R-G1-05) and another engine's is R-G5-06; a task
  moved into a pool uid by a kernel defect is H (R-G5-01, R-G5-02); a kernel-side task running on a borrowed
  credential either shares the submitting task's pid namespace, and is then a member, or runs at kernel
  credentials, not u_r. Configuration: all three under the common abstraction.
- **Transitions traversed:** by the ledger, T-01, T-05, T-61, T-62 and T-67 — the transitions that create
  or change holders of u_r; the slot's own history is unnamed. Any accepted event would then traverse
  T-20 (a) → T-21 … T-24 at row r through an endpoint (A-07), as in R-G5-06.
- **Sufficient condition violated:** C-06 p62; branch D_62 ∧ ¬(q24 ∨ q25 ∨ q26). The label would be wrong
  for the same reason as in R-G5-06: the chain of 02 §3 places the task in P_Xr by its uid alone.

## 3 What stops it
The deployer's uid inventory of engine-requirements §8 for tasks outside the engine's own executions, and,
for tasks inside them, the kernel's writers of a task's uid at the pinned tag — a real uid copied at fork,
never written by execve, moved by the setuid family only within the own set unless a reachable user
namespace maps another kernel uid, all q26 paths — so that with an intact kernel no history is left in this
cell. The argument splits the possible holders in two.

Holders outside the engine's executions. The first deployment entry of
engine-requirements §8
requires that the deployer's inventory of the pool range names every holder of a pool uid, the engine's
leases being the only ones, with no allocator, service or account and no second engine on the range; for
local configurations the model instance runs under no pool uid (rr L387–389, L885–886). Under it, no host
or other-compartment task holds u_r at any time; a kernel-service credential (the usermode helper) is a
host task's and not a pool uid (kub §6, writers passage); a privileged actor that places a task under u_r
outside every configured allocator is a T-67 configuration failure (AA-04). The engine does not check any
of this — the reservation reads only its own lease state (conn L106–107) — so it is a premise.

Holders inside the engine's executions. A task of another execution X_s that holds u_r either had it from
its launch — p61, p53, q24 or q33, all cells ordered elsewhere — or changed to it later. The 2026-10-18
source reading of kub §6 (the passage on the writers of a task's uid, proposed `[R]` row) settles which
later changes exist at the tag: a task alters only its own credential, and every commit starts from a copy
of it; the real uid is written only inside the setuid family (sys.c L552, L629, L713) and by the keyring
session-to-parent path, which copies the task's own values (process_keys.c L928); fork and clone copy the
parent's credential; `execve` never writes the real uid, and under `no_new_privs` cannot move the effective
uid either (exec.c L1643; commoncap.c L920–923); without `CAP_SETUID` in the task's current namespace each
new value must be one of its own uid, euid or suid. Every such change is a documented lawful change, a
namespace map or a credential-bearing creation — q26, which routes the history to R-G5-07, where C1 with
its re-read and the first half of C2 stop it.

The reading adds two conditions, each carried elsewhere:
- (a) "No `CAP_SETUID`" must be read as "no task of the execution can create or enter a user namespace whose
  map names a kernel uid other than u". The kernel guarantees it for every map the execution writes itself
  (one extent naming the writer's own euid; EV-21), the set-user-ID map helper is cancelled by
  `no_new_privs`, and entering an existing namespace needs `CAP_SYS_ADMIN` over it, which a task holds only
  over namespaces its own euid owns (EV-56 measured the refusal for another uid's). Step 11's seccomp does
  not filter `setns`, and is not needed here. A wider map needs a writer holding `CAP_SETUID` over the
  parent namespace: that is q26's namespace-map history — R-G5-07 path (iii) for the real uid, R-G5-04 for
  the explicitly attached stamp — carried by the same deployment entry against map-writing helpers and,
  for a host actor, AA-04. It does not land in this cell.
- (b) On the stamp side, an `override_creds` window that runs a unix send exists only in io_uring (a
  registered personality, or an SQPOLL ring's credential). An override replaces only the subjective
  credential, not the real uid that p62 reads, so (b) does not bear on this cell; it bears on the stamp's
  correspondence with its sender (C-02, the R-G2-05 remainder), carried by the production allow-set (S2;
  option-b step 11, E-10; EV-129 `[S]`) and the no-business-fd-pass constraint.

Nothing is left for this cell, and no mechanism is claimed against an unnamed cause: the stop is the two
positive properties holding. The G5 preservation rows bound the transitions (T-61 and T-62 preserve under
the premises; T-67 names the departures), and IG-02 is the guard any history here would violate.

## 5 Disposition
**supported under stated premises** (the same value as the `disposition:` field) — a design-layer and
kernel-semantics conclusion, not a claim about the deployed system. A deployment precondition the engine
does not check is a premise named below (user ruling of 2026-10-18 on CR-G5-05); the disposition rests on
stated positive properties, not on the totality of the cell's predicate.
- Premises that must hold: ¬H (otherwise the history is R-G5-01's or R-G5-02's); the exclusive pool and the
  uid inventory as the first entry of engine-requirements §8 states them, and the local-instance
  precondition (rr L387–389, L885–886); AA-04 for privileged actors outside the configured allocators,
  including a writer of a wider user-namespace map; the kernel at the pinned tag as read in kub §6 (AA-02);
  the selectors q24, q25 and q26 as 02 defines them; the common abstraction of the frozen revision.
- Evidence limit (configuration, substrate, run dates): no run measured any history in or near this cell; the
  kernel reading of 2026-10-18 is a text-pattern sweep with its stated bounds, unmeasured.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).

## 6 What remains
- Residual: the reading's bounds travel with the inside-engine half — a uid write through a whole-struct
  copy or an unusually named variable would escape the sweep, override callees were not traced, and the
  setuid-path LSM hook can only refuse a change. A history reaching u_r by a path the reading does not
  list would land here and must be investigated, not dismissed. Coverage uncertainty: U-02 keeps this as
  one of the seven refinement slots; a mechanism, if one is ever named, is an appended route in a new 02
  version, never a silent fill.
- 02's wording (CR-G5-04, answered): the inventory empties the slot for holders outside the engine's
  executions; holders inside them are emptied by the kernel reading, which routes every change to q26.
- Design obligations surfaced for the engine: none here. Condition (b) keeps io_uring out of the production
  allow-set and keeps the no-business-fd-pass constraint (S2, E-10), recorded for R-G2-05.
