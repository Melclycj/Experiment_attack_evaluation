# R-G1-03 — A's correctly stamped frame is installed/read through a row or endpoint whose initial lease/execution correspondence is wrong.

## 1 What the adversary does
A's correctly stamped frame is installed/read through a row or endpoint whose initial lease/execution correspondence is wrong.

## 2 How it would produce false attribution
- **Preconditions:** at install (T-09) the Channel the frame will arrive on is attached to a Session whose execution_id, lease_id or expected_uid belong to a different reservation than the socketpair's SpawnRecord — the engine end of record X_A installed into row B, or row A created with a lease_id naming another workspace's lease — or the peer end of A's socketpair went to another record's clone (the endpoint half of IG-12). A sends ordinary stamped frames on its own fd 3; the error is in the trusted path, nothing adversarial beyond sending is needed. Configuration: all three under the common abstraction (01 AA-06).
- **Transitions traversed:** T-01 (object creation), T-02, T-03 (record), T-04 (socketpair per record), T-05, T-06 step 10 (peer-end hygiene), T-08 (SEALED on that engine end), T-09 (install), T-12 and T-26 (activation on the whole welcome send), T-20 … T-24 (frames read through the installed object).
- **Sufficient condition violated:** C-05 p51 (the row read at a has the immutable reservation A_r corresponding to its original Channel). Cell D_51, selector q18 (the original row/channel/lease association was inconsistent when installed); B(R-G1-03) = ¬H ∧ D_51 ∧ q18. The label read at a then names A_r of the row while the bytes' origin is the execution whose clone holds the peer end of that socketpair — a different execution — so L(a).execution ≠ Exec(b). The three launch facts of 02 §1 (X_r launched with A_r.uid; row r holding X_r's engine end; the peer end to X_r's clone alone) are G1 preservation guards IG-10 (its halves (a) and (b) together give the first fact) and IG-12 (the other two); their failure alone puts no accepted byte at row r unless the stamp also matches, which under one uid per lease happens only when the row's uid and the clone's uid coincide — the record-level case of R-G1-06 and the double-allocation case of R-G1-05.

## 3 What stops it
The row, its lease and its channel are one object graph created at T-01 and bound at T-09 by matching the prepared record's execution_id and lease_id to the original row in one decision, by object and never by number. At T-01 the engine creates Execution, Session and UidLease together: the session, channel and lease identifiers are derivations of execution_id (conn L73), the row's lease is the workspace's registered uid (rr L560), and the triple is written in one executor decision (preservation row T-01). In the prototype, execution_id is the start-up engine_epoch (128 random bits) joined to a non-wrapping allocation_seq, and the lease, Session and Channel ids are that id with :u, :s and :c appended (EV-240); launch() builds the lease, Session and Execution in one call and links Session to Execution there (EV-194). T-02 serializes the same execution_id, lease_id, uid and gid into the spawn request (conn L223–224, L229–230; row T-02); T-03 creates the SpawnRecord from that request (conn L85; row T-03); T-04 creates one socketpair for that record (row T-04; EV-179). At T-09 the engine admits spawn_prepared only if its engine_epoch is the engine's, its execution_id names a row in the executions table and its lease_id equals that row's; an unknown execution or a changed lease is a control fault (conn L133; EV-220, EV-218); a consumed prepared arriving again has its fd shut before the fault (conn L135–137; EV-219); the three digests and copy_id must equal the row's and the row must be PREPARING (EV-185). The fd is installed into a new Channel built with that row's Session in the same call (conn L226, L231; EV-194; row T-09). Later callbacks hold the object, never an fd number: the loop dispatches a selected event only if the callback registered when it was selected is still the current one (conn L81, L523; EV-192; EV-94), and old callbacks did not reach a new row on a reused uid and fd number (EV-190, EV-189, EV-191). The endpoint half: the peer end reaches the clone of the same record by inheritance at T-05, every other descriptor is dropped at T-06 step 10 before execve (rows T-05, T-06) — the child shuts the engine end, the control and worker descriptors, moves the channel to fd 3 and runs close_range(4, ~0) (EV-179; EV-64 versus EV-63) — and the spawner's T-08 read of SEALED on this engine end requires the credential pid to equal the record's child pid (EV-210; row T-08), tying the fd it will hand over to the child of this record.

## 5 Disposition
**supported under stated premises**
- Premises that must hold: AA-04 (the spawner attaches the engine end of the record it names and runs the code read at EV-179 / EV-210 — MM-05: no kernel query lets the engine verify the peer); AA-01 (single executor; the one-decision install); AA-09 (the bootstrap writes only SEALED before execve). A design-layer conclusion, with the engine-side items realized in the prototype and checked; not a claim about a deployed system.
- Evidence limit (configuration, substrate, run dates): unit and integration runs of 2026-10-19 and the AA-13 run of 2026-10-18. Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). Limits of the checks: fd-number reuse inside one round is made by the tests (EV-190) or by os.dup2 (EV-191, epoll backend only), and through the real spawner only in sequence (EV-189); the endpoint half rests on code reading (EV-179) and the SEALED pid tie on code reading (EV-210); the earlier d2 descriptor cells are 2026-08 without seccomp.
