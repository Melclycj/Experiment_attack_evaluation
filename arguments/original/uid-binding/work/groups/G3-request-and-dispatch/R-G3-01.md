# R-G3-01 — A's protocol data reaches an internal constructor which fabricates a validated sender without an originating frame.

Re-run at follow-up step 4 (2026-10-19) on 04 version 7. Design line numbers below refer to the fourth-revision
blobs (conn `0c16e567a34aa441`, rr `1a8ea18374b07431`, si `c8aff1a37d73561b`); engine file:line to the prototype
at commit 3ec67985 (engine code equal to 74833c58).

## 1 What the adversary does
A's protocol data reaches an internal constructor which fabricates a validated sender without an originating frame.

## 2 How it would produce false attribution
- **Preconditions:** A is the adversary of execution X (every task of P_X from T-11 on) holding its own fd 3;
  no foreign descriptor (A-07) is needed. A supplies protocol content (A-02): a `request` with chosen `id`,
  `task_call_id`, `task_id`, `resource_id`, `action`, `args` (since the fourth revision a `grant_ref` field
  is an unknown field rejected at T-24: conn L4, L466–468 of the third freeze; 01 v10 A-02); a `hello` with chosen
  fields; `cancel`, `task_result`, `bye`; or bytes that fail T-22 or T-23. The route additionally needs an
  engine code path that the frozen text does not contain: a constructor that produces a ValidatedMessage or
  ValidatedRequest with a VerifiedContext — or an E-09 verified_subject typed as a message sender — from
  those fields, from a stored copy of an earlier request, or from the connection's expected subject, for
  bytes that have no current recvmsg witness. Candidate shapes of such a path: an internal retry that
  re-submits a stored request after a failure; a replay built from the high-water-mark history; a reject
  path that assembles a context from the Channel's row; a step that types a trusted-caller message
  (task_start, T-31) as agent-sent. Configuration: all three (C-LS, C-LP, C-R) under the common abstraction
  of the frozen revision — the constructor is engine-internal and the agent ↔ engine leg is the same.
- **Transitions traversed:** T-20 (a) → T-21 → T-22 → T-23 → T-24 for some message (or T-22 / T-23
  rejection, with no D-ACC) → [the alternate constructor — not a transition of the frozen text; in the
  frozen text T-30 consumes T-24's object and T-38 copies its context] → T-30 → T-32 → T-33 → T-34 → T-38.
- **Sufficient condition violated:** C-01, component p11 (D_11: Bytes(a) is not a nonempty normal-stream
  byte sequence from actual send events — the accepted-subject event has no originating frame), selector
  q01 (the accepted context is constructed outside the original receive_step / T-24 path); C-05 fails with
  it — p51, because the row read at the event does not correspond to a read on its original Channel, and
  p52 for whatever fields the constructor fabricates. The branch is B(R-G3-01) = D_11 ∧ q01, in the first-
  failure mask F_1. Why it is a wrong attribution: the engine would hold an accepted-subject event whose
  label names an execution while no sending task exists for the labelled bytes, or whose bytes were sent by
  a task of a different execution — "an actual accepted-subject event with no such origin" is false
  attribution by 02 §0.1, whatever the engine's label says.

## 3 What stops it
One VerifiedContext constructor, at the receive entry; every consumer takes the label by object reference and
constructs none, and no retry or replay path re-creates a request — realized in the prototype engine and
checked by test and code reading up to the stub handlers. The design states four items; each now has a
realization in the prototype and a check.

1. **Constructor locality (T-24, a Step 1 fact).** Design: receive_step(Channel) is the only constructor of
   the immutable VerifiedContext, whose identity fields come from the original engine objects; hello may not
   supply uid, agent_id or grant (conn L522, L565, L572; EV-110). Realization: receive.py:297 is the package's
   one construction of VerifiedContext, reached only after the C reader has handed over a whole frame that
   passed the per-fragment comparison, the strict parse and the phase rule (EV-172); a text search run as a
   test finds the constructor once (EV-183); receive_step has one caller (EV-169; its transport.c line numbers are those of 3ec67985, the reader at 7b4ab727 is EV-265); the label fields are read
   from the Channel and its Session, the expected uid being write-once (EV-186); an identity-like field,
   grant_ref among them, makes every message type invalid (EV-184). The message objects that carry the context
   (Hello, Request, Cancel, TaskResult, Bye) are built only in receive.py's _message, called only from
   receive_step (receive.py:259–270, :300; proposed row 1).
2. **Consumers take, never make (T-30, T-32, T-33, T-38).** Design: admission and the frozen operation objects
   carry the context by reference; verified_subject is copied only after full E-02 validation, reject events
   carry none and the expected subject may not fill it (EV-113, EV-123, EV-156). Realization: admission starts
   from context.session_ref and context.channel_ref, and the RequestEntry holds those objects (EV-198); the
   decoy test shows admission, prepare, the final decision, dispatch and result driving reach no row by
   execution_id and every E-09 subject equals the VerifiedContext copy (EV-197); the recorder accepts a
   verified kind only with a VerifiedSubject and refuses a subject on every other kind, the trusted caller's
   task_call_* records among the control kinds (EV-225, EV-224).
3. **No retry, no replay (T-33, T-34, T-35).** Design: no automatic retry of a dispatched operation, retry
   budget 0, a new request needs a new id and full authorization; old or duplicate active ids close the
   session and execution is never replayed (conn L709, L964, L972–984; EV-111, EV-112). Realization: the
   request manager calls authorize once in its final decision, clears the candidate and passes the one-use
   operation only to handlers.start (EV-241); the chain on_request → prepare → final decision → handlers.start
   has one entry, the call in the data plane after receive_step, and a failed start ends in a terminal
   (requests.py:286–292; proposed row 2); an old or repeated request id ends the row with protocol_error
   (EV-228); a late result does not rewrite the decided terminal (EV-223).
4. **No second constructor at the entries (01 §5 entry check).** Design: the E-10 adapter is in the sandbox
   and speaks only fd 3; the E-09 hook is observe-only and returns no label rewrite; the trusted task entry
   creates TaskCall and TaskBinding, not validated agent messages (EV-114, EV-126). Realization: the whole
   package has one VerifiedContext construction (EV-172, EV-183), so no entry holds a second; the observe-only
   pre_egress hook point exists with no observer configured in the product, receives the frozen
   CandidateOperation and its return value is discarded (requests.py:114, :229–230; proposed row 3); the agent
   in the runs is the native fixture, not an E-10 adapter.

Preservation rows relied on: T-30, T-32, T-33, T-38 (this folder). T-24 is cited as a Step 1 fact (where the
constructor is); the correctness of what T-24 constructs is C-01 … C-05 at G2 and G1, not this route.

## 5 Disposition
**supported under stated premises** — the same value as the `disposition:` field.
- Premises that must hold: the engine is honest (AA-04) and its code is the prototype's at commit 3ec67985,
  in which receive.py:297 is the only construction of VerifiedContext; no consumer pending design — the MCP
  compartment, engine-forwarded inter-agent messages (mech L316; U-06), a real E-10 adapter or a configured
  E-09 observer — adds a constructor (each re-runs this route when it enters); the engine-internal grant
  lookup adds none (EV-243, realized by EV-184, EV-226, EV-227); the three configurations share the consumer
  path (AA-06). This is a conclusion on the frozen design and its checked realization in the prototype, not a
  claim about the deployed system.
- Evidence limit (configuration, substrate, run dates): the integration rerun after commit 7b4ab727 passed (EV-265, EV-271). The run is
  20261019T011226Z-engine-pool-70000 of 2026-10-19, repeating 20261018T231612Z. The consumer path is checked up
  to the stub handlers and is to be re-checked for each real connector (val §R-G3-05); the single-constructor
  fact is a text search (a Python dataclass can be constructed by any later code); the decoy test replaces the
  execution_id key only; one sending uid in the unit layer. The arm3 rows are of the lab binding engine
  (docker-seccomp T1, 2026-07-02 and 2026-07-03, staged configuration). All three configurations alike at the
  design layer.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).
