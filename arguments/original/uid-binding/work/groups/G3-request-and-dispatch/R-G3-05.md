# R-G3-05 — An attributed consumer changes or loses the original context in a way not yet reduced to numeric reuse, current join or label-only mutation.

Re-run at follow-up step 4 (2026-10-19) on 04 version 7. Design line numbers refer to the fourth-revision blobs
(conn `0c16e567a34aa441`, rr `1a8ea18374b07431`, si `c8aff1a37d73561b`); engine file:line to the prototype at
commit 3ec67985 (engine code equal to 74833c58).

## 1 What the adversary does
An attributed consumer changes or loses the original context in a way not yet reduced to numeric reuse, current join or label-only mutation.

## 2 How it would produce false attribution
- **Preconditions:** a consumer event whose actual origin is a D-ACC (p81's domain), and whose carried
  context is changed or absent, or whose emitted execution label or local_agent_id differs from the origin's,
  by a cause that is none of the three named ones: not q30 (a relookup by numeric uid, fd or request number,
  or by a recurring local_agent_id after reuse — since 02 version 7 a departure from stated design text),
  not q31 (a current request, cancel, task, grant or binding association joining another session or
  context), not q32 (reference retained, emitted execution label or local_agent_id changed). The adversary's
  inputs are those of the other G3 routes: arbitrary code in the sandbox sending well-formed frames (A-02,
  A-06). Configuration: all three (C-LS, C-LP, C-R) under the common abstraction; the consumers are engine
  userspace and do not differ between them (EV-96).
- **Transitions traversed:** T-20 … T-24 with a correct label (D-ACC, the VerifiedContext built at the
  receive entry) → any of T-30 … T-39. The slot names no single consumer step; it is the explicit remainder
  of cell D_81 (02 §4: "else → R-G3-05").
- **Sufficient condition violated:** C-08, component p81. Branch B(R-G3-05) = D_81 ∧ ¬(q30 ∨ q31 ∨ q32).
  Shapes the predicate leaves here (sub-cases of the predicate, not mechanisms): a consumer step that acts
  on an origin while carrying no context for it (the context lost, not changed); a consumer that holds a
  context object, or its fields, belonging to another request or session without a numeric relookup or a
  current join (a stale or substituted object); anything else that fails p81. Why it is a wrong
  attribution: the consumer's statement of who asked for the action — the admission, the authorization,
  the dispatched operation, the E-09 verified_subject — then names an execution other than the origin's
  label, or none.


## 3 What stops it
Every consumer step carries the verified context by object reference, with no construction and no lookup or
state key by name, uid, fd or local_agent_id (conn E-02 L581–583) — established in the prototype by the R-G3-05
check of the validation record (test and code reading, up to the stub handlers). The design statements the
2026-10-18 run named, and what the prototype shows for each:

- **One constructor, immutable object.** Design: the VerifiedContext is built only by receive_step and is
  immutable; its identity fields come from the original engine objects (conn L565, L572; EV-110). Realization:
  one construction in the package, receive.py:297, a frozen dataclass (receive.py:182–183), its label fields
  read from the Channel and its Session (EV-172, EV-186); a static test finds the constructor once (EV-183).
- **Every consumer by reference.** Design: admission, prepare and authorize, dispatch, handler and record take
  the VerifiedContext by object reference, construct none, and neither look it up nor key state by name, uid,
  fd or local_agent_id; the response callback and the sink hold the original RequestEntry and Channel; the
  frozen operation objects carry the entry (EV-156, EV-124, EV-123). Realization: admission starts from
  context.session_ref and context.channel_ref and the RequestEntry holds Session, Channel, Execution, TaskCall,
  TaskBinding and GrantState once; prepare and the final decision read only the entry's objects; handlers
  receive only the AuthorizedOperation and a Sink that holds only its entry; results and release go through
  entry.channel.frame_writer; E-09 subjects are VerifiedSubject.from_context copies (EV-198, EV-241). In the
  package the only uid-keyed table is the allocator's holders, used at reservation and release; the only
  fd-keyed table is the loop's registration table, used to fetch the callback registered on that fd and checked
  by identity before dispatch; no table is keyed by local_agent_id (EV-196). Tests: with the lifecycle's row
  for the execution_id replaced by a fail-on-touch decoy before the request frame, admission, prepare, the
  final decision, dispatch, result driving and release ran on the original objects and every E-09 subject
  equalled the context copy; each of four stages changed to look the row up by execution_id hit the decoy
  (EV-197).
- **The two keyed consumers the design names.** Design: the model body's tool definitions are reached through
  RequestEntry → Session → Execution → LaunchPlan or RuntimeDescriptor, never by uid, local_agent_id or request
  content; a per-execution provider choice is keyed by execution_id as an object reference (EV-159, EV-160).
  Realization: freeze_operation takes the tools as entry.session.execution_ref.plan.tools (operations.py:211),
  and the build has no per-execution provider choice — the provider is fixed on the resource
  (operations.py:219–228; val row 243, 由构造满足); both fall under EV-196's package reading (proposed row 1).
- **The label fields do not move.** Design: the reservation fields, local_agent_id among them, are written once
  by the executor at row creation; the executor is the only writer of Session and RequestEntry (EV-152,
  EV-157). Realization: Session's session_id, execution_id, expected_uid, local_agent_id, channel_id and
  execution_ref and Execution's reservation fields are write-once by type (objects.py:14–22, :151–152,
  :178–180; EV-186); a second assignment raises (EV-187); handlers deliver by a callback posted to the state
  executor's loop and the record thread writes only its own queue (EV-231).
- **Lost context is not silent.** Design: verified_subject only a copy, absent fields omitted, an event over
  4 KiB a record failure, correlation fields value copies (EV-113, EV-122). Realization: the recorder refuses a
  verified kind without a VerifiedSubject and latches the failure (EV-225); correlation fields are copied from
  the entry's objects (EV-229).

Why this empties the slot within the prototype: from the D-ACC to each consumer the context travels along a
chain of object references that starts at the one constructor (EV-172, EV-183). For a consumer to carry another
context it must obtain another object: construction is excluded (EV-183); a lookup or key by uid, fd or
local_agent_id is excluded (EV-196) and a lookup by execution_id is shown absent on the request path (EV-197); a
relookup by request number is q30; a current association is q31; a change of a label field under a kept
reference is q32 and is excluded by the write-once fields (EV-186, EV-187). For a consumer to carry none, it
would be a consumer step without the reference: each consumer in the prototype holds the entry (EV-198) and a
verified-kind record without a subject is refused (EV-225).

Steps the statement's list does not name: task_result and cancel (T-36, T-37) resolve only in the original
session (EV-229), so a wrong match there is q30 or q31; the task and grant association (T-39) is created only
for one Session, write-once, with no rebind entry (EV-227), so a wrong one is q31.

Preservation rows relied on: none. C-08 is excluded from I (03 §1.3); the statements above are design text and
its realization, not preservation conclusions.

## 5 Disposition
**supported under stated premises** — the same value as the `disposition:` field.
- Premises that must hold: the engine is honest (AA-04) and its code is the prototype's at commit 3ec67985; the
  consumer set is the one this freeze describes (U-06) and the prototype realizes — admission, prepare and
  authorize, dispatch, the stub handlers, result driving, release and the E-09 record; no observer is configured
  on the pre_egress hook; the three configurations share the path (AA-06). This is a conclusion on the frozen
  design and its checked realization in the prototype, not a claim about a deployed system, and it does not
  claim the remainder empty in a real system.
- Evidence limit (configuration, substrate, run dates): run 20261019T011226Z-engine-pool-70000 of 2026-10-19
  (repeating 20261018T231612Z, the run val names). The check's own limits, as val
  §R-G3-05 states them: covered up to the stub handler; the decoy replaces the execution_id key only, the uid,
  fd and local_agent_id keys being excluded by code reading (EV-196); BUILD-PLAN asks for the check to be
  repeated each time a real connector replaces a stub, and a result under the stub is a stub result. All three
  configurations alike at the design layer.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).
