# R-G2-06 — A's ancillary is present but ABI conversion, stale decoded storage or a substituted pid lookup turns it into another principal.

## 1 What the adversary does
A's ancillary is present but ABI conversion, stale decoded storage or a substituted pid lookup turns it into another principal.

## 2 How it would produce false attribution
- **Preconditions:** the credential arrives intact; the route needs a receiver that misreads it — converting
  the uid to a signed integer (a uid above 2^31, or the overflow value, flipping sign), decoding the ucred
  with a wrong layout, reusing a previous read's decoded credential for the current bytes, or replacing the
  uid by a lookup of the delivered pid in /proc, which a pid reuse or an exit between send and lookup then
  misleads (K-10, T-65). The adversary's part is to choose a uid, pid or timing that makes the misreading
  land on another row's expectation. Configuration: all three branches under the common abstraction
  (agent ↔ engine leg).
- **Transitions traversed:** T-20 → T-21 → T-22 → T-23 → T-24; T-65 as a fact for the pid-lookup variant.
- **Sufficient condition violated:** C-03 p32 (v(f(b)) = r(k(b)) with the correct ABI and intact ancillary).
  B(R-G2-06) = D_32 ∧ ¬q12 ∧ q13. Why it is a wrong attribution: the decoded value v(f) compared at T-23 is
  not the rendering of the sender's stamp, so equality with e_r no longer implies that the sender's uid is
  u_r.

## 3 What stops it
T-23's decode with the ABI types from the current read's control buffer, the pid diagnostic only, and no
identity lookup cut the route at the decode. Design text (conn at the fourth-revision blob
0c16e567a34aa441): E-02 step 4 (L462–464) — pid, uid and gid are decoded as pid_t, uid_t and gid_t, the uid
is never converted to a signed int, pid 0 and the sentinel uids are refused before the equality; step 1
(L453–455) — msghdr, iovec and control buffer are re-initialised on every step and the last return's
length, flags or credential are never reused; step 6 (L469–471) and E-02 VerifiedContext (L573) — the pid
is a diagnostic, recorded only when equal across fragments, never a finer subject. The kernel renders the
stamp with from_kuid_munged in the receiver's namespace (kub §2.5), which is the initial namespace under C3,
so the rendered number is the kernel uid itself.

Realization in the prototype (commit 3ec67985). Decode: w2_ancillary copies the credential into a struct
ucred that is zeroed on each call and compares its uid_t with the expected uid_t in C (EV-171, EV-237, read
at transport.c:90–122 on 2026-10-19); the observed uid never leaves C — w2_frame_receive returns only a
whole frame body and its length (EV-169, EV-186) — so no conversion of the observed value to a Python or
signed integer exists. The comparand crosses from Python as an unsigned 32-bit value within
0 < uid < 0xFFFFFFFF (ffi.py:52, :97; val row 167; EV-247). Pid: on the
data channel the pid is only required to be positive (EV-171); the engine package and the sandbox code
contain no pidfd_open, pidfd_getfd, ptrace or nsenter call and read no per-process /proc file except the
engine's own status (EV-235), so no pid lookup can replace the uid. Sentinels: uid 0 and the overflow uid
are rejected even when equal to the expectation (EV-175, EV-176). Namespace: the start-up check refuses
service unless uid_map is the identity map (EV-163, EV-164, EV-165); that the engine's namespace is the
initial one is a deployment premise (val row 256, S13). Preservation rows relied on: T-21, T-23.

## 5 Disposition
**supported under stated premises**
- Premises that must hold: C3's deployment half — the engine runs in the initial user namespace (S13; val
  row 256, a deployment premise with a development-host reading; the start-up check confirms the identity
  map, not the namespace's identity); the kernel at the pinned tag; configuration: all three branches on
  the agent ↔ engine leg. Design-layer and kernel-semantics conclusion with the prototype's checked
  realization; nothing here is a claim about the deployed system.
- Evidence limit: integration run 20261019T011226Z-engine-pool-70000 and sandbox regression
  20261019T010923Z-sandbox-pool-70000 (2026-10-19); root unit cases of commit b262e80e (tests and the
  integration runner only, no engine or sandbox code changed) in run
  20261020T154357Z-engine-extra-evidence-rerun (2026-10-20, same host and kernel, runner as root, senders at
  the uids the rows name), with negative controls by planted transport.c defects in a copy of the engine tree.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). The checks' own limits: the pool uids above 2^31 are exercised on the receive side only — the catalog
  and the spawner were not run with such uids; the pid-lookup cases hand the holder its copy of the agent end
  in the test, and the sender holds CAP_SYS_ADMIN only so that it can name another task's pid; the absence of
  a /proc scan elsewhere in the engine is by text search; the sentinel buffers of the sandbox regression are
  synthetic; the identity map is a development-host reading.
