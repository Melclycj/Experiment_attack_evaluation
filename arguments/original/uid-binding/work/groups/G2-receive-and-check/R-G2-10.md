# R-G2-10 — A's checked frame receives context fields naming a different execution than the row used for comparison.

## 1 What the adversary does
A's checked frame receives context fields naming a different execution than the row used for comparison.

## 2 How it would produce false attribution
- **Preconditions:** the comparison at T-23 is correct against row r's expected_uid, but the constructor at
  T-24 fills execution_id, local_agent_id, session_id, channel_id or receiver_generation from another
  source: a global "current execution", a lookup by local_agent_id (which recurs across executions,
  MM-16), by numeric uid, by fd number, or a stale copy of an earlier Channel's fields. The adversary's
  part is only timing — sending while two executions are live, or around a reuse of a name, uid or fd
  number. Configuration: all three branches under the common abstraction (agent ↔ engine leg).
- **Transitions traversed:** T-23 (comparand read through the Channel) → T-24 (label copied) → T-25
  (carried by reference); T-01 and T-45 as facts for name and uid reuse.
- **Sufficient condition violated:** C-05 p52 (L(a).execution = A_r.execution and L(a).local_agent_id =
  A_r.local_agent_id, with session, channel, lease and epoch from the same record). B(R-G2-10) = D_52
  (q22 by the definition of p52). Why it is a wrong attribution: the bytes were sent by X and compared as
  X, yet the label names another execution, so L(a).execution ≠ Exec(b).

## 3 What stops it
VerifiedContext is built only by receive_step from the Channel's own Session and Execution objects — the
same objects the comparand was read through. Design text (conn at the fourth-revision blob
0c16e567a34aa441): E-02 VerifiedContext (L565) — the immutable VerifiedContext is constructed only by the
receive entry, with the interface receive_step(Channel); L572 — execution_id, local_agent_id, session_id,
channel_id and receiver_generation are the original engine objects, never an agent-reported identity;
L573 — expected_uid comes from the row and sender_uid from the per-fragment verified value; E-01 (L101) —
a new execution under a recurring local_agent_id inherits nothing; L579 — callbacks hold the original
objects and are never re-addressed by fd or request id; L580–582 — no consumer constructs it itself or
looks it up by name, uid, fd or local_agent_id; si L93 — verified_subject is a copy of the
VerifiedContext's fields. The comparand of T-23 is Session.expected_uid reached through the same Channel
object, so the row compared and the row labelled are one object.

Realization in the prototype (commit 3ec67985). receive_step takes the Session from the Channel it was
invoked on, passes that Session's expected_uid to the C reader, and constructs the VerifiedContext from the
same Session (execution_id, local_agent_id, session_id) and Channel (channel_id, receiver_generation)
(EV-172, EV-186, read at receive.py:280–299 on 2026-10-19); a text search finds the construction only
there (EV-183). The Channel → Session link is made only by constructing a new Channel at install and is
cleared only at close step 2 (EV-194); the identifiers are write-once (EV-187) and an execution_id is the
engine epoch joined to a non-wrapping allocation counter, the Session and Channel ids derived from it, one
of each per execution (EV-240). No table is keyed by local_agent_id, the only uid-keyed table is the
allocator's, and fd-keyed handlers are checked by identity before dispatch (EV-196, EV-192). Every verified
record's subject is a copy of the VerifiedContext (EV-183); with the lifecycle's row for the execution_id
replaced by a decoy, the request path still ran on the original objects (EV-197). In the integration run
two parallel executions were attributed to their own rows (EV-188), and a second execution on the same
workspace, uid and fd number was attributed to the second row (EV-189). Preservation rows relied on: T-23,
T-24, T-25.

recurring local_agent_id, recording that each accepted frame's VerifiedContext names its channel's own
execution_id (the parallel case uses distinct names, which the run does not record either way). — not registered (2026-10-19): it names a run not yet made, so there is no observation to check.

## 5 Disposition
**supported under stated premises**
- Premises that must hold: one Channel object per execution installed at T-09 (IG-09, IG-12; realized:
  EV-194, EV-240); the single executor (AA-01); configuration: all three branches on the agent ↔ engine leg. Design-layer conclusion
  with the prototype's checked realization; nothing here is a claim about the deployed system.
- Evidence limit: integration run 20261019T011226Z-engine-pool-70000 (2026-10-19). Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). The checks' own
  limits: the single construction and the absent lookups are by code reading and text search; the decoy
  check replaces only the execution_id key and runs up to the stub handlers (BUILD-PLAN asks for a re-check
  for each real connector).

## 6 What remains
- Residual and open questions: MM-16 — resolved in 01 v9: local_agent_id is written once at row creation
  and no consumer looks it up or keys state by it; the prototype has no table keyed by it (EV-196); a lookup
  by the recurring name after reuse is selector q30, now a departure from that text, and belongs to R-GX-05
  (G3 + G4); MM-15 — resolved in 01 v9 as one receiver_generation per Channel, write-once in the prototype
  (EV-187); an association that is wrong for a reason outside installation, control correlation or alias is
  R-GX-06.
- Design obligations surfaced for the engine: keep every label field taken from the Channel object
  receive_step was invoked on; re-check the by-reference property for each real connector that replaces a
  stub.
- Cross-references: R-G2-08 (row rewrite by the observed value), R-G1-03 (wrong initial correspondence,
  G1), R-GX-05, R-GX-06. Obligations #2 and #6.
