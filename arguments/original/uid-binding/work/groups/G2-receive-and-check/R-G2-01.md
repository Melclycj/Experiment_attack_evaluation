# R-G2-01 — A feeds a read path without a current normal-stream credential witness and it produces a sender label anyway.

## 1 What the adversary does
A feeds a read path without a current normal-stream credential witness and it produces a sender label anyway.

## 2 How it would produce false attribution
- **Preconditions:** the adversary is any task of P_X after T-11 holding fd 3 (A-01, A-02, A-05). The route
  needs either an engine read path that consumes bytes without the per-read SCM_CREDENTIALS witness — read,
  recv, stdio, MSG_PEEK, MSG_WAITALL, a second reader on the same channel, or any API that drops ancillary —
  and a constructor that still emits a label for them (selector q03), or the T-24 constructor emitting a
  subject for bytes with no normal-stream origin at all (q02: a label built from a W2BP FAIL record arriving
  after exec, an empty frame, or bytes the trace does not contain). Configuration: all three branches
  (C-LS / C-LP / C-R) under the common abstraction of the frozen revision — the route lives on the
  agent ↔ engine leg, which the three branches share.
- **Transitions traversed:** T-20 (a send, when there is one) → T-21 (the read) → T-24 (the constructor);
  T-64 for the alternate write paths, which do not help the adversary because they stamp alike.
- **Sufficient condition violated:** C-01 — p11 (Bytes(a) is a nonempty normal-stream sequence from actual
  send events) or p12 (every byte has a current recvmsg witness).
  B(R-G2-01) = (D_11 ∧ ¬q01 ∧ q02) ∨ (D_12 ∧ q03). Why the violation is a wrong attribution: a label
  emitted for bytes with no witnessed origin has no sender for the label's execution to equal, so P_acc's
  "actual send origins" clause fails; a byte read without its witness was never compared, so its Exec is
  unconstrained by the row's label.

## 3 What stops it
T-21's single recvmsg read path and T-24's constructor, which labels only bytes that passed T-23, cut the
route at the read and at the constructor. Design text (conn at the fourth-revision blob 0c16e567a34aa441):
E-02 receive steps 1–2 (L453–458) — one non-blocking recvmsg per step, sized to the remaining header or
body length, with a fresh msghdr and a control buffer of at least CMSG_SPACE(ucred), under
MSG_CMSG_CLOEXEC; read / recv / stdio, MSG_PEEK, MSG_WAITALL, the urgent/OOB entry and a second reader are
forbidden on the channel, and POLLPRI/OOB triggers close; step 4 (L462–464) — only a fragment that passed
the per-fragment check enters the header or body buffer; step 5 (L465–468) — an unfinished or rejected
frame yields no subject event; E-02 VerifiedContext (L565–566) — receive_step is the only constructor and
NeedMore keeps a bounded FrameReader without reaching admission; the wire definition (L430–431) — a W2BP
FAIL after exec becomes an oversize length and closes the channel, never JSON or a success fact.

Realization in the prototype (commit 3ec67985; the C reader as changed by commit 7b4ab727, EV-265). The data channel's bytes reach Python only through
receive_step → the Channel's FrameReader → Native.frame_receive → w2_frame_receive, whose one recvmsg is
in w2_recv_credential (transport.c:154) with the flags MSG_CMSG_CLOEXEC and MSG_DONTWAIT only; receive_step
has one caller (EV-169, read at the cited lines on 2026-10-19), and no Python read call on a socket exists
in the package (EV-170). Every positive return passes w2_ancillary before it is counted, the length is
decoded only from four counted header bytes, a zero or oversize length is rejected, and any failure kills
the reader (EV-171 for the comparison and the counted header, which hold at 7b4ab727, EV-265; the zero,
oversize, rights and urgent frame cases pass after the change, EV-270); a POLLPRI byte kills the reader and the row is ended with receive_rejected (EV-171,
EV-182). VerifiedContext is constructed once, after the whole frame, the strict parse and the phase rule
(EV-172, EV-183). An exec failure after COMMIT ended the row with receive_rejected and no message accepted
(EV-211). Preservation rows relied on: T-21 and T-24 in this group's preservation file.

The defence never depended on the C-side body parse. At commit 3ec67985 the C reader parsed each body with
jansson only after every fragment had passed the comparison and discarded the result (04 §2, version 9
paragraph); the cut — one witnessed read path, bytes counted only after the comparison, one constructor —
lies before that parse. Commit 7b4ab727 removed it: the C reader now hands the credential-checked body over
unchanged (EV-265, EV-266, EV-270), the strict parse is the Python one in receive_step, and a malformed
body from the expected uid still ends the row with no subject, now with close_reason protocol_error instead
of receive_rejected (EV-272). This route's cut therefore does not rest on the parser classification
referred to the user under CR-S4-07: jansson no longer runs on the frame body, CPython's json runs only on
bytes already compared, and a parse failure yields no subject; a memory error inside a parser is R-G2-11's
case, not this one.

**Composition:** conjunction of three items, each now realized and checked. (1) A witness per read: the
kernel supplies a credential only with a control buffer and credential passing armed (EV-14 [R]; EV-34
[S] realized — every recvmsg has its own control buffer, EV-237 [R], and the engine end has SO_PASSCRED
before clone, as R-G2-03 records). (2) One read path: EV-78 [S] realized by EV-169 [R] and EV-170 [M]; the
forbidden flags are absent from the one call (EV-169), and POLLPRI ends the row (EV-171 [R], EV-182 [M]).
(3) One constructor that labels only checked bytes: EV-171 [R], EV-172 [R], EV-183 [M], the exec-failure
case EV-211 [M], the changed reader EV-265 [R], EV-266 and EV-270 [M], and the malformed-body outcome

measured items are component tests and fault cases; no recorded run drove this route's whole composition

## 5 Disposition
**supported under stated premises**
- Premises that must hold: the kernel at the pinned tag (AA-02); configuration: all three branches on the agent ↔ engine leg. This
  is a design-layer and kernel-semantics conclusion with the prototype's checked realization; nothing here
  is a claim about the deployed system.
- Evidence limit (configuration, substrate, run dates): integration run 20261019T011226Z-engine-pool-70000 and its rerun after the change
  20261019T025203Z-engine-no-c-parse-rerun, sandbox regression 20261019T024756Z-sandbox-no-c-parse and fuzz
  runs 20261018T231525Z-fuzz-transport-oracles (before the change) and 20261019T025332Z-fuzz-no-c-parse
  (after it), 2026-10-18 / 19. The engine-side read path does not depend on the production allow-set S2.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). The checks' own limits: the single-path property is by code reading and a text-search test; the fuzz
  leaves the EOF, deadline and reader-rebinding branches to unit tests and code reading; the Python JSON
  parse of the copied body, now the only body parse, is not fuzzed (it runs only after the bytes passed the
  comparison).

## 6 What remains
- Residual and open questions: an alternate read API admitted by a future production ABI would need its own
  witness check (the asynchronous-submission note of 02 U-01 applies to reads as well as sends); the
  remainder of the C-01 cells outside the named mechanisms is R-G2-11.
- Design obligations surfaced for the engine: keep the single read path a property of the code structure
  (EV-169, EV-170) when real connectors replace the stubs; at T-24, receive_step stays the only producer of
  VerifiedContext.
- Cross-references: R-G2-02 (unchecked bytes inside a checked frame), R-G2-03 (truncated or missing
  ancillary), R-G2-11 (the C-01 remainder), R-G3-01 (an alternate constructor, G3), R-G1-01 (credential
  passing never armed, G1). Obligation #2 (channel-to-agent binding); condition C4.
