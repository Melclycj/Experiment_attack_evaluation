## Findings

### F-01 — W2-LW-finish's successor is refused at spawn admission (Q3, Q2) — P1

- **Where:** conn 104 (terminal record still holds uid and lease) against rr 541–543 (WorkspaceLease
  re-grant), rr 581–582 and 650–652 (uid re-lease on CLOSED AND empty; "runtime 未释放可晚于 uid"),
  conn 97–98 and 832–836; si 703.
- **Defect:** The spawner now counts a reaped record whose RuntimeCopy is not yet released as holding its
  uid, while the engine frees the uid lease and re-grants the WorkspaceLease on CLOSED + empty alone; the
  workspace's uid is static, and GC starts only after reap — the same fact that frees the uid — so the
  successor of W2-LW-finish reserves the same uid and its spawn reaches the spawner while the old copy is
  still being deleted. The spawn is refused (spawn_failed + never_created), the new row closes, and no
  sentence makes the engine or the trusted entry wait for the old execution's runtime_status released (si
  703 describes that order, nothing enforces it), so on the written normal path the restart fails rather
  than merely being slower.
- **What would resolve it:** one gate — a workspace's uid (or its WorkspaceLease) is re-leased only after
  the previous execution's RuntimeCopyView = released — or define the refusal as retryable and have the
  trusted entry wait for that release.

### F-02 — the tool definitions have no home in the catalog the design names (Q4) — P2

- **Where:** rr 372–376; si 256–257, 412–414, 504, 545–546, 613–615.
- **Defect:** E-07 and the Pi bridge say the tool definitions (name, description ≤4KiB, input_schema
  ≤8KiB) come from the RuntimeDescriptor/LaunchPlan static registry, but neither object's schema has such a
  field — the only tool data in the registry is a name list in the agent-side adapter config — while the six
  Pi tools' descriptions and schemas are generated at runtime by the SDK's `create*ToolDefinition` inside
  the sandbox. An implementer cannot build `tools`, or the connector's declared-name set used by the format
  check, from the written catalog, and if an engine-side copy is added nothing requires it to equal the
  schema the adapter validates against.
- **What would resolve it:** add a tool-definition field (or a referenced artefact with digest) to the
  engine-loaded registry and require the adapter's definitions to be byte-identical to it, checked at
  adapter start-up.

### F-03 — "the connector attaches the tools" vs the single freeze point (Q4, Q2) — P2

- **Where:** rr 357 and 375–376 against rr 230, 243–248, 271–274.
- **Defect:** E-07 says the connector attaches the tool set to the outbound request "按 profile", whereas
  E-06 makes `freeze_operation` the only serialization entry, has body_hash/argument_hash cover the frozen
  body, and forbids `start` from serializing again; CandidateOperation carries no reference to the
  execution's tool set. Read literally, attaching in the connector puts bytes on the wire that body_hash,
  pre_egress and the local CRA-F32 scheme never saw; read the other way, freeze must reach the tool set
  through a path the design does not name.
- **What would resolve it:** state that `freeze_operation` includes the tool set, reached through the
  request's Session → Execution → LaunchPlan by reference, and that the connector only sends the frozen
  bytes.

### F-04 — the input limits no longer add up (Q4, Q3) — P2

- **Where:** rr 95, 245, 357, 375, 826; si 551–555.
- **Defect:** The agent-side limits (messages text ≤48KiB, tool_calls arguments in history counted
  nowhere, request frame ≤64KiB) plus the engine-attached tool set (≤32KiB) can exceed the frozen outbound
  body cap of 64KiB (E-06, E-08), and ModelDescriptor/Grant `max_input_bytes` no longer says what it
  measures. A request that passes the adapter's own budget check (the adapter cannot see the engine's
  tool-set size) can then fail at prepare with an engine error instead of Pi's context_budget, which
  W2-LW-followup's retained history makes likely.
- **What would resolve it:** define max_input_bytes over the whole outbound body (messages + history
  tool_calls + tools), give the adapter the tool-set byte size, and size the body cap or the 48/32KiB
  limits so the sum fits.

### F-05 — returned tool calls escape the completion evidence and the flow record (Q4) — P2

- **Where:** rr 464, 466–469, 472–473; si 98, 120, 129–131.
- **Defect:** CompletionEvidence's output_digest/output_bytes cover only streamed text and post_read flow
  events are emitted only per Chunk, so tool_calls — up to 32KiB of model output delivered to the execution
  in the Complete value — leave neither a digest nor a flow event. That contradicts E-09's rule that a
  required observation is not bypassed for data reaching the agent, and makes a tool-call turn's record
  indistinguishable from an empty reply.
- **What would resolve it:** include the serialized tool_calls in the evidence digest (or a separate
  field) and emit a post_read-equivalent flow event for the Complete value.

### F-10 — "Python stdlib json" without configuration breaks the strict-parse rules (Q2) — P2

- **Where:** conn 463 against conn 444–446 (step 5) and 484.
- **Defect:** `json.loads` accepts NaN/Infinity, keeps the last of duplicate keys, accepts lone-surrogate
  escapes, auto-detects UTF-16/32 when given bytes, and bounds neither integers to ±(2^53−1) nor depth to
  16 — all forbidden by step 5. Naming the stdlib parser without its configuration lets a plain
  `json.loads(body)` satisfy the new sentence while violating the old ones.
- **What would resolve it:** specify strict UTF-8 decode first, an object_pairs_hook rejecting duplicates,
  a parse_constant rejecting NaN/Infinity, a surrogate check, and post-parse depth/node/integer checks.

### F-11 — a reap-stage spawn_failed after an earlier spawn_failed is undefined (Q1, Q2) — P2

- **Where:** conn 106–107 against conn 132, 151–152, 192.
- **Defect:** The control table defines spawn_failed as "标明启动失败", keeps one spawn_failed intent per
  record, and its duplicate rule covers only semantically equal terminals; a record that already sent a
  startup spawn_failed after clone (e.g. stage=exec) and then hits a wait error sends a second, different

- **What would resolve it:** state that a stage=reap spawn_failed may follow an earlier spawn_failed for

## Q3 — the seven workloads under the stricter reading

- **W2-LW-start:** reservation (write-once) → spawn → bootstrap with re-read → prepared → install (link,
  generation) → COMMIT → hello/welcome → task_start → model.generate (parse + admit in one decision →
  prepare → authorize → dispatch → SSE → Complete). Completes once the tool-definition source is written
  (F-02, F-03); needs deployment inputs (provider, a tool-calling chat template / `--jinja` for llama-server).
- **W2-LW-files / W2-LW-exec:** workspace tools run in the sandbox; up to eight calls per turn come back in
  Complete and Pi runs them serially. Completes; history size bounded by F-04.
- **W2-LW-resource:** w2_read_document issues a new document.read through the receive pipeline, admission
  and E-06. Completes.
- **W2-LW-followup:** same execution, grant and TaskBinding; no-inheritance, close and lease rules are not
  on its path; parse + admit in one decision changes nothing. Completes if the approved small task fits the
  fixed 64KiB frame / 48KiB history (pre-existing limit) and the outbound body cap (F-04) — needs fixture
  sizing, not a design change.
- **W2-LW-parallel:** distinct workspaces have distinct static uids, so a terminal record awaiting storage
  release holds only its own uid; capacity is bounded by 16 execution slots, 16 spawner records (terminal
  records included), 16 ProviderLeases, and the storage profile, which guarantees only two concurrent copies
  (`max_reserved_bytes ≥ 2*max(B)`, si 304) — a deployment input to size for N. Completes; the one stricter
  reading that can stop it is the stop-for-unknown fault, which is a failure path (F-12).
- **W2-LW-finish:** old session closes (finish → DRAINING → bye → close steps 1–4 → stop → reap → empty →
  step 6). The successor cannot complete on the written immediate path: the engine frees the uid and the
  WorkspaceLease before the old copy's release and the spawner refuses the same uid until then (F-01).
  With a wait for runtime_status released it would complete, slower.

## Gate

**May not pass** for starting the engine build on this design: F-01 is a contradiction inside build step 1
(lifecycle and uid lease) — the engine's re-lease rule and the spawner's stricter admission make the
approved W2-LW-finish restart fail — and F-14 means the plan as written would build the readings the
revision rejected. Both are short fixes (one gate sentence in conn/rr; two entries in BUILD-PLAN §1 and its
step-1 checks); with them in, the remaining P2s on native tool calling (F-02–F-05) do not block build steps
1–3, since the model connector is a stub, but must be settled before a real connector is built.
