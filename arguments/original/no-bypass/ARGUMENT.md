# 1.1 不可绕过 — 论证方法说明

## 0 本文件

- **用途。** 说明 1.1 的论证怎样组织、靠什么判官、能声称什么，供人读，也供写论文时解释论证方法。规则在 SPEC（论证规格）、
  TESTING（反向测试与 TLC）与 PLAN（执行与停点），与本文件不一致时以它们为准；共用的方法规则在 METHOD。
- **始终是当前方法的单一完整说明。** 方法改动时，在同一次提交里改到本文件对应的位置，只写现在的做法，不追加"更新"条目；
  改动经过与审核记录在 PLAN §3 与 work/reviews。
- **文中的编号。** "01 §x" 指 01 模型清单；"§4.1""§4.2"等不带文件名的指 SPEC；本文自己的节写"本文 §x"。

## 1 论证的逻辑（主线）

1. **要证明的结论：** 在列出的前提和配置下，engine 没交给 execution 的东西，execution 不经 engine 就拿不到。
   - "配置"包括：基线 v1（固定版本的 engine 代码和 kernel 源码）、诊断白名单里的 74 个系统调用、开发机的宿主读数
     （NB-EV-018、NB-EV-019）。
   - "前提"包括：可信方不受攻击者控制、不作恶，其中只有 hypervisor 与固件、supervisor、离线部署方的正确行为是前提
     （engine、spawner 等影响可达性的代码行为要证，不当前提）；以及部署前提。其中一条专管宿主上的特权进程：凭据能通过对
     execution 任务的 ptrace 访问检查、或持有特权 fanotify 组的宿主进程，不取用、不读写 execution 的私有部分（NB-AA-08，按凭据写的
     保守上界，部署方要列出这些进程逐个核对）。
2. **什么算"拿到了"：** 把 execution 每个动作可能造成的后果逐个拿出来看。合法的后果只有四类：
   - 经 engine 中介完成；
   - 落在交付清单给的权利之内；
   - 只作用于它自己的私有对象（按 §4.1 的完整判据，含"由构造为本 execution 单独创建"的本地环境实例）。宿主不要特权就看得到
     的部分不算私有；可见性还没确定的按看得见处理，两者分开标注（01 §2.6）；
   - 只碰到没人拥有的全局汇总量，比如负载计数。其中只用来推断别人活动的，当作侧信道记录下来，定价或记为未定价；让别人的操作
     变慢或失败的，记为可用性效果。同一类里还有**宿主可观察**：只作用于它自己状态里宿主看得见的部分，比如参数区、comm、任务
     状态，以及 kernel 代它写进宿主日志、取自它自身状态的内容（例如 comm）。它没有拿到任何未交付的对象，所以不是路线；但这些内容可以由它选定，宿主普通进程读得到，是一条不经 engine、通向宿主
     读者的出向通道，作为局限写进结论。

   不属于这四类的后果，就是一条**路线**：一个动作的一个后果，越出了交给它的东西。本地环境只是对象来源，不是第五类。
3. **怎么保证没漏：** agent 对外产生影响只经五族事件：系统调用、用户态指令与内存访问、kernel 代它完成的动作、延迟执行的动作、进程状态变化（依据见本文 §3.2）。
   - 系统调用按白名单逐个列成行；一个调用里分多种操作的，按 kernel 的分派位置拆开，另留一行兜住其余取值。
   - 其余四族的行按追踪规则导出：从每个已纳入模型的事件与沙箱构造的状态出发，加上几个补充入口（用户态能触发的异常向量、kernel
     返回用户态与调度的公共路径、后台线程），跟踪它留下的映射、登记、队列、脏状态与引用，一直追到被处理完、或交给某一列或某一行
     负责为止；新导出的行同样往下追。同一个事件可以从几个入口触发，只立一个主行，各入口记在主行里，主行的分析覆盖所有入口；
     某个入口改变了所用的状态、执行点或后续动作的，另立主行。
   - 列机械导出，不靠手工列举：来自参数的语义（结构体里的字段、嵌套的指针与 fd、子操作都是名字来源）、不带参数时的隐式主体
     （进程组与会话、父进程、keyring、按 uid 计数的资源等）、copy_process 与 execve 保留的继承属性，以及可信方之后会解引用的
     状态（每个这样的可信方一列）（SPEC §4.2 第 2、4 步）。
   - 每一格要么分析，要么写明为什么不适用。

   所以"没漏"有明确含义：相对于这张表是完整的。这张表本身有没有漏行、漏列，由审核一专门审；已知的 namespace 绕过案例在第二块
   开头先归一次分支，矩阵填完后再连同 CCT 的资源与检查种子逐项对照（SPEC §3.4、§4.2 第 5 步）。
4. **用一个不变量把整件事串起来**，它由三句话组成：
   - I1：execution 手里的每个引用，都来自开工时代码实际交给它的东西与沙箱构造的本地环境，或来自它自己在表里有记录的动作；
   - I2：它的私有对象里宿主要特权才碰得到的那部分，只有它自己和名单上的可信方取用、读写得到；宿主上的特权进程不取用、不读写它，
     是前提 NB-AA-08；
   - I3：它产生的每个后果都在四类之内（私有按完整判据判，I2 只是其中持有者一条），否则就是一条被具体机制挡住、或只能借
     排除项实现的路线。
5. **证明分三步：**
   - 初态（第一块）：证明 execve 那一刻三句都成立。逐项核对代码实际交出去的东西、沙箱构造的每一步、继承下来的属性。
   - 保持（第二块）：表里每一格对应一类动作，按主干写定的转换粒度切成一步或几步（一次系统调用可以是几步），证明每一步之后
     三句仍然成立。这一步里有两种工作：
     - **单格事实**：这个动作经这个名字碰得到什么、挡不挡得住。主干 v9 分出 306 个分支，工作量的大头。可测的格以**反向测试**
       为判官（本文 §4）：测试加在保守摘要与源码引用之上，两样都要，一致才算数；不一致时，路线记 open，其余的格记未定，查清
       再定。测不了的格只靠保守摘要与源码引用。
     - **组合逻辑**：所有单格结论，加上 spawner、worker、engine、supervisor 的动作，在各种先后顺序、并发、生命周期下拼起来
       三句是否仍成立。判官是 **TLC**（本文 §5，在第三块运行），在有界实例内代替手写归纳；实例之外的规模与 TLC 没写进模型的转换，
       由各格的干扰义务与组合章论证。
   - 蕴含（第三块）：三句话永远成立，就推出第 1 条的结论。
6. **每条路线的结局四选一**（所有证明单元通用）：
   - 被挡住（机制代码逐行引用；可测的还要有反向测试的实测，两者不一致时记 open、查清再定；组合层面界限之内由 TLC 检查）；
   - 有条件成立，等某项尚未实现的要求；
   - 证据不足，记为 open；
   - 声明在范围外。
7. **结论怎么报：**
   - 全部路线被挡住或声明在外，并且没有"未定"的格：报"在所列前提与配置下不可绕过，相对于 M 完整"，并写明各个版本、
     TLC 的界限与反向测试的覆盖范围。
   - 有 open 或"未定"（只要有一处）：不报性质成立，只报已支持的部分，外加 open 清单。
   - 没有 open 与"未定"、但有带条件的路线：只报带条件的结论，条件逐条列出。
   - 发现的反例单独标记，不与证据不足的 open 混在一起。

   另外附带一份"生产白名单必须满足的条件"清单；宿主可观察一类作为局限列出，已核实可见的与按可见处理的分开；作者抽查的结果
   （样本量与发现的错误数）写进结论。
8. **这个证明不声称的事：** 生产白名单（结论只对诊断白名单成立）、对宿主普通进程保密（宿主可观察一类，及它通向宿主读者的
   出向通道）、真实 connector、kernel 被攻破、跨域硬件读写与宿主原有共享
   硬件上的争用、同一 execution 内部的 subagent、宿主层面的拒绝服务（engine 自己引入的共享写成局限，不在此列）、非 Intel 处理器。

## 3 矩阵

### 3.1 一格里做什么（例：openat × 路径）

| openat 打开的是 | 碰到什么 | 归属 |
|---|---|---|
| /work 下的文件，读写 | 工作区文件 | 交付，权利之内 |
| /runtime 下已有的文件，以写方式 | runtime 副本 | 超出交付权利 → 路线；文件权限与只读挂载两道都挡：不带 O_TRUNC 时文件权限先给 EACCES，带 O_TRUNC 时只读挂载先给 EROFS |
| 宿主 /etc/shadow | 宿主文件 | 没交给它 → 路线；mount namespace、pivot_root、卸载旧根挡住（路径不存在） |
| /proc/self/fd/0 重开 | 宿主 /dev/null | 宿主共享项：有外部效果的按共享汇总（第 4 类）或路线判 |
| /tmp/x | 自己沙箱的临时文件 | 私有，要证别的 execution 碰不到 |

这张表就是保持一步在 openat 这一格的内容："判归属、定结局"和"证明这一步保持三句"是同一份工作，不分先后。1.1 的路线不是
uid 线那种多步攻击链；多步组合（例：在 /work 留符号链接，可信方之后去跟随）在"可信方解引用"列与跨章组合里处理。

**拆开**：靠操作码做不同事的调用（fcntl、prctl、futex、clone、unshare、getsockopt、madvise、arch_prctl），每个操作码各成一行，
因为碰到的对象不同（例：F_GETFL 只读自己 fd 标志，F_SETLEASE 会让别人打开文件时被阻塞）。

### 3.2 为什么是这五族

依据分三层，出处在 hardware-premise-sources 与 unprivileged-instructions：

1. **处理器。** 以处理器按 Intel 64 与 IA-32 架构软件开发者手册（325462-093US）描述的 x86-64 特权与内存保护规则执行为前提
   （SPEC §4.2）。手册列出了全部程序控制转移手段（Vol. 3A §6.8）。其中能从用户态升到 kernel 特权级的，是系统调用指令（SYSCALL、SYSENTER）、
   软中断指令、异常、外部中断，以及经调用门的远调用（Vol. 3A §6.8.4、§7.12.1.2）；手册里没有这样一句穷举，这一条由各节拼出
   （证据记录 §2.2），其中 IRET 不能向更高特权返回一项，证据记录没有引出处。用户态访问内存受分页的权限约束，碰到 kernel 的页
   触发缺页（Vol. 3A §5.6.1、§5.7；证据记录 §2.1 把这一条标为部分支持，例外列在那里）；特权指令与没有权限的 I/O 指令在用户态
   触发异常（Vol. 3A §6.9；Vol. 1 §20.5）。
2. **基线 kernel 的配置。** 每条升级途径都经 kernel 自己配置的结构。基线 v1 上：系统调用入口寄存器只指向 64 位入口与两个 32 位
   兼容入口，后者被过滤器按架构不符杀掉；GDT 与 LDT 里没有调用门；异常向量逐个有去向；没有 FRED、LASS、用户中断，也没有开放
   I/O 权限的系统调用。
3. **不进 kernel 的指令。** 手册 Vol. 2 的 822 个指令页与 Vol. 3 的 43 个逐页落位。多数只碰自己的寄存器与自己映射的内存，或在
   用户态触发异常；读时钟、CPU 号与处理器静态配置的几条只读全机共享的值，归观察信道（01 NB-E-M-04、NB-E-M-08）；在虚拟机里
   直接退到 hypervisor 的，由"hypervisor 与固件的正确行为"这一前提承担；只造成缓存、时序、总线争用的，归 METHOD 规则 2 的跨域
   硬件读写与共享硬件争用排除项。

由此，除下面 PTWRITE 一处外，用户态代码影响自身以外只有两条路：用户态指令读写已映射的内存、或读全机共享的处理器状态；进入 kernel（主动陷入是系统
调用，指令触发的异常是 kernel 代为完成）。PTWRITE 一处是：宿主开启处理器跟踪并允许 PTWRITE 时，用户态指令把数据写进宿主的跟踪记录，
模型里归 01 NB-E-K-14。延迟动作与进程状态变化的起因都在前三族或构造初态（例如继承的 RLIMIT_CPU），后果发生在之后，单列是因为逐个看系统调用时
最容易漏；它们由 kernel 源码的追踪规则导出（本文 §1 第 3 条）。排除的只有 METHOD 规则 2 的四类。这三层只读手册与源码，没有在机器上
实测；结论只对 Intel 处理器写定。

五族是分类，不是来源：同一个事件可以从几个 kernel 入口触发（例如父进程收到通知，既可以来自正常退出，也可以来自被杀），
一个入口的后续动作也可以落在别的族。所以"没漏"不靠"每族一个入口"，而靠本文 §1 第 3 条的追踪规则。依据是五族来源的结构核查
（记录）。

### 3.3 规模（主干 v9，2026-10-27）

系统调用 45 行（74 个调用），其中 8 个多路复用的调用拆成 87 个子操作行（含 8 行"其余取值"）；其余四族 39 个主行，构造与生命周期
16 行；列 13 个（8 个命名域列，加 5 个可信方列）。分支表共 306 个分支，另有 97 个不适用项与 13 条列的不适用规则（02 §3.3–§3.6）。

## 4 反向测试

- **是什么**：在沙箱里实际去做一个动作，观察 kernel 的真实反应。判官是 kernel 的实际行为，不是读源码的推断。它是验证，不是
  攻击：对象是本机上、由本次运行从固定版本编出的沙箱；测试只确认越权的尝试被挡住；目标是本次运行自建的诱饵，不碰真实的敏感
  对象；不研究、也不记录任何绕过方法。
- **能证明什么**：具体输入下"碰不到"（被拦下）或"碰到的正是交给它的那个"。把单格结论从推断变成实测。推广到整类（例：几条
  宿主路径代表"所有宿主路径"）要有以源码为据的论证，推广不了的部分记 open。
- **不能证明什么**：列没列全；没测到的参数；组合与竞态（交给 TLC 与生命周期章）；宿主范围内的私有性（两个沙箱互看只查别的
  execution 碰不碰得到，不查宿主进程，也不验证前提 NB-AA-08）。
- **哪些格要测**：

  | 后果的性质 | 例 | 测不测 |
  |---|---|---|
  | 只碰自己 | 取自己的 pid、改自己的内存保护 | 不测，按源码判；保守摘要里有延迟或外部效果的不能免测 |
  | 路线（声称碰不到） | 打开宿主上的诱饵文件、写 /runtime、向诱饵进程发信号 | 反向测试：去做，观察被拦下；声明在范围外与有条件成立的路线不声称被挡住，不测 |
  | 类别边界（声称碰到的正是交给它的、且只到那里） | 写 /work 能成；/tmp 别的沙箱看不见 | 做一次再核对对象身份（fstat 的设备号与 inode、挂载信息）；私有类用两个沙箱互看 |
  | 只经共享汇总（声称没有作用到具体对象，例如在宿主共享的设备上） | /proc/self/fd/0 确实是宿主 /dev/null | 对象身份测试，支持第 4 类的归类 |
  | 宿主可观察（声称作用到的只是它自己的状态，或 kernel 代它写进日志、取自它自身状态的内容） | 宿主读到它的参数区 | 对象身份测试，核对宿主读到的是这个 execution 自己的条目 |

  按记录取值逐行的完整义务表在 TESTING。
- **每个测试事先写什么**：
  - 判据：三种结果各是什么观察——预期的机制挡住；成功；其余结果（别的机制挡住、准备或观察失败）记不确定，查清再定。
  - 目标：目标存在，并核对它的身份。
  - 对照：路线测试配正对照（同一个探针去碰一个按设计够得着的对应物，必须成功）；边界测试配负对照（越出权利的一侧必须失败）。
  - 事后核对：路线测试在效果可能发生的窗口过后，从沙箱外核对被禁止的效果没有发生；边界测试核对改变只落在交付对象上。
  - 对照不成立、准备失败、超时或观察不足，都不算实测证据。
- **为什么不做单项消融**：检验测试本身是否查得出错，一种办法是去掉一个机制、看测试结果是否随之改变。在 1.1 已分析的实例里，
  去掉一个机制，要么被别的机制兜住，要么构造失败、沙箱不启动；目前只确认一道机制的，去掉之后会怎样，本文不预判。所以没有统一的
  "去掉就翻转"可作判据。
  - 被别的机制兜住：同一条路线常被不止一道机制挡住。以写方式打开 /runtime 已有的文件，文件权限（副本属 root，文件 0444 或
    0555）与只读挂载两道都挡：不带 O_TRUNC 时文件权限先给 EACCES，带 O_TRUNC 时只读挂载先给 EROFS。白名单之外的特权调用，
    seccomp 的默认动作与 capability 检查都返回 EPERM。网络与 SysV IPC，诊断白名单里没有 socket 与 SysV 调用，bind、connect 固定
    禁止，net、ipc namespace 是第二道。去掉其中一道，路线仍被挡住；去掉的若是 kernel 路径上先触发的那一道，观察换成后一道的
    （例如 EACCES 变成 EROFS），按 TESTING 的判据记不确定。这时消融只说明还有后备，说明不了测试本身是否有效。
  - 构造失败、沙箱不启动：构造中任何一步执行失败，沙箱都不启动，agent 代码一行都不运行（每步失败即中止，engine 回归在各步注入
    失败）。互相依赖的有两对：不卸载旧根，下一步删旧根目录就失败；不设 no_new_privs，降权之后 seccomp 过滤器装不上。其余步骤
    （例如只读重挂、proc 只留进程目录、关闭多余的 fd）去掉之后沙箱照样启动。初态分析逐步核对失败后的状态。
  - 目前只确认一道机制的：例如 clone 与 unshare 的 CLONE_NEWUSER 标志由 seccomp 拦下；白名单之内的特权操作（setuid(0)、不带
    CLONE_NEWUSER 的 unshare 建其他 namespace）首先由 capability 检查拦下，其后的检查是否另成一道还没有排除（例如 setuid 在
    capability 检查之后还有安全钩子）。这类路线有多少，由第三块的纵深统计给出。

  所以测试本身是否有效，靠每个测试的对照与判据，不靠消融。错误码相同的（例如上面的 EPERM），观察本身分不出是哪一道，由 [R]
  写明 kernel 路径上先触发的那一道；实测证明的是被挡住。哪些路线被几道机制挡住，作为纵深防护的分布在第三块汇总（PLAN §1.1）。
  上面各实例在基线快照里的源码位置，列在 reconcile"2026-10-27 写回的定向复核修改"一段。
- **怎样组织**：按"挡住它的机制"成组，每组一张尝试清单（表驱动）。这是**测试的组织方式（事后分类），不是完整性的推导**；
  要测什么由矩阵决定，矩阵找到的每条路线再归到挡住它的机制那一组，归不进的就新开一组，所以分组不限制覆盖。

  | 机制 | 挡住什么 | 一组测试 |
  |---|---|---|
  | 文件视图（mount namespace、pivot_root、挂载标志） | 宿主路径、只读区域的写 | 宿主路径表 × 所有取路径的调用 |
  | pid namespace | 别的进程 | 宿主 pid 表 × kill、wait4、prlimit64、F_SETOWN 等 |
  | net namespace + seccomp 禁网络调用 | 网络 | 各种网络调用 |
  | ipc namespace | 共享内存、消息队列 | 相关调用 |
  | seccomp 过滤器 | 白名单外的调用与被禁标志 | 调用与标志表 |
  | 无 capability、no_new_privs | 特权操作 | 特权操作表 |
  | 文件权限 | 别人的文件 | 权限表 |

  另加三组边界测试：交付权利两侧、两个沙箱间的私有性、宿主共享设备的身份。
- **怎样运行**：沿用 engine 现有回归的做法：从基线 v1 的快照编出沙箱程序，以 root 在 WSL 的私有 mount namespace 里运行，新建
  两个 256 MiB 镜像、mkfs.btrfs 后 loop 挂载作部署根与工作区存储（engine 要求它们在 btrfs 上）。每次运行先核对 kernel 版本与
  登记的宿主读数；测试目标一律是本次运行自建的诱饵，只能拿真实敏感对象来测的路线不测、按源码判；时间、内存、进程数与输出都有上限；结束或出错都按固定顺序清理并核对。
  每批由用户说"开始"。会影响宿主的测试（内存耗尽、全机写回压力）不做。完整规则在 TESTING；试跑（NB-EV-020）确认了这套
  做法可行。
- **规模与代价（推断）**：约 200–400 个用例、20–40 组，形状同 engine 现有 172 个回归用例；约 3–6 次工作会话加审核。

## 5 TLC

- **三个名字**：TLA+ 是规约语言（写状态、每步怎么变、什么永远成立）；TLC 是它的模型检查器，把模型代入一个有限规模，从初态
  出发走遍所有能到达的状态，每个状态检查不变量；TLAPS 是证明系统，由后端证明器逐步核对，对任意规模成立（暂不做）。
- **界限**：模型本身可写成任意多个；TLC 每次只查一个具体实例——两个 execution，其中一个有后继（同一工作区的后继 execution
  与 engine 的 epoch 更换都包含在内），有限个对象与引用；在这个实例内检查所有动作的先后顺序（所有交错）。实例之外的规模，
  TLC 的结论不说明，由组合章论证。运行上限：最长 10 分钟、堆 2 GiB、状态目录 1 GiB，碰到上限记为不确定。
- **模型写什么**：只写和 1.1 有关的状态——每个 execution 握着哪些引用、每个对象归谁（交付、本地独占、宿主共享、别的
  execution、宿主）、登记了哪些延迟动作、epoch 与 uid 分配。动作按类抽象，每条动作规则从相应各格的保守摘要写，不从格的结论写
  （例："打开"只会加一个指向自身视图里对象的引用；"经通道传 fd"把引用移给 engine，engine 关闭；"退出"触发已登记的延迟写；
  "回收"；"构造后继"可能复用 uid）；动作粒度按主干写定的转换粒度。可信方的动作写会移动引用的那几个，其余相关转换（例如
  可信方后来解引用的 symlink、锁与租约）逐个写明去处：写进模型、证明不影响后省略，或交给具名的剩余论证。对象按种类各取一个
  代表，可以互换的理由写进 run-spec，所以状态空间小。
- **粒度**：在引用、归属、登记、生命周期这几个维度上细，其余维度粗。两个动作组合出的新结果，只要相关动作已写进模型、能表达成
  这几个维度上的状态变化，并且落在所运行的实例之内，TLC 就会在交错里查到；依赖更细的 kernel 语义的组合（文件内容、时序信道）不在模型里，交给单格与测试或组合章的
  论证。"不在模型里"不等于在范围外，排除只用 METHOD 规则 2 的四类。
- **反例怎么处理**：只有读源码能说明那一步在任何输入下都不会发生，才当模型错误改掉，改掉的只是抽象多出来的行为；测试只作
  旁证。否则反例转成一条路线，查清之前记 open。
- **能查出什么**：漏掉的先后顺序、引用传递链（clone、exec、经通道传 fd）、回收与删副本的顺序、跨 epoch 的残留引用与 uid 复用。
- **查不了什么**：每条抽象规则是否忠于 kernel 与 engine（靠测试与读源码）；列没列全（靠表与审核一）；模型里的不变量是否足以
  推出 §4.1 的性质（靠人审与蕴含论证，审核三核对）。TLC 只查 I1–I3 在界限内的可达状态上成立，不给出"I 推出性质"的一般论证；
  这里也不要求 I3 与性质相等，I 可以比性质强。模型只有引用、归属、登记、生命周期这几个维度，I 在模型里最多承载 §4.1 在这些维度
  上的部分；其余部分（例如私有判据里"生命周期内作用不到"与"没有外部对象效果"两条、文件内容与时序）由各格承担，蕴含论证把
  两者合起来。
- **代价（推断）**：模型约 300–600 行，1–3 次会话写和调试，加审核。TLAPS 以周计，AI 辅助先例少，暂不做。

## 6 两个判官在 1.1 中的贡献

| 层 | 只靠文字推理时 | 加测试之后 | 加 TLC 之后 | 仍然靠论证 |
|---|---|---|---|---|
| 单格事实（碰不碰得到） | AI 读源码，AI 互审 | kernel 的实际行为；抓出读错的 kernel 语义、配置间的相互影响 | 不变 | 推广到整类的论证（以源码为据） |
| 组合逻辑 | 手写归纳，AI 互审 | 不变 | 工具在界限内查全部交错；抓出漏掉的先后顺序、引用传递链、回收顺序问题 | 界限之外的规模；没写进模型的转换；模型维度之外的效果（文件内容、时序） |
| 列没列全 | 表、检查脚本、审核一 | 不变 | 不变 | 是 |
| TLC 模型是否忠于代码 | — | 测试覆盖一部分 | — | 其余部分 |

**为什么要做（先例）**：本次检索到的、顶会里用 AI 做安全分析或证明的先例，都有一个"不是大模型"的判官——证明器、验证器、真实运行或人工
确认；判官和被判都是大模型的做法没找到先例（10 次检索的范围内），而 IEEE S&P 2024 有论文指出大模型的安全推理理由常不忠实。
已核实会议与年份的先例：Baldur（ESEC/FSE 2023）、Lemur（ICLR 2024）、Selene（ACL 2024，seL4 引理）、AutoVerus（OOPSLA 2025）、
PropertyGPT（NDSS 2025）、KernelGPT（ASPLOS 2025）、LLift（OOPSLA 2024）、IRIS（ICLR 2025）；反面：Ullah 等（IEEE S&P 2024，
DOI 10.1109/sp54263.2024.00210）。写进论文前按 research 规则逐条再核原文。

方法细节另有两处来源：
- **已知案例对照**（SPEC §3.4）学两个先例：Provos、Friedl、Honeyman（USENIX Security 2003）§5 用过去报告过的安全问题分析权限分离
  会有什么影响；Nelson 等的 Hyperkernel（SOSP 2017）§6.1 图 7 对 xv6 在 2016 年 1 月至 2017 年 7 月修掉的缺陷（排除两个不适用的锁缺陷后
  共 8 个）逐条人工判断能否防住，是对照，不是重放执行。两篇拿历史案例说明"会被挡住"，1.1 改作覆盖检查，只看案例有没有落到格里，不当路线被挡住的证据。N1–N10 的部分结论已经
  进了设计文本，又经 S1 转写进 01，对这些条目对照查到的比独立来源少。
- **"不变量推出性质，不要求二者相等"**（本文 §5）与 Hyperkernel §2.2、§2.4 的写法一致：状态机规约之外另写声明式性质，由验证器检查前者
  满足后者。1.1 里这一步由人审与蕴含论证承担（性质公式 P 若采用，TLC 也只在界限内查）。

**强度声明（草稿）**：本文给出的是结构化安全论证，不是机器检查的证明；范围是有版本的模型 M；完整性只说相对于 M；前提写明，
其中包括宿主特权进程不取用、不读写 execution 私有部分的部署前提（NB-AA-08）；逐格分析由 LLM 在固定方法下起草；可测的单格事实以反向测试

**依赖与限度**：结论依赖这些工具在各自职责内正确工作：基线快照与版本核验（baseline.py，含 kernel 文件的导出）；反向测试的
