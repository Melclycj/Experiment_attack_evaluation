## 2 New findings introduced by `c0aef66b`

### M-01 — the per-message 64-byte allowance can be read as the only wrapper allowance, and it does not cover mapped tool-call wrappers — P2

- **Where:** rr 378 and si 557–558, against rr 359 (args form `tool_calls:[{id,name,arguments}]`, no per-message count limit) and rr 408–409 (mapped form `{id,type:"function",function:{name,arguments}}`).
- **Defect:** "messages 按映射后形式计（历史 tool_calls 的 arguments 按编码成 JSON 字符串后的长度，每条消息另计 64 bytes 固定开销）" reads either as "serialize the full mapped messages exactly, plus 64 bytes of margin" or as "serialize the E-07 form, substitute the encoded argument length, and add 64 bytes per message for the mapping". si 557–558 omits the "messages 按映射后形式" clause and supports the second reading. Under the second reading each mapped call adds about 31 bytes (`"type":"function","function":{` and `}`), and each text message adds 3 for text → content. An assistant message with 8 calls is about 250 bytes over its 64-byte allowance, and 20 such messages exceed the 1 KiB fixed-field slack, so an adapter-passing request can again be rejected at prepare.
- **What would resolve it:** state in both places that the adapter serializes the complete mapped messages array exactly as rr 407–409 maps it (the 64 bytes being margin), or replace the 64-byte rule with a per-message plus per-tool-call allowance that bounds the wrapper. One clause in si 414 could also say tool_set_bytes is measured on the mapped `tools` array.

### M-02 — ereq's summary of the absorbed musts still says every kill or wait error is reported as spawn_failed — P3

- **Where:** ereq 38–39 (header: "a kill or wait error reported as `spawn_failed` with stage reap") and ereq 195, against conn 123–126.
- **Defect:** conn now excepts the kill error that follows an earlier spawn_failed: no record is sent, and quarantine comes from the stop deadline. The ereq header was not touched and states the rule without the exception. The must at ereq 195 (name the record that carries the error, as the precondition of quarantine) is still met in purpose, but the header's description of what the design states is now incomplete.
- **What would resolve it:** one clause in the ereq header, for example "except a kill error after an earlier spawn_failed, quarantined by the stop deadline (conn E-01)".

### M-03 — the re-read now also runs in the engine's and the file worker's drops, but neither the design nor the check states that case's outcome — P3

- **Where:** BP 13–14 and 80–83, against conn 127–128 and optb step 11 (bootstrap only).
- **Defect:** BP places the re-read in the shared `w2_drop`, so the engine process (`cell.c`) and the storage file worker (`storage.c`, drop to 0) run it too. The design files describe it only for bootstrap step 11, and the negative check lists one expected outcome for both injection cases ("FAIL(stage=uid)、无 SEALED、无 prepared，spawn_failed 与 execution_empty"), which fits only the bootstrap case. A failed file-worker drop marks the worker unhealthy and has no SEALED or prepared stage. The existing mechanism also scopes the worker's fault points as `worker.drop.…`, so the point there is not literally `uid.reread`. Both behaviours are fail-closed.
- **What would resolve it:** in BP, give the file-worker case its own expected observation (worker unhealthy, store not admitted or control_ready not sent, whichever the code does) and its scoped point name. Optionally, add one clause to conn E-01 saying the re-read is in the shared drop and fails engine start or worker health.

### M-05 — "integer" is type-based on the engine side and unspecified on the Node side, so an integral number in exponent form passes one and may fail the other — P3

- **Where:** rr 380 ("整数限 ±(2^53−1)…同 E-02") with conn 491 (Python post-check on parsed integers), against si 460 (Node rejects "非安全整数").
- **Defect:** a model argument such as `1e20` parses in Python as a finite float, so it passes the engine's new integer and finiteness check and is re-serialized as `1e+20`. If the Node receiver reads "非安全整数" by value, `Number.isInteger(1e20) && !Number.isSafeInteger(1e20)` holds, and it closes the whole execution instead of returning a tool error. This is the N-04 failure mode for a narrower input class, and it is bounded to one execution.
- **What would resolve it:** define "integer" lexically at both ends (a JSON number token without fraction or exponent), or have the connector also reject integral-valued floats of magnitude above 2^53−1.

### M-06 — two older sentences still state the full per-fragment values without the first-build pointer — P3

- **Where:** conn 447 (FrameReader holds "frame_started_at、共同 uid 与诊断 pid 摘要") and conn 468 (received_at "取首个通过校验的头字节时间"), against conn 491–493.

- **What would resolve it:** add the same "（首版取值见接收侧补充）" pointer at conn 468, and "（首版 pid 摘要不交给 Python）" at 447.
