# R-G1-01 — A sends opening bytes which lack a valid stamp because credential passing was not established at production, and those bytes reach a labelled acceptance.

## 1 What the adversary does
A sends opening bytes which lack a valid stamp because credential passing was not established at production, and those bytes reach a labelled acceptance.

## 2 How it would produce false attribution
- **Preconditions:** the engine end of A's channel lacks SOCK_PASSCRED at the instant A's opening bytes are queued — the option was set after A's first send (the setup race kub §6.1 calls route A), set on the wrong end only, or never set — and the per-fragment check then admits a credential that is absent or rendered as a sentinel. A needs nothing beyond its own peer end (fd 3) and the timing of its first send: no foreign descriptor, no privilege. Configuration: all three (C-LS / C-LP / C-R) under the common abstraction of the frozen revision — the launch leg is the same in each (PLAN §Frozen design revision, Supported configurations; 01 AA-06).
- **Transitions traversed:** T-04 (socketpair and PASSCRED), T-05, T-06, T-07, T-08, T-09 (handoff, the engine's PASSCRED check), T-10, T-11 (the adversary begins), T-20 branch (a) with no credential-producing option armed, T-21, T-22, T-23, T-24 (D-ACC).
- **Sufficient condition violated:** C-02 p21 (every contributing origin has a populated valid kernel uid stamp). Cell D_21, selector q08 (no credential-producing option or path was armed when the relevant bytes were queued); B(R-G1-01) = ¬H ∧ D_21 ∧ q08. If an unstamped skb were admitted, the kernel renders its uid as the overflow uid and its pid as 0 (EV-35): the label would be the row's execution while the stamp carries no sender identity, so the step of 02 §3 that derives u(task_b, send_b) = u_r from the stamp has no premise — a labelled acceptance with no stamped origin is ¬P_acc (02 §0.1, "no such origin"). The G2 check facts are the second line (C-03 p31 and C-04 p42: a sentinel must not pass the comparison); the ledger marks them "if admitted".

## 3 What stops it
SO_PASSCRED is set on the engine end at T-04, before any task of P_X exists, and the engine verifies at T-09 that the delivered fd carries SO_PASSCRED = 1 — so the kernel stamps every skb that is ever queued on this engine end, and an fd without the option is never installed as a channel. The cut is at T-04 (preservation row T-04): the spawner creates the socketpair and sets the option on the engine end before clone (conn L257, L277; optb L188). In the prototype the spawner calls socketpair, sets SO_PASSCRED on pair[0] at once, and only then clones the child, handing it pair[1] (EV-179, spawner.c:113–129, read 2026-10-19 and confirmed at commit 3ec67985); the order was observed in the sandbox regression's strace (EV-178). The only sender that will ever hold the peer end is created afterwards (T-05, T-06 step 10; rows T-05, T-06), and the kernel's passive fill runs per skb whenever either end has the option (EV-07), on every write path into a stream socket (EV-10, EV-11). The race of route A needs a sender that exists before the receiver's setsockopt; here no such sender exists, so the window is absent rather than narrowed (kub L662–668). The agent cannot clear the engine end's option — fd-based socket operations resolve in the caller's own table (EV-94) — and the engine never clears it: the engine package holds no setsockopt call, and the only SO_PASSCRED write in the sandbox code is the spawner's one at spawner.c:115 (EV-180; EV-100 states the requirement). The verification is at T-09 (row T-09): the engine's control receive passes a handed-over fd to w2_validate_channel, which requires SO_PASSCRED == 1 by getsockopt and fails the record otherwise, without setting the option (EV-99 the requirement; EV-180 the code; EV-177 the test, in which an fd without PASSCRED faulted the control link with no Channel installed). The second line the ledger names — the per-fragment rejection of a missing, truncated or sentinel credential (T-22, T-23 as Step 1 facts; conn L419–424) — is G2's check and is not relied on for this disposition.

## 5 Disposition
**supported under stated premises**
- Premises that must hold: AA-04 (the spawner runs the code read at EV-179; the engine cannot observe the peer end's history); C4(a) as stated in kub §6; the kernel semantics of the pinned tag (AA-02); the engine in the initial user namespace (C3 / S13, a deployment premise, val row 256) so that a filled stamp renders to a pool uid — the sentinel rendering of an unmapped uid is R-G5-05's subject. A design-layer and kernel-semantics conclusion, with the engine-side items realized in the prototype and checked; not a claim about a deployed system.
- Evidence limit (configuration, substrate, run dates): runs of 2026-10-18 and 2026-10-19. Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). Limits of the checks: the PASSCRED-before-clone order was observed on the busy case of the diagnostic fixture only, not in an engine integration run (EV-178); the T-09 refusal was exercised with sockets the test made, not with a spawner that omitted the option (EV-177); "never cleared" rests on a text search (EV-180).
