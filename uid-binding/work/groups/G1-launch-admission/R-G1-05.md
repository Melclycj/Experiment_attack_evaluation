# R-G1-05 — A and B simultaneously receive the same uid from distinct allocations made by one engine process in one epoch, and A's bytes are accepted as B.

## 1 What the adversary does
A and B simultaneously receive the same uid from distinct allocations made by one engine process in one epoch, and A's bytes are accepted as B.

## 2 How it would produce false attribution
- **Preconditions:** one engine, one epoch; two reservations whose leases carry the same numeric uid u are both open (J_A and J_B overlap); both are launched (two P_X at u); A's bytes reach B's row — on B's endpoint (A-07, stipulated) or, with the endpoint half intact, not at all, since A's own endpoint carries expected u = u_B and A's bytes at A's row are labelled A, which is correct. The engine's allocator would have to hand out u twice: a lease marked free while held, a second lease object for one uid, or two workspaces mapped to one uid in the directory (the last is the U-05 premise failure that 02 D_61 routes to R-G5-06). Configuration: all three under the common abstraction (01 AA-06).
- **Transitions traversed:** T-01 (twice, same uid), T-02, T-03 (twice), T-05, T-07 (two clones at u), T-11, T-20 … T-24 at row B.
- **Sufficient condition violated:** C-06 p61 (at each t in J_r no other allocation interval for another execution assigns u_r). Cell D_61, selector q23 (the two overlapping allocations were made by the same engine process in the same engine_epoch); B(R-G1-05) = ¬H ∧ D_61 ∧ q23. With two live executions at u, p62 cannot separate them: A's task at u is not a member of P_XB, yet its stamp u equals row B's expected_uid, T-23 passes, and the label names B while Exec(b) = X_A. This is the same-uid limit W2.1 reached by allocation rather than by the deployer's choice; the design's own text says a pool that wraps turns the principled boundary into a resource-management failure (kub §2.1).

## 3 What stops it
T-01 refuses a reservation while the workspace uid's lease is held or quarantined — one lease, one holder; one workspace, one uid, one execution — and T-03 refuses a spawn whose uid or lease is in a live SpawnRecord. First cut, the engine's allocator (preservation row T-01): the only UidLease allocator leases a workspace nothing but the uid registered for it, and only if that lease is in the pool, free, and its previous lease satisfied CLOSED AND empty; any mismatch is a refusal with no row created and no substitute uid chosen (rr L560–564; conn L74, L78). In the prototype the reservation refuses unless the workspace is AVAILABLE with no active lease, takes uid and gid only from the workspace record, refuses a uid outside the pool or already in the holders table, and refuses a workspace whose previous row is not CLOSED with membership_empty; a quarantined lease stays in holders, and no path picks another uid (EV-200, lifecycle.py:121–167, confirmed at commit 3ec67985 on 2026-10-19); a held-workspace launch and a launch naming another workspace were refused with no row created (EV-199). The directory maps one uid to one workspace and the same workspace admits one execution at a time (rr L551, L562; rr L65): at start-up check_pool refuses a uid or gid shared by two workspaces (EV-202). A lease returns to the pool only when its row is CLOSED and membership_empty, close step 2 has run and the lease is HELD, and only once; membership_empty is set only from the spawner's empty fact or the local never-submitted withdrawal (EV-205, EV-206, EV-221), and an error or timeout quarantines the lease (EV-203, EV-204). So within one engine and one epoch, u's lease is held by at most one execution at every instant (IG-06), and IG-02's exclusivity across launches follows from row T-01's argument. Second cut, independent of the allocator, on the trusted spawner (row T-03): a spawn whose uid, gid or workspace is held by a live non-empty record, or whose uid or gid differs from the workspace's registered value, is refused before any clone (conn L112, L160–162; rr L65; si L271–272; EV-209, spawner.c:83–94), and both refusals were exercised in the sandbox regression (EV-207 busy, EV-208 bad-uid and bad-gid) — so a double reservation by a defective allocator yields at most one clone at u while the first record's process is not terminal. A refused second spawn ends as spawn_failed with no Channel and its row CLOSED (T-13; row T-13; IG-09; EV-211 for the validate stage), so no acceptance at it is possible.

## 5 Disposition
**supported under stated premises**
- Premises that must hold: one engine per uid pool and one epoch (U-05; engine-requirements §8, val row 252, a deployment premise; the concurrent-engine case is R-G5-06, the stale-epoch case R-GX-04); the deployer's directory is one-to-one (val row 253, deployment premise; the start-up check refuses a shared uid or gid, EV-202); AA-04 for the spawner's record discipline; AA-01 (single executor); the empty fact's soundness (IG-03 … IG-05 as pre-state guards; G4's rows for T-42/T-43; the kernel half EV-17). A design-layer conclusion, with the allocator and spawner rules realized in the prototype and checked; not a claim about a deployed system.
- Evidence limit (configuration, substrate, run dates): integration run and sandbox regression of 2026-10-19 (pool uids 70000–70002). Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). Limits of the checks: the held-uid launch test is refused at the workspace check (lifecycle.py:137–138) before the holders check (L140) is reached, so the holders refusal and the "previous row CLOSED and empty" refusal (L142–144, val row 130) rest on code reading; uid-pool exhaustion is exercised by no test — val row 129's cited test is refused at the execution-slot limit, not by a uid shortage — so "refuse rather than reuse" rests on EV-200's reading that no path picks another uid; the regression records the busy, bad-uid and bad-gid case results only. The consequence measurements (EV-50, EV-51, EV-68) are on the arm3 docker substrate of 2026-07 and the 2026-08 dprime cells.
