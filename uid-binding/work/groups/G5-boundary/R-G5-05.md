# R-G5-05 — Distinct senders render to a sentinel/overflow value in the receiving namespace and a labelled decision treats the alias as a principal.

## 1 What the adversary does
Distinct senders render to a sentinel/overflow value in the receiving namespace and a labelled decision
treats the alias as a principal.

## 2 How it would produce false attribution
- **Preconditions:** two kernel routes deliver an identity-less rendering (kub §6.1). Route B: the engine's
  own user namespace has no mapping for the sender's kernel uid, so `from_kuid_munged` renders the overflow
  uid without error (EV-01, EV-13) — this is C3 / S13 absent (T-67 branch d), and it renders every unmapped
  sender as the same number (EV-33). Route A: the credential travels unfilled because `SO_PASSCRED` was not
  in effect at send, arriving as pid 0 and the overflow uid (EV-35, EV-36) — structurally absent here, since
  the spawner sets `SO_PASSCRED` on the engine end at `socketpair`, before the child exists (T-04 precedes
  T-05, a Step 1 fact; EV-34; measured kept on the handed-over fd, EV-76). A third case, the receiver
  discarding a valid credential (C4's collected half absent, `MSG_CTRUNC`, EV-14), yields no credential
  rather than an alias and meets T-22's close outcome. For a wrong label the alias must become a principal:
  with p31 failed, two distinct senders A and B both render as the overflow value, and a labelled decision
  treats that value as one principal — on the compare path only if some row's comparand is the sentinel,
  on the record path only if a `verified_subject` is written from a fragment the comparison did not pass.
  Configuration: all three under the common abstraction.
- **Transitions traversed:** T-67 (C3 absent) → T-20 (a) (the kernel stamp is the sender's real kuid,
  intact) → T-21 (rendering: the overflow value) → T-22 → T-23 (sentinel test, then comparison) → T-24;
  T-38 for the record path. Selector q11.
- **Sufficient condition violated:** C-03 p31 — r is not injective on the relevant uids (two kernel uids,
  one rendered value); branch D_31 ∧ q11. C-04 (p41 / p42) if a decision admits the alias without the
  comparison. The label would be wrong because the compared value no longer identifies the sending
  principal: any unmapped sender's bytes would match any row whose comparand were the alias.

## 3 What stops it
C3 — the engine in the initial user namespace (S13) keeps the rendering injective, and the engine refuses
service unless its namespace has the single full identity map; if an alias still arrives, T-23's sentinel
rejection, T-01's pool exclusion of sentinel values and D4 on the record paths keep it from being a
comparand or a principal — realized in the prototype and checked. Under C3 the engine's namespace is the
initial one with the identity map, so r is the identity on every kernel uid and injective (EV-01, EV-13);
measured earlier on a root engine in the initial namespace, which read the true uid 60001 for a sender whose
own view was 65534 (EV-65, d4). The two halves of C3 now stand differently:

- **Engine-side half, realized and checked.** Before the catalogs are loaded and the control endpoint is
  used, the engine reads /proc/self/uid_map and the overflow values and hands them to the spawner's C parser,
  which accepts only the single line 0 0 4294967295 and positive overflow values; anything else prints one
  startup_refused line and exits 3 (EV-165). The product entry recorded that map in every engine case with a
  startup field (EV-163) and refused service under an unshare-made namespace whose map reads 0 0 1 (EV-164).
- **Initial-namespace half, a deployment premise.** That the engine's namespace is the initial one is
  engine-requirements §8 row 256, result 部署前提 (development-host reading: the map holds; that the WSL2
  distribution's init namespace is the host's initial namespace is stated there as an inference). It is a
  premise, not a remaining `[S]` item, for three reasons. First, step4-brief §1 makes a deployment
  precondition the engine does not check a premise, as the 2026-10-18 rulings did for R-G5-06 and R-G5-08.
  Second, the engine cannot check it from inside: an identity-map reading does not show that the namespace is
  the initial one (EV-80's own limit; EV-163 note). Third, what the premise adds over the checked half is
  narrow: route B needs a sender kuid that is unmapped in the engine's namespace, and the engine already
  refuses to serve in any namespace whose map is not one extent covering 4294967295 ids, so the premise
  bears on which namespace that is, not on the map's shape. A kernel reading that would remove even that
  dependence is proposed in section 4.

If an alias nevertheless arrives (C3 absent, or route A on a substrate that reopened it), three engine
behaviours keep it from becoming a principal, each now realized:

- **Pool exclusion (T-01).** At start-up the engine refuses a pool id outside 0 < id < 0xFFFFFFFE, a uid
  equal to the overflow uid or the engine's own, a shared uid or gid, and a uid that names a host account
  (EV-202, EV-201); the lease uid comes only from the workspace record (EV-200), and expected_uid is written
  once from the lease (EV-186, EV-187). So no row's expected_uid is ever a sentinel (EV-130's realization).
- **T-23's sentinel test.** On the data channel's only recvmsg the C reader rejects unless there is exactly
  one credential, pid > 0 and the uid is not 0, the overflow uid or 0xFFFFFFFF and equals the bound expected
  uid; on failure the reader is dead, no frame is formed, and no observed uid is returned or used to look up
  another row (EV-171, EV-169, EV-186, EV-196). Tested: a root sender and an overflow-uid sender were
  rejected, the latter even with the expected uid set equal to it (EV-175); six synthetic credential buffers
  including uid 0, uid 65534, pid 0 and MSG_CTRUNC were rejected (EV-176).
- **D4 on the record paths (T-38).** The recorder refuses a verified subject whose sender uid is 0, the
  overflow uid or 0xFFFFFFFF or differs from its expected uid, and refuses a subject on every other kind
  (EV-225); tested with uid 0, the overflow uid and a non-comparison sender uid (EV-224).

Route A stays absent by T-04's ordering: the spawner creates the socketpair, sets SO_PASSCRED on the engine's
end and only then clones (EV-179, observed in the trace of one diagnostic-fixture case, EV-178), and the
engine refuses to install a handed-over fd without SO_PASSCRED = 1 (EV-177). Preservation row relied on: T-67
(branch d: I_state preserved, C-03 p31 fails) — the stop is the stated and now realized check, not a
preservation result.

## 5 Disposition
**supported under stated premises** (the same value as the `disposition:` field).
- Premises that must hold: C3 / S13 — the engine runs in the initial user namespace (val row 256, a
  deployment premise the engine does not check; development-host reading: the identity map holds, the
  initial-namespace identity inferred). This route traverses T-67 only as the departure from C3 (branch d,
  route B): the disposition holds only on the branches where C3 holds, and where C3 fails the alias layer is
  what stands; the route does not rest on C1, C2 or the exclusive-pool premise, whose T-67 departures are
  R-G5-03 / R-G5-07, R-G5-04 and R-G5-06. The kernel rendering semantics at the pinned tag (AA-02); the spawner
  runs the code read at EV-179 (AA-04); the common abstraction of the frozen revision. A design-layer and
  kernel-semantics conclusion, with the engine-side items realized in the prototype and checked; nothing here
  is a claim about a deployed system.
- Evidence limit (configuration, substrate, run dates): runs of 2026-10-18 and 2026-10-19 (integration
  20261019T011226Z-engine-pool-70000, sandbox regression 20261019T010923Z-sandbox-pool-70000, the PASSCRED order
  run of 2026-10-18). Limits of the
  checks: the self-check's refusal was shown for one non-identity map in the integration run plus the unit
  tests' parameterized maps (EV-164); the pid 0 and MSG_CTRUNC cases are synthetic buffers, not kernel-generated
  (EV-176); host identities are checked through NSS only (EV-201); the PASSCRED-before-clone order was observed
  on one diagnostic-fixture case, not in an engine integration run (EV-178); EV-65 is a root engine, not the
  unprivileged engine of the design.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).

## 6 What remains
- Residual: within the stated premises, none for this route. Outside them — an engine in a non-initial
  namespace whose map nonetheless reads 0 0 4294967295 — the alias layer above still holds by itself, and the
  first proposed kernel reading would show that rendering is then still injective. The record-path half (a
  `verified_subject` from an unvalidated fragment at T-38) is R-G3-04's subject if an alias ever enters a
  consumer. Coverage uncertainty: the D_31 remainder is R-G2-12.
- Code-reading confirmation: startup.py (L61–72, L167–185), support.c (L218–227: the sscanf takes three
  numbers and fails on any further character, so a second extent line is refused), main.py (L37–45),
  transport.c (L90–121, L150–161: the data channel calls w2_ancillary with early_failure false, so the
  sentinel test always applies there) and records.py (L206–226) were opened at commit 3ec67985 and say what
  EV-165, EV-202, EV-171 and EV-225 and val rows 131, 166, 219 and 239 say; no disagreement.
- Design obligations surfaced for the engine: none new; the C3 self-check, T-23's sentinel test and D4's
  record-path rejection named by the first version are realized. Check scope that would strengthen the
  evidence: the engine's own namespace link in its startup posture (proposed row 3); a kernel-generated pid 0
  or unfilled credential against the product reader.
- Cross-references: R-G1-01 (credential passing at production, the route A half), R-G1-02 (a comparand not
  equal to r(u_r), D_33), R-G2-03 (missing or truncated ancillary), R-G2-06 (ABI or stale decode), R-G2-12
  (the D_31 remainder, whose closing property is the same self-check), R-G3-04 (originless subject);
  preservation row T-67 (branch d). kub §6 C3 (engine-side half realized, initial-namespace half a premise)
