# R-G5-07 — A later obtains, or lawfully creates a task with, another allocation's real kernel uid and its genuine stamp passes as that execution.

## 1 What the adversary does
A later obtains, or lawfully creates a task with, another allocation's real kernel uid and its genuine stamp
passes as that execution.

## 2 How it would produce false attribution
- **Preconditions:** a task of P_XA changes its real kernel uid to u_B, or creates a task that has it,
  through a path the kernel permits (q26: "a documented lawful uid change, namespace map, or
  credential-bearing task creation"). The paths at the pin, as the kub §6 source reading of the uid writers
  lists them (proposed row): (i) `setresuid`, `setuid` or `setreuid` to a member of the own set — needs u_B in `{real,
  effective, saved}`, i.e. C1 absent (T-67 branch a; T-61); (ii) the same calls to any uid under
  `CAP_SETUID` in the initial namespace — the first half of C2 / S4 absent (T-67 branch b; T-61); (iii) a
  self-made user namespace with a map naming u_B, then `setuid` to the local number that resolves to u_B —
  the broader map needs the parent-namespace capability or a privileged writer (T-62's broader-map branch,
  T-67); an own-only map resolves only to u_A, and `setuid` to an unmapped number fails `EINVAL` with the
  kernel uid unchanged (EV-60); (iv) `execve` of a set-user-ID program owned by u_B — it would change the
  effective and saved uid, not the real one, and `no_new_privs` makes it ineffective anyway (EV-05), with
  the mounts `nosuid`; (v) fork or clone — the child inherits the credential, so it has u_B only if its
  parent already did (T-60). Every path reduces to C1 absent or `CAP_SETUID` in the initial namespace, the
  agent's or a privileged actor's. Given that, the task — still a member of P_XA, since a uid change does
  not move it between pid namespaces — sends with the passive fill: T-20 (a) stamps its genuine real uid
  u_B; the stamp equals row B's `expected_uid` and is accepted at row B when the bytes arrive on B's channel
  (A-07, or a G1 installation error); on A's own channel it meets u_A and is discarded (01 T-23).
  Configuration: all three under the common abstraction.
- **Transitions traversed:** T-67 (branch a or b) → T-07 (its re-read passing despite the departure) → T-61
  (or T-62 then T-61) → optionally T-60 (a child at u_B) → T-20 (a) → T-21 → T-22 → T-23 → T-24 at row B.
- **Sufficient condition violated:** C-06 p62 — at send_b the task has real uid u_B but is not a member of
  P_XB; branch D_62 ∧ ¬(q24 ∨ q25) ∧ q26. C-02 holds (the stamp is genuine), which distinguishes this route
  from R-G5-04. The chain of 02 §3 then places the task in P_XB by its uid, and the label B is wrong.

## 3 What stops it
C1, checked by the getresuid re-read before the seccomp install, and the first half of C2 — three equal
values at step 11, no CAP_SETUID in the initial user namespace — with the kernel's own-set and write-time map
rules, so no task of P_X can come to hold another allocation's real kernel uid (preservation rows T-61,
T-62). Under C1 the own set is `{u_A}` after step 11 (01 T-07 outcome; EV-74), and since the 2026-10-18
freeze this is checked in the product path: after `setresuid` and before the filter, `getresuid` re-reads
the three values, and any value unequal to the recorded uid gives FAIL(stage = uid), no filter, no SEALED
(conn E-01 identity supplements, L127–130; optb step 11, L252–257) — a failed spawn, with no agent code run.
Path (i)'s precondition, a foreign value left in the own set, therefore no longer reaches a running agent
through a mis-coded call; the premise narrows to "the bootstrap runs the shared drop with its re-read".
The kernel admits an unprivileged change only within the own set (EV-06), refusing others with `EPERM`
(EV-70: regaining uid 0 refused; EV-74: `setuid(0)` failed). Under the first half of C2 the task holds no
`CAP_SETUID` in the initial namespace and cannot regain it — the bounding set is a ceiling across `execve`
and `no_new_privs` neutralises set-user-ID programs (EV-05) — so a direct `setresuid` to u_B fails; a user
namespace the task makes where S1 is absent gives it capabilities bound to that namespace only (EV-20,
EV-32), with a map it can fill only with its own uid (EV-21; EV-59: foreign map `EPERM`), so a `setuid`
toward u_B inside it fails `EINVAL` and the kernel uid stays u_A (EV-60); `setns` into another uid's user
namespace is refused (EV-56) and would not change a kernel uid anyway. No fork or thread carries a uid its
parent does not hold (T-60; kub §6 reading, proposed row). Hence no task of P_XA ever holds u_B and p62 is
maintained: the T-61 row (preserves) and the T-62 row (preserves on both branches) are the preservation
results relied on; T-67's branches (a) and (b) are the departures, recorded there as not preserving IG-02.

The re-read's reach for this route is narrow and stated: it is one reading at one instant, before the
capability clear, the filter and `execve`; it reads uids, not capabilities, so path (ii) is carried by the
bounding-set clear, the capability clear after the re-read and `no_new_privs`, not by the re-read; and it
reads in the initial user namespace (step 0's `clone` creates none; C3), so its values are kernel uids,
while a later self-made namespace (path iii) renames without changing them (T-62). Later uid changes are
bounded by the kernel rules above, not re-checked. S1's deny removes path (iii)'s namespace but is not
load-bearing (02 §4.1 item 2); the route is stopped at the credential change, before the endpoint question,
so A-07 enters only the reachability of the accepted event.

## 5 Disposition
**supported under stated premises** (the same value as the `disposition:` field) — a kernel-semantics and
design-layer conclusion, not a claim about the deployed system.
- Premises that must hold: C1 with its check (the bootstrap runs the shared drop with `setresuid(u, u, u)`
  and the `getresuid` re-read before the filter); the first half of C2 (S4: bounding set cleared,
  capability sets cleared, `no_new_privs`); `nosuid` on the runtime and /work (optb steps 3–4); no privileged
  actor writing a broader map or changing a uid for the agent — for configured helpers, the first deployment
  entry of engine-requirements
  §8 (no /etc/subuid or /etc/subgid entry, container remap or other allocator overlapping the exclusive
  pool), and for a privileged actor outside every configured allocator, AA-04 (its error is a T-67
  configuration failure); the kernel at the pinned tag (AA-02); the common abstraction of the frozen
  revision.
- Evidence limit (configuration, substrate, run dates): EV-59, EV-60 and EV-56 are the 2026-09-01 rendezvous
  run on WSL2 6.6.87.2 with no seccomp and a uid-1002 agent; EV-70 is the 2026-08-18 probe in Docker on the
  WSL2 VM, not the engine; EV-74 is the 2026-09-11 run of the P2a sandbox code on direct WSL under the
  diagnostic policy; the re-read run is 2026-10-18 on the same substrate and policy, its negative path by
  test-build injection and its unequal-value branch read in the code; the list of credential paths is
  the 2026-10-18 kub §6 source reading, a text-pattern sweep with its stated bounds, unmeasured.

## 6 What remains
- Residual: q26's cell also holds a task outside the engine that becomes a holder of u_B later through a
  documented path — a host process started or switched under a pool uid by a privileged actor. The agent's
  C1 and C2 do not reach it; the deployment entry and AA-04 named in section 5 do, as premises the engine
  does not check (conn E-01 identity supplements, L106–107: the reservation reads only the engine's own
  lease state). Coverage uncertainty: the D_62 remainder is R-G5-08.
- Pre-registered hypothesis, adjudicated: the PLAN's "C2 and spawn step 11 stop it" — C1 (now with its
  re-read) and the first half of C2, both inside step 11, stop the route; the `unshare` deny does not (02
  §4.1 item 2; kub §3). No disagreement with 02 §4.1.
- Design obligations surfaced for the engine: (1) keep the re-read and its two injection cases in the
  regression (BUILD-PLAN's re-read check; T-07); (2) the explicit ambient and permitted clear of step 11 is
  still marked unexercised as a step in its own right (01 MM-13), its outcome — capability sets zero — being
  EV-74; the earlier obligation of this file, a deployment statement against a map-writing helper covering
  the pool, is now the first deployment entry of engine-requirements §8 (T-62).
