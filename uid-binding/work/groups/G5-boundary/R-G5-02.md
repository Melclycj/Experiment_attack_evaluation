# R-G5-02 — A uses cross-domain hardware memory access to alter observations/state, or uses a hardware read plus an attribution-changing step.

## 1 What the adversary does
A uses cross-domain hardware memory access to alter observations/state, or uses a hardware read plus an
attribution-changing step.

## 2 How it would produce false attribution
- **Preconditions:** a hardware mechanism that reads another domain's memory below every software check
  (transient execution) or reads and writes it (a Rowhammer-class DRAM disturbance fault) — the fifth
  non-goal, N9 — with no kernel defect involved (¬N1). The adversary, arbitrary code at u, can run the
  instruction sequences and memory-access patterns such a primitive needs inside the envelope; the model's
  capability is not an input (AA-12). Configuration: all three under the common abstraction; the primitive
  sits below the agent ↔ engine leg and model locality does not enter.
- **Transitions traversed:** T-11 → T-66 (hardware form). Write half (a fault): a bit flip in a task's
  `struct cred` uid field (R-G5-01's w1), in a queued skb's control block (w2), in engine memory holding
  `expected_uid`, the Channel → Session association, a lease state or `membership_empty` (w3), or in a
  pid-namespace membership structure (w4) → then T-20 … T-24 as in R-G5-01. Read half (transient
  execution): a read of engine memory (secrets, the session table, descriptor numbers) or of kernel memory
  changes no stamp, rendering, row, lease or membership (02 §4.2), and under intact memory protection a
  leaked identifier confers no reference (EV-94); so within the model the read half reaches an accepted
  wrong label only through the write half, through N1 (R-G5-01), or through an in-model step that keeps its
  own route (A-07 is a held descriptor, which leaked data does not supply; R-G2-09). No in-model transition
  names an attribution-changing step for a pure hardware read; 02 §4.2 records that cache-timing
  observation alone is not N9's cross-domain read primitive, and the design's contention channels are CCT's
  (tm D9), outside this property.
- **Sufficient condition violated:** any of C-01 … C-08, by B(R-G5-02) = H ∧ ¬N1 ∧ (Bad_acc ∨ ¬C-08)
  (02 §4). The label is wrong for the same reason as in R-G5-01: an input the chain of 02 §3 relies on was
  altered below the kernel rather than produced by it.

## 3 What stops it
Declared exclusion: the kernel-breach paragraph of scope-and-boundary.md §Boundary Defence (N9, the hardware
path), with S14 its checkable deployment half — "the fifth non-goal (N9) is the hardware path
(transient-execution read, Rowhammer-class fault read/write; S14 its checkable half). The two are declared
side by side" — together with the fifth entry of the non-goals list ("cross-domain memory read or write by a
hardware mechanism", added 2026-09-28) and its Out-Of-Scope Ledger row: these mechanisms "reach another
domain's memory directly, below every check this design adds, so no software design defends them"; the
transient-execution half is made checkable as S14; the Rowhammer half is declared only, with no claim that
ECC, DDR5 or disabling KSM (S12) prevents it. The preservation row T-66 records that no guard of I survives
the disturbance; no mechanism of the frozen design is claimed against it.

**What S14 is and is not.** S14 requires that no file under the cpu vulnerabilities directory of sysfs read
`Vulnerable` on the production host and that the engine, which holds the secrets, opt into the per-task
indirect-branch mitigation by `prctl` unless the host forces it on for all tasks. It is a deployment
requirement "stated; not checked on any production host" — `[S]`, EV-128 — that narrows the read half's exposure on
the deployed host; it does not touch the write half, and by its own reasoned exclusion it does not cover
bounds-check-bypass gadgets in the engine's code or store-bypass reads. It is therefore the checkable half of
a declaration, not a stop.

**What the exclusion buys and its width.** As in R-G5-01: every guard is stated about memory the hardware
keeps intact; the declaration is what lets the preservation arguments speak about kernel-produced values.
The paragraph and the ledger row cover read and write alike (the fault half is read and write), so the
exclusion is as wide as kub §8 requires; the design's own statement that no software design defends these
mechanisms is why the declaration is the only disposition available. The read half carries §2's
second-step clause: a hardware read alone is not an attribution change.

## 5 Disposition
**declared out of scope** (the same value as the `disposition:` field).
- Premises that must hold: the fifth non-goal and its Out-Of-Scope Ledger row as frozen (approved
  2026-09-28; its Rowhammer anchors carry the provisional marker `CCT-F54`); the kernel-breach paragraph's
  N9 clause; S14 as the checkable half; the common abstraction of the frozen revision.
- Evidence limit (configuration, substrate, run dates): the engine half of S14 — the per-task indirect-branch
  opt-in with PR_SPEC_FORCE_DISABLE before holding secrets — is realized at engine commit 9981dd7b and tested in
  the run of 2026-10-20, where a later PR_SPEC_ENABLE failed with EPERM (EV-283, EV-284); for the host half, the
  production host's sysfs vulnerability readings, the only readings are the development host's, recorded by the
  engine's validation record as a deployment premise (val row 259), not a registry observation, and EV-80's
  2026-09-11 precheck did not read them. S14 remains the checkable half of a declared exclusion, not a stop.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).

## 6 What remains
- Residual: the read half has no named in-model second step — its attribution-changing step is the write
  half or N1 — and this is a statement about the model (02 §4.2, U-04), not evidence that no such step
  exists; the Rowhammer read/write capability under ECC, DDR5 or KSM-off conditions is owed by the
  protected-state investigation (SUB-07) per the ledger row, not asserted here; what S14 leaves inside the
  non-goal (engine-code gadgets, store-bypass) stays declared. No new ID.
- Design obligations surfaced for the engine: the S14 per-task opt-in — `prctl` for the indirect-branch
  mitigation with PR_SPEC_FORCE_DISABLE before holding secrets — is realized as the first start-up action and
  tested (EV-283, EV-284); it is not a transition of 01 and stays on the obligation list as a start-up
  obligation; a deployment must still state the sysfs readings of its production host beside its build
  (tm D8).
- Cross-references: R-G5-01 (N1, declared beside this one; its w1–w4 forms are reused); R-G2-09 and A-07
  (the in-model step the read half would need); preservation row T-66; S12 (not claimed to prevent
  Rowhammer); U-04. C1–C4 and obligations #1–#6 presume memory integrity; obligation #6 is touched as a
  tamper-resistance premise the route does not discharge.
