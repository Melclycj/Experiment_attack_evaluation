# R-G5-06 — A nonmember host/other-compartment task already possesses an allocated uid, or a concurrently running engine's allocation assigns it, and bytes under it are accepted as that execution.

## 1 What the adversary does
A nonmember host/other-compartment task already possesses an allocated uid, or a concurrently running
engine's allocation assigns it, and bytes under it are accepted as that execution.

## 2 How it would produce false attribution
- **Preconditions:** two branches of 02 §4 land here. Under p62 (D_62 ∧ ¬q24 ∧ q25): a task outside P_Xr
  already has real kernel uid u_r when T-01 reserves u_r for row r — a host task, a task of another
  compartment, a second engine's execution, or the local model instance — and it is not a survivor of a
  prior allocation (that is R-G4-01, q24). Under p61 (D_61 ∧ ¬q23 ∧ ¬q33): another engine process, running
  at the same time on an overlapping pool, allocates u_r to its own execution — not the same engine in the
  same epoch (R-G1-05, q23) and not a predecessor epoch of this cell (R-GX-04, q33). Both are failures of the
  exclusive-pool premise (02 §0.3, U-05; conn L87; EV-81), which 01 T-67 names since version 8 (branch f).
  The design now also writes the premise's limit: the reservation reads only the engine's own lease state,
  so it sees neither a task left by an earlier epoch nor a task outside the engine holding a pool uid
  (conn E-01 identity supplements, L106–107; 01 T-01). For a wrong label the holder's bytes must reach row
  r's channel: the frozen construction gives the agent-side endpoint only to X_r's clone (T-04, T-05, T-06
  step 10), so the holder needs A-07 — a descriptor obtained by collusion or an implementation leak, whose
  measured origin is d2 (EV-63) — or a G1 installation error. With it, T-20 (a) stamps u_r, which equals
  `expected_uid`, and the frame is accepted as X_r while the sender was never in P_Xr. Configuration: all
  three under the common abstraction; for C-LS and C-LP the local model instance is one more host process
  the premise must cover (rr E-07, L387–389).
- **Transitions traversed:** T-67 (branch f) → T-01 (reserves u_r from the engine's own lease state only)
  → T-02 … T-11 → the foreign holder: T-20 (a) through an A-07 endpoint → T-21 → T-22 → T-23 (u_r equals
  u_r) → T-24 (D-ACC labelled X_r). In the concurrent-engine branch the other engine's own T-01, T-03, T-05
  and T-07 create a P_Y at u_r; T-49 is not involved, since that engine is not a predecessor epoch.
- **Sufficient condition violated:** C-06 — p62 (a live task with real uid u_r at some t in J_r is not a
  member of P_Xr) or p61 (two allocation intervals assign u_r at once); IG-02 fails at the same state. The
  chain of 02 §3 then places task_b in P_Xr by its uid alone, and the label is wrong.

## 3 What stops it
The exclusive-pool premise as the design now writes it — the pool reserved on the host to the engine alone,
at most one engine per range, a uid inventory naming every holder, the local model instance under no pool
uid — under which no task outside the engine's own executions holds a pool uid, so the route's precondition
does not arise (03 §3, IG-02; T-67 branch f is the departure). The premise has three written parts since the
2026-10-18 freeze: the statement that the trusted deployment supplies pool exclusivity before start and
that a /proc scan cannot establish it (conn L87–89); its limit, that the reservation reads only the
engine's own lease state (conn L106–107); and, for local configurations, the deployment precondition that
the local model instance is an external process under no pool uid and in no execution's process domain
(rr L387–389, L885–886). The deployment entries that realize it are the first entry of
engine-requirements §8: the
range overlaps no uid allocator on the host (the login and system ranges, every /etc/subuid and /etc/subgid
entry, systemd `DynamicUser`, a container runtime's remap), no service or account runs under a pool uid, at
most one engine runs per range at a time, and the deployer's inventory names every holder, the engine's
leases being the only ones — each checkable by reading configuration (§8 notes), which the earlier
statement lacked.

Why the premise suffices. Branch p62 ∧ q25 needs a task outside P_Xr holding u_r at the reservation that is
not a prior survivor. Under the premise the only tasks that can hold a pool uid are the engine's own
executions; a task of an earlier allocation of u_r is q24's (R-G4-01) and one of a predecessor epoch q33's
(R-GX-04), so no history is left for this cell. Branch p61 ∧ ¬q23 ∧ ¬q33 needs a second engine allocating
from an overlapping range at the same time, which "one engine per range" excludes. No engine mechanism
enters: the engine does not and cannot check the premise — it reads only its own leases (conn L106–107), a
/proc scan races a forking agent and is ruled out (EV-16), and neither the engine nor the spawner enters an
execution's namespace (EV-19). The premise is therefore a deployment precondition the engine does not
check, which the brief counts as a premise; the stop is its holding, and its failure is the T-67 branch (f)
departure, against which the design offers nothing. Preservation row relied on: T-67 (branch f: does not
preserve, named as the departure).

## 5 Disposition
**supported under stated premises** (the same value as the `disposition:` field) — a design-layer
conclusion about the frozen text, not a claim about the deployed system. 02 version 7 calls the route
"conditional on deployment preconditions"; under the brief's rule that a deployment precondition the
engine does not check is a premise, and with no unbuilt engine component in the stop, that standing is
this value (change request CR-G5-05).
- Premises that must hold: the exclusive pool as engine-requirements §8's first entry states it (no
  overlapping allocator, no service or account under a pool uid, one engine per range at a time, the
  inventory naming every holder); the workspace ↔ uid directory prepared by the trusted deployer with pool
  uids (§8, second entry), so that the u_r T-01 reserves is a pool uid; for C-LS and C-LP the local model
  instance under no pool uid and outside every execution's process domain (rr L387–389, L885–886); no
  privileged actor placing a task under a pool uid outside every configured allocator (AA-04; its error is
  a T-67 configuration failure); the common abstraction of the frozen revision.
- Evidence limit (configuration, substrate, run dates): no run has measured a pre-existing holder, a concurrent
  engine or a deployment's inventory; the arm3 same-uid cells (2026-07-02 / 2026-07-03, docker-seccomp T1 on
  WSL2, staged configuration) show only that the check does not distinguish holders of one uid.
  Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).

## 6 What remains
- Residual: when the premise fails (T-67 branch f) the route is reachable given A-07, and the engine cannot
  see it — it reads only its own leases (conn L106–107), and its start-up checks do not replace the
  deployment requirement (conn L87–89). The premise is configuration-level: it bars the holders a host
  configures, not a privileged actor's ad-hoc action, which stays with AA-04. Running engine and agents in a
  dedicated-kernel VM would shrink the entry to the guest image (engine-requirements §8 notes) — a
  deployment-shape choice left to the user, not a requirement. Coverage uncertainty: none beyond the
  premises; the method question this file's first version raised is answered by the §8 entry.
- Design obligations surfaced for the engine: none — the obligations are the deployer's, already listed as
  §8 entries (T-01, T-67). A deployment-time attestation consumed at start-up stays optional.
- Cross-references: R-G4-01 (prior survivor, q24), R-G1-05 (same engine, same epoch), R-GX-04 (predecessor
  epoch, MM-10), R-G5-07 (later acquisition, whose host-side branch rests on the same entry), R-G5-08 (the
  remainder), R-G2-09 (the A-07 endpoint route); preservation row T-67 (branch f), whose conclusion line
  still records the method as unstated (CR-G5-03). Obligation #4 (uid ↔ execution 1:1 for the row's
  lifetime) — this route is its deployment half; obligation #6 touched; C1–C4 untouched, the holder's stamp
