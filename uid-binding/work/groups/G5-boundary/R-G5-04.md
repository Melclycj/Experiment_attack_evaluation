# R-G5-04 — A attaches another mapped kernel uid using relevant namespace privilege and it is accepted as another execution.

## 1 What the adversary does
A attaches another mapped kernel uid using relevant namespace privilege and it is accepted as another
execution.

## 2 How it would produce false attribution
- **Preconditions:** the sender attaches `SCM_CREDENTIALS` naming u_B. The kernel accepts it only if (i)
  `make_kuid(cred->user_ns, u_B)` is valid — u_B has a mapping in the sender's user namespace — and (ii)
  u_B is in `{uid, euid, suid}` or `ns_capable(cred->user_ns, CAP_SETUID)` holds (EV-08). Two sub-branches:
  (A) the sender stays in the initial user namespace, whose identity map makes (i) true for every uid; (ii)
  then needs `CAP_SETUID` in the initial namespace — the first half of C2 / S4 absent (T-67 branch b).
  (B) the sender has made its own user namespace (T-62 branch 2, S1 absent): (ii) is free, the creator
  holding the full set bound to its namespace (EV-20, EV-32), but (i) needs u_B in the new map, and an
  unprivileged writer may map only its own effective kernel uid (EV-21; EV-59); a broader map needs
  `ns_capable(ns->parent, CAP_SETUID)` — the capability in the initial namespace again — or a privileged map
  writer acting for the agent (T-62's broader-map branch, T-67); deeper nesting only narrows (EV-21). Both
  sub-branches reduce to one premise failure: `CAP_SETUID` held in the initial user namespace by the agent,
  or exercised for it. Given that, the stamp is u_B (T-20 (c) with capability; the explicit path suppresses
  the passive fill, EV-07), rendered u_B in the engine's namespace (C3); on A's own channel it meets row A's
  u_A and is discarded (01 T-23 outcome); it is accepted only at row B — through B's agent-side endpoint
  (A-07) or a G1 installation error. Configuration: all three under the common abstraction.
- **Transitions traversed:** T-67 (first half of C2 absent; or S1 absent with a broader map) → T-62
  (sub-branch B only) → T-11 → T-20 (c) → T-21 → T-22 → T-23 → T-24 at row B. T-61 is not traversed: the
  real uid is unchanged, which is what distinguishes this route from R-G5-07.
- **Sufficient condition violated:** C-02 p22 — k(b) = u_B ≠ u(task_b, send_b) = u_A; branch D_22 ∧ ¬q09 ∧
  q10 (a foreign mapped uid outside the own set, permitted by the actual capability and map predicates).
  The label is wrong as in R-G5-03: the chain of 02 §3 reads the stamp as the sender's real uid.

## 3 What stops it
First half of C2 — no `CAP_SETUID` in the initial user namespace (step 11's cleared bounding set and
`no_new_privs`) — with the kernel's write-time map rule, under which a sender can name only its own kernel
uid (T-07 outcome; preservation rows T-61, T-62). The derivation follows kub §3 and 02 §4.1 item 2, not the
PLAN's hypothesis. The clause on the send path, `ns_capable(cred->user_ns, CAP_SETUID)`, is satisfiable by
any process that makes a namespace and is not a barrier (EV-20; the full set returning after the drop is read in kub §6 C2, EV-32 `[R]`, whose report lies outside the registry's source list); the
barrier is the map: `new_idmap_permitted` admits an unprivileged map of one extent of length one naming the
writer's own effective uid (EV-21), measured as own map ok and foreign map `EPERM` (EV-59, 2026-09-01, no
seccomp); the author of the clause names the same limit — "any valid value", valid meaning mappable (EV-22).
Given no `CAP_SETUID` in the initial namespace — bounding set cleared and `no_new_privs` at step 11 (EV-05;
measured EV-70, EV-74) — the agent can neither write a broader map nor skip the detour and call `setresuid`
directly. In sub-branch B, u_B is nameable in no namespace the agent can occupy: `make_kuid` returns an
invalid uid and the send fails `-EINVAL` before the permission test, with no skb (EV-08; T-20 (d)). In
sub-branch A the identity map makes u_B valid, but the capability test fails and the send fails `-EPERM`,
with no skb (T-20 (c); EV-29's third route). Either way p22 holds: no accepted byte carries a stamp other
than the sender's real uid. S1 — the user-namespace deny (EV-75 under the diagnostic policy; the single
clause EV-71) — removes sub-branch B's namespace altogether and is reachable-surface reduction (kub §6 C2's
second half; scope S1 row as rewritten 2026-08-30); it is not what stops this route. Preservation rows
relied on: T-61 (no own-set growth), T-62 (preserves on both branches: own-only map), T-67 (branch b names
the departure).

## 5 Disposition
**supported under stated premises** (the same value as the `disposition:` field) — a kernel-semantics
conclusion with the step-11 posture as its design-layer premise; nothing here is a claim about the deployed
system.
- Premises that must hold: the first half of C2 — no `CAP_SETUID` in the initial user namespace (S4:
  bounding set cleared, `no_new_privs`); no privileged map writer acting for the agent's namespace; the
  engine in the initial namespace (C3), needed not for p22 but for the route's acceptance step to compare
  u_B as u_B; the kernel at the pinned tag (AA-02); S1 is not a premise; the common abstraction of the
  frozen revision.
- Evidence limit (configuration, substrate, run dates): the map rule is measured on 2026-09-01 on WSL2
  6.6.87.2 with no seccomp (EV-59, EV-60); the posture on 2026-08-18 (Docker on the WSL2 VM, EV-70) and
  2026-09-11 (direct WSL under the diagnostic policy, EV-74); the explicit foreign-uid send is measured
  once, on WSL2 6.6.87.2 with no seccomp (EV-29, 2026-10-14), the native-Linux VM arm pending.

## 6 What remains
- Residual: the explicit foreign-uid send is measured on one substrate only (EV-29; the native-Linux VM arm
  is pending); the deployment premise that no privileged tool writes a broader map for the agent's
  namespace is not stated as a requirement (the design's agent never self-maps, EV-61 note and EV-29 note;
  a deployer's user-namespace tooling is outside the frozen text); the production allow-set (EV-129)
  is, for sub-branch B, an optional surface reduction — it decides only whether the agent can create the
  namespace at all — and not a component the identity defence needs: the required defence is the map rule
  plus the initial-namespace capability posture, which stop the route even when the namespace is created
  (§3–§5), so EV-129's `[S]` does not enter this disposition.
- Pre-registered hypothesis, adjudicated: the PLAN's "C2 and spawn step 11 stop it" holds for the first
  half of C2 — step 11's bounding-set clear and `no_new_privs` — with the map rule; the second half, the
  `unshare` deny, does not stop the route (02 §4.1 item 2; kub §3's ruling of 2026-08-30). The reading
  "unshare allowed ⇒ forged uid" is rejected, not copied. No disagreement with 02 §4.1, hence no change
  request on this point. The PLAN's Stream P row expected an error for the self-mapped sub-arm; EV-29
  arm 3 measured acceptance with the receiver reading the sender's own uid, as 02 §4.1 item 4 derived —
  that bears on the note 02 left for reconcile, not on this route's disposition.
- Design obligations surfaced for the engine: none new; the S1 `clone` clause remains man-page-derived
  (MM-13) and is surface, not identity (T-62); a deployment statement that no set-user-ID map-writing
  helper covering the pool's uids is installed on the host is a deployment precondition beside S1–S14,
  recorded in R-G5-07 §6.
- Cross-references: R-G5-03 (own-set selection, q09), R-G5-07 (real-uid change, C-06), R-G2-05 (the D_22
  remainder for the intact posture), R-G2-09 (the A-07 endpoint variant); preservation rows T-61, T-62,
  T-67. kub §6 C2 (both halves, kept separate) and C3 touched; obligations #2 and #6 presume this posture.
