# R-G3-02 — A's correctly attributed request/cancel/task result is joined by request id or task/grant reference to B's context during admission/dispatch.

Re-run on 01 version 10 (the third freeze: conn `0c16e567a34aa441`, rr `1a8ea18374b07431`, si
`c8aff1a37d73561b`, optb `e84d0b4255cfa022`); design line numbers refer to these blobs. Re-run again at follow-up
step 4 (2026-10-19) on 04 version 7; engine file:line refers to the prototype at commit 3ec67985 (engine code
equal to 74833c58).

## 1 What the adversary does
A's correctly attributed request/cancel/task result is joined by request id or task/grant reference to B's context during admission/dispatch.

## 2 How it would produce false attribution
- **Preconditions:** A is the adversary of execution X; its frames are correctly attributed at T-24 (label
  X — P_acc holds, so the history is in F_8). B is another execution with its own row, TaskCall, TaskBinding
  and Grant, concurrently ACTIVE. A chooses protocol identifiers (A-02, 01 v10): `request.id`,
  `task_call_id`, `task_id`, `cancel.reply_to`, `task_result.reply_to` — any values, including values equal
  to B's current ones. Equality needs no guessing: active ids count from 1 per direction and their
  namespace is session + direction (conn L535–536), so A's and B's ids coincide in the normal case.
  Since the fourth revision A has no grant input: `task_start` and `request` carry no grant field (conn
  L524–525), the adapter is given no grant (si L361–362), and a `request` carrying a `grant_ref` field is an
  unknown-field failure of T-24's strict parse (conn L4, L466–468; 01 v10 T-24, A-02), so it creates no
  ValidatedRequest and reaches no consumer. Configuration: all three under the common abstraction.
- **Transitions traversed:** T-20 (a) → T-21 … T-24 (label X) → T-25 → one of the consumer steps below →
  T-33 → T-34 → T-38. The consumer step that would change the association, one per owned transition:
  - T-30 admission: the entry is created against "the current RUNNING call" of the original Session and
    the TaskBinding of that call. If the TaskCall were found by task_call_id in a table spanning sessions,
    or the binding by task_id in a global table, A's request would enter B's TaskCall.children and carry
    B's task_call_ref, binding and — since the grant is taken from the matched binding — B's grant.
  - T-33 authorize + try_dispatch: the decision requires task, grant and call equal to the original
    references. The grant compared is the engine's, taken from the matched call's TaskBinding (01 v10
    T-33). The grant sub-case has therefore lost its own agent-chosen input: A's request can reach B's
    Grant only if T-30 matched B's call or binding (the sub-case above), or if a trusted T-39 step bound
    A's TaskBinding to a Grant of B's session.
  - T-36 task_result: it resolves against the original in-flight call; a lookup by reply_to across sessions
    would let A's task_result commit B's TaskCall outcome.
  - T-37 cancel: it resolves in the original session's and direction's in-flight table; a lookup across
    sessions would let A's cancel terminate B's request.
  - T-39 association lifecycle: a trusted rebind that selected a Grant of another session, or a removal
    while references exist, would attach A's binding to B's Grant or leave A's entries referencing a
    removed object. This is an honest-engine step with no agent input.
- **Sufficient condition violated:** C-08, component p81 (D_81): the consumer event has an actual D-ACC
  origin (A's message) but does not carry that origin's context/reference unchanged — its task_call_key,
  grant_ref or request reference is B's — and the action it performs or records belongs to B's context.
  Selector q31 (a current request/cancel/task/grant/binding association joins another session/context,
  including T-39); not q30 (no relookup by number or recurring name after reuse). Branch B(R-G3-02) =
  D_81 ∧ ¬q30 ∧ q31. Why it is a wrong attribution: the D-ACC label stays X, so P_acc is intact, but the
  consumer's record of who requested the action (task_call_started children, authorization_decided,
  request_terminal with B's call_key and grant) names B's context for an action A's origin requested — the
  P_carry statement of 02 §3 fails at that consumer.


## 3 What stops it
Admission, cancel, task_result and dispatch resolve only inside the original Session's objects: request and call
keys carry session_id and direction, the TaskBinding and the Grant it names are the ones reachable from the
original Session's current call, and no agent-facing message carries a grant selector — realized in the
prototype engine and checked by test and code reading. Per owned transition, the design rule and its
realization:

- **T-30 admission.** Design: request_key = (session_id, direction, id) and call_key = (session_id,
  engine_to_agent, task_start.id) (conn L83–84; EV-115); task_call_id must point to the current RUNNING call,
  task_id must match it and a valid binding, and grant_ref is taken from that call's TaskBinding, not from the
  message (conn L574, L751; EV-243, superseding the quoted clause of EV-116); a business refusal does not cross
  into another session (conn L591). Realization: admission starts from context.session_ref and reaches the
  call as session.current_task_call (EV-198); it binds the request only if that call is RUNNING and its
  call_id and binding task_id equal the message's (requests.py:155–160; EV-227); the request key is
  session_id + ":a:" + id and the call key session_id + ":e:" + call id (EV-229); the RequestEntry holds the
  call, its TaskBinding and its GrantState as objects (EV-198). Tests: a binding mismatch and a request with
  no call are denied without a slot (EV-226); the decoy test shows admission reaches nothing by execution_id
  (EV-197); a request carrying grant_ref is invalid (EV-184).
- **T-33 dispatch.** Design: the no-await decision requires task, grant and call equal to the original
  references, TaskBinding and GrantState active and matching; a Grant is not borrowed across sessions
  (EV-120, EV-119). Realization: the final check requires the call, binding and GrantState to be the entry's
  own objects, the binding active and attached to the request's Session, and the grant active, of that
  session (state.session is session and grant.session_id equal), naming the task and unexpired; the summary's
  grant_ref is read from the entry's GrantState (requests.py:238–260, operations.py:173–182; EV-227). Tests:
  the final check sees a revoked grant state and expired or revoked grants deny (EV-226).
- **T-36 task_result and T-37 cancel.** Design: both resolve only in the original session's and direction's
  in-flight table; a reply above the high-water mark is a protocol error; a request of the previous call is
  refused (EV-118). Realization: cancel looks up message.context.session_ref.requests (requests.py:530), and
  task_result compares reply_to with the original session's current call (tasks.py:358–365; EV-229). Tests and
  integration cases: in-flight and unknown cancels, a stale task_result dropped and a future one ending the row,
  a request citing an earlier call denied (EV-228).
- **T-39 association lifecycle.** Design: the trusted entry creates a TaskBinding for one Session; rebind only
  through the trusted entry with no active call or request; task and grant ids engine-assigned and never reused
  (EV-119). Realization: TaskBinding.session, task_id and grant_state are write-once and the build has no
  rebind entry (tasks.py:80–86; EV-227); task and grant ids are engine-assigned and unique (EV-226); removal
  happens only for a binding no longer active with no references (tasks.py:191–206; proposed row 1).
- **T-38 record.** Design: correlation fields are value copies of the original objects' IDs (EV-122).
  Realization: request_key, task_call_key and connection_ref are copied from the entry's own objects
  (requests.py:120–132; EV-229).

**The grant sub-case.** No agent-facing message carries a grant field (EV-243): the request schema has a fixed
field set, a grant_ref field makes a request invalid (EV-184; receive.py:146–163), and the grant T-30 records
and T-33 compares is the one the matched binding names (EV-227). The stop does not rest on the parse: even a
grant field that passed would select nothing, since the prototype reads the grant only from the entry's
GrantState. The sub-case reduces, as in the 2026-10-18 run, to an agent-chosen task_call_id or task_id matched
outside the original Session (excluded at T-30 above) and a trusted T-39 step binding a Grant of another
session (excluded by the write-once binding with no rebind entry).

Preservation rows relied on: T-30, T-33, T-36, T-37, T-39 (this folder). T-24 and T-25 are cited as Step 1
facts (01 v10: the unknown-field outcome and the in-flight-table rule); the correctness of the label itself is
G2's.

## 6 What remains
- Residual and open questions: the same-execution limit — a same-uid process in P_X that learns the current
  call id is the same subject, not a different one (conn L760–762; W2.1), so a join inside one execution is
  outside this route and outside P_carry. The two points 01 v10 MM-06 leaves open (session close or associated
  error for a request whose only fault is a grant_ref field; two unrewritten sentences pairing task and grant,
  conn L759, si L365) do not reopen the route: in the prototype that request is invalid at the parse, so the
  row ends with protocol_error and no RequestEntry exists (EV-184; phases.py:78–87). A rebind entry, if a later
  build adds one, re-runs the T-39 sub-case. A cross-session test with two sending uids would turn the T-36 /
  T-37 code reading into an observation; the integration run's parallel case (EV-188) has two executions but
  exercises only hello.
- Design obligations for the engine: (T-30) reach TaskCall and TaskBinding only through the Session of the
  context and fill the grant from that binding only — realized (EV-198, EV-227); (T-33) refuse a Grant of
  another session — realized (EV-227); (T-36 / T-37) resolve reply_to only in that session — realized
  (EV-229); (T-39) rebind or remove only under the stated guards — realized without a rebind entry; (T-38) copy
  the correlation keys from the decision's objects — realized (EV-229). Each to be re-checked for each real
  connector.
- Cross-references: R-GX-05 (a relookup after uid, fd, request-number or local_agent_id reuse — not argued
  here), R-G3-03 (label changed with the reference kept), R-G3-05 (the remainder). Obligation #6
  (reference-monitor correctness: session-table lifecycle and grant model) is instantiated, the prototype
  evidence bearing on its consumer part; obligation #5 (no delegation leakage between agents) is adjacent — the
  subagent chain is outside the frozen text. C1–C4 are not touched.
