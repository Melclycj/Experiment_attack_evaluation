# R-G3-03 — A's correctly attributed work is recorded or sent onward with another execution label or local_agent_id despite retaining its original request reference.

Re-run at follow-up step 4 (2026-10-19) on 04 version 7. Design line numbers refer to the fourth-revision blobs
(conn `0c16e567a34aa441`, rr `1a8ea18374b07431`, si `c8aff1a37d73561b`) where they were re-read; engine file:line
to the prototype at commit 3ec67985 (engine code equal to 74833c58).

## 1 What the adversary does
A's correctly attributed work is recorded or sent onward with another execution label or local_agent_id despite retaining its original request reference.

## 2 How it would produce false attribution
- **Preconditions:** A is the adversary of execution X; its request is correctly attributed at T-24 (label
  X) and admitted and dispatched inside X's own context (the association is right, so R-G3-02 does not
  apply). A second execution Y exists or has existed in this engine epoch, so that a label other than X is
  available to a consumer. A's inputs are ordinary protocol content (A-02) and timing (A-06); the route
  needs no privilege beyond sending. Configuration: all three under the common abstraction.
- **Transitions traversed:** T-20 (a) → T-21 … T-24 (label X) → T-25 → T-30 → T-32 → T-33 → T-34 →
  T-35 → T-38. The consumer step that would change the emitted label while the request reference is kept:
  - T-38 record emission: an event whose request_key is A's request but whose verified_subject names Y —
    if the subject were populated from a source other than the carried VerifiedContext (a fresh lookup of
    the Session or Channel, the lifecycle control_binding, the Grant's owner, a stale decoded copy); or a
    post_read flow whose destination execution_id is taken from anywhere but the original request; or an
    event whose execution_id and request_key are A's but whose verified_subject.local_agent_id is another
    row's name — a name resolved at emit time instead of copied from the carried VerifiedContext (the case
    the widened q32 of 02 version 4 brings here from the R-G3-05 remainder, CR-F-03).
  - T-34 handler and callbacks: the chunk and result frames of A's request queued to Y's channel — if the
    writer were selected by anything but the RequestEntry's original Channel object (the handler itself
    cannot name a session or fd, so the defect would sit in the engine's apply step); or an E-07 connector
    result attached to Y's request by a connector-side identifier.
  - T-33 authorize + try_dispatch: an AuthorizedOperation or OperationSummary whose verified_context or
    operation_id (session_id + ":r:" + id, rr L234) is Y's while request_ref is A's.
- **Sufficient condition violated:** C-08, component p81 (D_81): the consumer event keeps A's request
  reference but the label it emits for the action — verified_subject.execution_id or local_agent_id, the
  flow's destination execution, the channel the response is written to — differs from the origin's
  (p81 requires both label fields to equal the origin's). Selector q32 (the original request/context
  reference is retained but the emitted execution label or local_agent_id changes; 02 version 4, CR-F-03);
  not q30 (no relookup by number or recurring name) and not q31 (no current association joins another
  session). Branch B(R-G3-03) = D_81 ∧ ¬(q30 ∨ q31) ∧ q32. Why it is a wrong attribution: the D-ACC label
  is X and P_acc holds, but the record of the action, or the execution that receives its result, says Y —
  or says X under another execution's name — the P_carry statement of 02 §3 fails at that consumer.


## 3 What stops it
The label and the response destination travel by object reference from the original RequestEntry: the sink is
fixed to that entry, verified_subject is copied only from its carried VerifiedContext, and the per-channel writer
is owned by the original Channel — realized in the prototype engine and checked by test and code reading up to
the stub handlers. Per owned transition:

- **T-33 dispatch.** Design: CandidateOperation is built in the original RequestEntry's slot and carries
  request_ref and verified_context; AuthorizedOperation is moved once and never cached, copied or reused;
  operation_id is the engine's correlation of request_key (rr L230–234; EV-123). Realization: CandidateOperation
  is a frozen object built only by freeze_operation and holding its RequestEntry, operation_id = session_id +
  ":r:" + request id from the entry's own Session; AuthorizedOperation is frozen and constructible only through
  authorize(), called once (EV-241); the OperationSummary is derived from the candidate, its grant_ref from the
  entry's GrantState (EV-227).
- **T-34 handler and callbacks.** Design: the sink delivers only to the original RequestEntry and cannot name a
  session, fd or seq; the response callback holds the original RequestEntry and Channel; workers never write
  the fd or bypass the queue; each channel's writer takes frames from that channel's FIFO with their original
  owner (EV-124, EV-125; the T-26 fact). Realization: the Sink holds only its entry and the manager
  (__slots__), handlers start only an AuthorizedOperation (EV-198); handlers deliver by posting a callback to the
  state executor's loop and never write the fd (EV-231); each Channel gets its own FrameWriter at install, each
  queued entry holds its owner, and the writer's flush is the data channel's one sendmsg (EV-242); the response
  writer is reached as entry.channel.frame_writer (requests.py:308, :327, :435). Tests: the request received
  its chunks and result on the original channel with the entry's objects identical to the arrival objects
  (EV-197); a stale sink after close reaches nothing new and late facts do not overwrite the terminal (EV-223).
- **T-38 record.** Design: verified_subject — execution_id and local_agent_id alike — is copied only after
  full E-02 validation from the request's VerifiedContext, whose local_agent_id is the original row's; the
  post_read destination is the original request's execution; correlation fields are value copies; workers
  cannot choose a session or write the log (EV-113, EV-122, EV-156). Realization: the entry's subject is
  VerifiedSubject.from_context of the arrival context, built once at admission and passed to every record of
  that entry (requests.py:120–132, :155); the context's local_agent_id comes from the Session, a write-once
  field (EV-186), and no table is keyed by local_agent_id (EV-196); the recorder refuses a verified kind
  without a VerifiedSubject (EV-225); post_read names entry.execution.execution_id as destination
  (requests.py:343, :374; EV-230); correlation fields come from the entry's objects (EV-229); the log thread
  writes only its own queue (EV-231). Tests: every verified-kind record subject is the row's copy (EV-183) and
  every E-09 subject of the request equals the VerifiedContext copy (EV-197).
- **T-35 terminal events.** Design: request_terminal, response_sent, response_abandoned and request_released
  come from the original RequestEntry's own state (si L71, L97, L122). Realization: all four are emitted
  through the entry's _rec, with the entry's subject and keys (requests.py:120–132, :421–525; EV-229).

Preservation rows relied on: T-33, T-34, T-35, T-38 (this folder). T-26 (G2) is cited as the Step 1 fact that
the writer is per channel and holds the frame's original owner; no G2 preservation conclusion is used.

**Composition:** conjunction of the rules at T-33, T-34, T-35 and T-38. The engine-side items: at those steps
the label, the correlation keys and the destination come from the carried RequestEntry, VerifiedContext and
Channel objects (realized: EV-198, EV-229, EV-241, EV-225; tests EV-183, EV-197, EV-230); the per-channel
writer holds the frame's owner, the T-26 fact (realized: EV-242); the stub handlers neither name a session, fd
or seq nor touch the entry (realized: EV-198, EV-231). Each design rule (`[S]`) is paired with
its realization: T-33 by EV-241, EV-227; T-34 by EV-198, EV-231, EV-242 (code reading) and EV-197, EV-223
(tests); T-38 by EV-186, EV-196, EV-225, EV-229, EV-231 (code reading) and EV-183, EV-197, EV-230 (tests); T-35
by EV-229. EV-125 is marked partly realized in the step 4 map: a queued entry's bytes are produced when the
writer takes it, not when it is queued, and no validation row checks the FIFO's frame discipline. That clause is
not a necessary item of this route. What the route needs from the writer is that it is the original Channel's
and that each frame keeps its owner (the T-26 fact), and both are realized (EV-242). The deferred build reads
only the owner entry's own request id, its sequence counter and the handler's text (requests.py:350–352,
:460; proposed row 1), and the wire frame carries no execution label at all, so the timing of the encoding
cannot change the label or the destination. It bears on frame order and integrity, which are not this route.
No necessary item rests on `[S]` alone; no recorded run exercises the composed defence end to end.

## 5 Disposition

  handlers are the prototype's stub handlers; no observer is configured on the pre_egress hook; the three
  configurations share the path (AA-06). Where the label, the keys and the destination come from, the writer's
  owner, and what the stub handlers can name are items of the composition, not premises (section 4). This is
  a conclusion on the frozen design and its checked realization in the prototype, not a claim about the
  deployed system.

  (repeating 20261018T231612Z); the response and record paths are checked up to the

  execution_id key only; no E-09 export consumer exists. The lab-engine rows are context only. All three

## 6 What remains
- Residual and open questions: outbound confidentiality is a different property — the response goes to the
  original channel, and what another holder of that endpoint can read there is X-10 / kub §7.4 (EV-43, EV-95),
  not this route; any future consumer of the E-09 export (MPI-F05, inter-agent forwarding mech L316) inherits
  whatever T-38 emitted (U-06); a real E-07 connector replaces the stub's callback with network-side
  identifiers, and its attachment of results to the sink is re-checked then; an observer on the pre_egress hook
  receives the candidate and through it the mutable RequestEntry, so a configured observer re-runs this route;
  receiver_generation enters only as a label field and does not bear on the route.
- Design obligations for the engine: (T-38) populate verified_subject and the flow's destination only from the
  carried context and entry — realized (EV-183, EV-197, EV-230); (T-34) select the writer only by the entry's
  Channel and apply connector results only to the sink's entry — realized for the stub handlers (EV-198,
  EV-242); (T-33) derive operation_id and the summary from the entry — realized (EV-241, EV-227).
