# R-G2-05 — A labelled acceptance violates stamp population/equality through an as-yet unrefined cause outside the identified production/selected-slot/privilege cases.

## 1 What the adversary does
A labelled acceptance violates stamp population/equality through an as-yet unrefined cause outside the identified production/selected-slot/privilege cases.

## 2 How it would produce false attribution
- **Nature of the slot.** This is the C-02 refinement slot of 02 U-02, a remainder defined by predicates, not
  a demonstrated path. It holds every history in which an accepted byte either lacks a populated valid kernel
  stamp although a credential-producing option was armed when it was queued (D_21 ∧ ¬q08; the unarmed case q08
  is R-G1-01), or carries a populated stamp differing from its sender's real uid by neither an own-set
  selection (q09 → R-G5-03) nor a permitted foreign map (q10 → R-G5-04): D_22 ∧ ¬(q09 ∨ q10).
  B(R-G2-05) = (D_21 ∧ ¬q08) ∨ (D_22 ∧ ¬(q09 ∨ q10)).
- **Preconditions.** For the producer branch (D_21 ∧ ¬q08): bytes reach the engine's reader on row r's channel
  without a populated valid stamp while the engine end has had SO_PASSCRED since T-04 — so either an skb was
  enqueued by a path that does not run maybe_add_creds, or bytes reached the reader by a path that is not an
  skb on the receive queue. For the credential-read branch (D_22 ∧ ¬(q09 ∨ q10)): an skb carries a populated
  stamp that is neither the real uid of the task that executed the send nor an own-set or privilege-mapped
  value the kernel checked. Since the route ends in a labelled acceptance, the wrong or empty stamp must also
  pass T-22 and T-23 — the wrong value equals u_r, or the engine's own check fails (C-03 / C-04 cells); the
  slot itself owns only the stamp half. The adversary is arbitrary code at u inside the envelope from T-11
  (A-01, A-03, A-04, A-05). Configuration: all three branches (C-LS / C-LP / C-R) under the common
  abstraction — the agent ↔ engine leg is the same in each.
- **Transitions traversed:** T-20 or T-64 (the send, or an alternate write or submission path), then
  T-21 → T-22 → T-23 → T-24. The histories the cut leaves outside the frozen design exit through T-66 (a
  kernel defect) or T-67 (a configuration departure); section 6 names them.
- **Sufficient condition violated:** C-02 — p21 (every contributing origin has a populated valid kernel uid
  stamp) or p22 (k(b) = u(task_b, send_b)). The chain of 02 §3 reads k(b) as the sender's real uid; with p21
  or p22 broken, the label's uid equality says nothing about the task that sent the byte, so Exec(b) is
  unconstrained by L(a).execution.

## 3 What stops it
The per-skb stamp at the only two enqueue sites of a connected stream socketpair — unix_stream_sendmsg and
queue_oob, each after maybe_add_creds — with step 11's initial-namespace capability posture gating the one
credential-less delivery path, the BPF sockmap ingress list, cuts both branches of the slot (preservation
rows T-20, T-64). The 2026-10-16 reading of kub §2.4 (EV-142 … EV-146) supplies what the previous version
of this file listed as proposed evidence; each branch is argued from it below.

**Producer branch, D_21 ∧ ¬q08.** Inside net/unix the receive queue gains an skb at five places (EV-142).
Two are the stream senders: unix_stream_sendmsg (af_unix.c L2250, after maybe_add_creds at L2248) and
queue_oob (L2137, after L2128); both write only to unix_peer(sk), which unix_socketpair fixes once for both
ends at creation (EV-142; T-04). The other three cannot reach the engine's end: unix_stream_connect queues
its connection skb only on a socket in the listening state and listen() refuses a connected socket;
unix_dgram_sendmsg finds its destination with the sender's own socket type, a path of another type failing
EPROTOTYPE and an abstract name being hashed with the type (EV-143); the garbage collector re-queues an skb
only under a destructor nothing at the tag sets (EV-144). The 2026-10-13 reading already placed every
write syscall — write / writev, send / sendto, sendmsg / sendmmsg, splice / sendfile, the MSG_OOB byte — at
those two sites, vmsplice filling only a pipe (EV-10, EV-11). With SO_PASSCRED armed on the engine end
(C4 (a), T-04), maybe_add_creds fills every skb that carries no identity with the caller's tgid, real uid
and real gid (EV-07); an skb that already carries one got it from scm_check_creds, which fails EINVAL on an
unmappable value before any permission test (EV-08). So every skb on the engine end's queue carries a
populated valid stamp, and no byte of an skb is in D_21. One path delivers bytes to the reader that are not
skbs on that queue: a unix stream socket held in a BPF sockmap hands over bytes from the psock ingress list
through sk_msg_recvmsg, with no credential at all (EV-145). To use it the attacker must create a SOCKMAP or
SOCKHASH map, which needs capable(CAP_NET_ADMIN) — the initial user namespace — and must insert the engine's
end through a descriptor in its own table (EV-145). Step 11 leaves the agent no capability in the initial
user namespace: bounding set cleared, every set cleared, no_new_privs (S4; EV-05; measured EV-70, EV-74;
the requirement restated at EV-04 and EV-31); the full set a self-made namespace confers is bound to that
namespace (EV-20) and does not satisfy capable(). That gate alone stops the path. Two further gates are not
needed for the cut and are recorded as surface: the agent's table at execve is {0, 1, 2 → /dev/null,
3 → channel} (EV-74; the close_range arm EV-64), the engine's end lives in the engine's table only (T-05,
T-09) and no business fd-pass delivers it (AA-06), while a numeric identifier confers no reference (EV-94);
and bpf is not in the diagnostic allow (EV-93), the production allow-set being S2's [S] item (EV-129).
Were credential-less bytes delivered nonetheless, they arrive with no SCM_CREDENTIALS and T-22 closes the
session with a receive_rejected event carrying no subject (C4 (b), EV-34; the transport library's
behaviour EV-89, EV-90) — a second, engine-side cut this disposition does not rest on.

**Credential-read branch, D_22 ∧ ¬(q09 ∨ q10).** Every skb on the queue was enqueued at one of the two
sites above, so its stamp is one of two things. Either it is the passive fill: one synchronous read of the
live credential of the task executing the send, current_uid_gid inside the syscall, with no check-then-use
pair (EV-07, EV-25). By 02 §0.1, origin(b) is the task that executed the send that queued b, so this value
is u(task_b, send_b) whichever task is current — the in-kernel senders of EV-146 (the NBD client, the 9p fd
transport, USB/IP) included: they reach the socket's sendmsg, pass maybe_add_creds, and stamp the task that
is current when the subsystem writes, so their skbs satisfy p22 for that task and are judged at T-23 and by
C-06, not here; setting any of them up needs CAP_SYS_ADMIN, a mount a user namespace cannot make, or a
write-only sysfs attribute (EV-146), none inside the envelope of step 11. Or the stamp is an explicit
SCM_CREDENTIALS value that passed scm_check_creds (EV-08): a member of {real, effective, saved} — the real
uid itself under C1, or q09 (R-G5-03) — or a value mapped under ns_capable(cred->user_ns, CAP_SETUID), which
an unprivileged map can name only as the writer's own kernel uid (EV-21; measured EV-59, EV-60) and which
otherwise is q10 (R-G5-04); anything else fails EINVAL or EPERM and queues nothing (T-20 (c), (d); measured
EV-29 arm 2 on the WSL2 substrate, arms 0, 1 and 3 the positive cases). Hence within intact kernel semantics
at the pin the branch holds no history. What would put one there — a control block rewritten after enqueue,
a credential check run against another task's credential as in the historical EV-23 — is a kernel defect,
and the derivation's own last clause sends it to the kernel-breach exclusion: R-G5-01, scope-and-boundary.md
§Boundary Defence.

Preservation rows relied on: T-20 and T-64 of this group's preservation file (the stamping facts at every
write path); T-22 for the engine-side second cut, which is not load-bearing.

**Composition:** a conjunction of two parts. The first is kernel semantics at the pin, all `[R]`: the five
enqueue sites and the two that reach a connected end (EV-142, EV-143, EV-144), the stamp on each (EV-07,
EV-08, EV-25, with EV-10 and EV-11 for the syscall side), the in-kernel senders' stamp of the current task
(EV-146), and the privilege gate on the sockmap list (EV-145); these are necessary and source-read, within
the bounds the reading states. The second is the initial-namespace capability posture of step 11: `[R]` for
the kernel facts it rests on (EV-05, EV-20), `[M]` for the as-built drop (EV-70; EV-74 under the diagnostic
policy, which bears on the filter, not on the drop), with EV-04 and EV-31 as the restated requirement whose
exercised halves those rows are — the drop code exists and was exercised, so no necessary component is
unbuilt. Every other item is an alternative, not a necessary component: the descriptor discipline (EV-74,
EV-64, EV-94; the no-business-fd-pass rule of AA-06), the allow-set (EV-93 `[R]` under the diagnostic
policy; EV-129 `[S]` for production), and the engine-side missing-credential rejection (EV-34 `[S]`; EV-89,
EV-90 `[R]` for the transport library). The measured neighbours of the explicit path (EV-29, EV-59, EV-60)
confirm the derivation of the second branch and are not what cuts it. EV-23, EV-24 and EV-27 bound the
remainder (kernel defects, a search-bounded negative, an unassessed lead) and are not defences. No `[S]`
item is necessary, so the disposition may be *supported under stated premises*.

**Proposed evidence (not yet in the registry):** a source reading at the pin of the execution context of
the io_uring send path — which task executes the enqueue and with which credential — to be made only if a
production ABI admits asynchronous submission (02 U-01); a line-by-line read of the 30 out-of-family
receive-queue writers and of the remaining sockfd_lookup callers at the pin, which would lift the two bounds
EV-142 and EV-146 state.

## 5 Disposition
**supported under stated premises** (the same value as the `disposition:` field) — a kernel-semantics
conclusion with step 11's capability posture as its design-layer premise; nothing here is a claim about the
deployed system, and the conclusion holds within the bounds the reading states.
- Premises that must hold: the kernel at the pinned tag, intact (AA-02; tm D8; the kernel-breach paragraph
  of scope-and-boundary.md §Boundary Defence, R-G5-01); S4 / step 11 — the agent holds no capability in the
  initial user namespace, CAP_NET_ADMIN and CAP_SYS_ADMIN included (bounding set cleared, every set cleared,
  no_new_privs); C1 and C2 as stated, whose departures are R-G5-03 and R-G5-04, not this slot; C4 (a) —
  SO_PASSCRED armed on the engine end at T-04, whose absence is q08 → R-G1-01; configuration: all three
  branches on the agent ↔ engine leg. Stated but not needed for the cut: the descriptor discipline (the
  engine's end never in the agent's table; AA-06) and S2's deny of bpf and asynchronous submission.
- Evidence limit (configuration, substrate, run dates): source readings at linux-msft-wsl-6.6.87.2, read
  2026-10-13 (EV-10, EV-11) and 2026-10-16 (EV-142 … EV-146), each file checked byte-identical to upstream
  v6.6.87; the 2026-10-16 reading's own bounds — the 30 receive-queue writers of other protocol families
  were sorted by directory, not read line by line (EV-142), and the remaining sockfd_lookup callers were
  sorted by the protocol their file serves, not read (EV-146) — so "nothing else enqueues" is a reading
  within those bounds, not a reading of every file; the posture measured 2026-08-18 (Docker on the WSL2 VM,
  a probe, EV-70) and 2026-09-11 (direct WSL, diagnostic policy, EV-74); EV-75 and EV-93 under the diagnostic
  policy, the production allow-set `[S]` (EV-129); EV-29 on the WSL2 arm only, the native-Linux VM arm
  pending — not load-bearing here. Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below).

## 6 What remains
- Residual and open questions. (i) Kernel defects: a stamp altered after enqueue, a credential check run
  in another task's context (EV-23's historical form), the SOCKMAP lead (EV-27) and whatever the bounded
  negatives (EV-24, EV-45 in kub §8) did not reach — all R-G5-01's declared exclusion, as the derivation's
  last clause states. (ii) The two bounded parts of the reading named in section 5; a line-by-line read
  would lift them. (iii) Asynchronous submission under a future production ABI (02 U-01): the io_uring
  execution context at the pin is not read; at the pin S2 denies io_uring (EV-75 under the diagnostic
  policy; EV-129 `[S]` in production). Under the model's one credential per task, an enqueue by such a
  path is still stamped with the executing task's real uid (EV-142 with EV-07), so what it raises is that
  task's membership of P_X (C-06) and the correspondence of the model's single credential to the kernel's,
  not this slot's predicates; recorded as open, not routed. (iv) Step 11 absent on the deployed host (S4,
  T-67) is a configuration failure — 01 T-67: a deployment or trusted-actor error, not the adversary — not
  an adversary route: with CAP_NET_ADMIN in the initial user namespace and a descriptor to the engine's end,
  credential-less bytes could reach the reader through the sockmap list. Like the C1 / C2 failures of
  R-G5-03 / 04 / 07, it is carried as this route's premise (section 5), an engine obligation (step 11 clears
  every capability) and a deployment check; the engine's missing-credential rejection at T-22 (C4 (b), an
  `[S]` engine check) is a second layer, not the cut (02 v6 ledger row; executor wording, 2026-10-16).
- On PLAN's closing property for this slot ("every skb on the stream socket's receive queue is stamped at
  enqueue by maybe_add_creds from current's credential; no other in-kernel producer exists at the pinned
  tag"): established within the stated bounds, with one qualification — the sockmap ingress list is a
  credential-less delivery path to the reader, not an skb producer, and sits behind a privilege outside the
  envelope. PLAN's expected disposition was a hypothesis and did not decide this file. On 02 §4.1 item 4,
  this file's derivation of the four probe cases agrees with 02's and with the WSL2 measurement (EV-29);
  no disagreement with 02 §4.1 is recorded.
- Design obligations surfaced for the engine: at T-22, the product receiver must treat a positive-length
  return without exactly one SCM_CREDENTIALS as fatal (C4 (b), MM-08) — the engine-side cut for any
  credential-less delivery; at T-64, the production allow-set must state whether it admits bpf and any
  asynchronous-submission interface (EV-129), and if the latter, the U-01 correspondence check is owed
  before the slot's producer branch is re-read against it; at T-07, step 11's bounding-set clear must
  remain the clear of every capability (S4), since this cut uses CAP_NET_ADMIN and CAP_SYS_ADMIN, not only
  C2's CAP_SETUID.

  kernel-defect remainder), R-G2-03 (the engine-side landing of a return without ancillary), R-G2-11
  (the C-01 remainder), R-G2-09 (A-07, the agent-end holder — not this slot); preservation rows T-20, T-22,
