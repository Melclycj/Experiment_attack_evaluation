# R-G2-08 — A's observed uid or identity field chooses/rewrites the expected row instead of being compared to the original expectation.

## 1 What the adversary does
A's observed uid or identity field chooses/rewrites the expected row instead of being compared to the original expectation.

## 2 How it would produce false attribution
- **Preconditions:** a receiver that, on a mismatch or on first contact, searches the session table for the
  row whose expected uid equals the observed one, or writes the observed uid into the row as its new
  expectation, or reads a uid, agent_id or grant from the hello or request payload to select the row. The
  adversary then sends with its own genuine stamp (T-20 (a)) and a payload naming another execution, or
  relies on uid reuse so that the observed value selects a different row than the channel's. Configuration:
  all three branches under the common abstraction (agent ↔ engine leg).
- **Transitions traversed:** T-20 → T-21 → T-22 → T-23 → T-24; T-52 as a fact (the control path never finds
  another row by uid or fd).
- **Sufficient condition violated:** C-04 p42 (the decision requires v(f) = e_r with the same original
  comparand and no observe-and-rebind or fallback identity source) and C-05 p51 (the row read at a is the
  one corresponding to the original Channel). B(R-G2-08) = D_42 ∧ q16. Why it is a wrong attribution: the
  label is taken from a row chosen by the adversary's observed value or payload, not from the channel its
  bytes arrived on; the equality then holds by construction rather than by the sender's identity.

## 3 What stops it
The immutable expected_uid is compared against and never written from an observation; no row is
selected by the observed uid or by a payload identity field. Design text (conn at the fourth-revision blob
0c16e567a34aa441): E-01 objects (L80) — expected_uid cannot be changed to an observed value after creation;
E-02 step 4 (L464) — a failing fragment discards the frame and closes, with no lookup of another row by the
observed uid; E-01 control (L176–177) — a control record never finds another row to receive by the same
uid or fd; hello (L522) — the hello must not supply uid, agent_id or grant to set identity; E-02
VerifiedContext (L572) — the label fields come from the original engine objects, never from agent-reported
identity; E-02-R2 (L415) — claimed identity, targets, labels and arguments are not authorization evidence.
mechanism.md §Identity lifecycle (CRA-F15): the check compares against the expected uid; recording what is
seen may fail open, comparing against the expectation fails safe. kub §7.3 defence C is this rule.

Realization in the prototype (commit 3ec67985). expected_uid is written once, in the reservation decision,
from the lease whose uid comes only from the workspace record, and a text search finds no other
assignment (EV-186, confirmed at lifecycle.py:150 on 2026-10-19); a second assignment raises (EV-187). The
C reader is passed the row's expected_uid and returns no observed uid (EV-169, EV-186), so no code path can
search a table by the observed value or write it into a row; the only uid-keyed table is the allocator's
holders, used at reservation and release, and no table is keyed by local_agent_id (EV-196). The row is
reached only through the Channel the bytes arrived on (EV-194, EV-172). Every message type, the hello
included, is invalid with any of 13 identity-like fields added (EV-184). Control records are matched by
execution_id with lease_id compared, never by uid or fd (EV-220). Root unit tests rejected a frame from
another pool uid with no other row selected (EV-174), and in the parallel integration case each of two
executions was attributed to its own row (EV-188). Preservation rows relied on: T-23, T-24.

## 5 Disposition
**supported under stated premises**
- Premises that must hold: configuration: all three branches on the agent ↔ engine leg (the engine-side
  facts this route needs are items of the composition above, each realized and checked).
  Design-layer conclusion with the prototype's checked realization; nothing here is a claim about the
  deployed system.
- Evidence limit: integration run 20261019T011226Z-engine-pool-70000 (2026-10-19); the swapped-rows case of
  commit b262e80e (tests and the integration runner only, no engine or sandbox code changed) in run
  20261020T154357Z-engine-extra-evidence-rerun (2026-10-20, same host and kernel, runner as root, senders at
  uids 60000 and 60001), with its negative control by a planted transport.c defect in a copy of the engine
  tree. Shared limits: [coverage-uncertainties § Shared evidence boundary](../../convergence/coverage-uncertainties.md#shared-evidence-boundary-every-route-not-repeated-below). The checks' own limits: the swapped-rows case runs the Lifecycle in the unit harness with a
  scripted spawner and real kernel senders, not an integration case; the absence of a lookup by observed uid,
  local_agent_id or fd is by code reading and text search; the write-once guard is a Python-level check on
  attribute assignment.
