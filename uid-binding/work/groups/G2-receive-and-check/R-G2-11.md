# R-G2-11 — An adversarially triggered accepted byte-origin/witness association fails C-01 outside the identified insertion/read/buffer cases; its concrete cause remains unresolved.

## 1 What the adversary does
An adversarially triggered accepted byte-origin/witness association fails C-01 outside the identified insertion/read/buffer cases; its concrete cause remains unresolved.

## 2 How it would produce false attribution
- **Nature of the slot.** This is the C-01 refinement slot of 02 U-02: the explicit remainders of the three
  C-01 cells. It holds every history in which an accepted byte has no actual send origin (p11), no current
  recvmsg witness (p12), or a witness that does not belong to the same read, channel, generation and frame
  as the event (p13), by a cause other than the named ones — not an alternate constructor (q01, R-G3-01),
  not the T-24 path emitting a subject with no origin (q02, R-G2-01), not a credential-dropping read API
  (q03, R-G2-01), not an identified header/body/OOB/second-reader insertion (q04, R-G2-02), not a buffer of
  a prior allocation generation (q05, R-GX-01), not data and ancillary from different reads (q06, R-G2-03),
  not another frame's or channel's buffer (q07, R-G2-04).
  B(R-G2-11) = (D_11 ∧ ¬(q01 ∨ q02)) ∨ (D_12 ∧ ¬(q03 ∨ q04)) ∨ (D_13 ∧ ¬(q05 ∨ q06 ∨ q07)).
- **What would have to be true for it to be a route:** the receiver's association between bytes and their
  read witness is altered by a path the inputs I-01 and I-04 do not name — for instance a memory-safety
  defect of the parser or FrameReader triggered by an earlier frame (the engine is C17, iv L17), an engine
  worker or log path that copies or rewrites the buffer (forbidden by conn L574 and si L111–112, which keep
  workers from writing Session or RequestEntry, but the FrameReader is not named there), or a kernel
  receive-path defect that returns another socket's bytes (which is the N1 class, R-G5-01). The adversary
  triggers the path with its own protocol input (A-02) and timing (A-06).
  Configuration: all three branches under the common abstraction (agent ↔ engine leg).
- **Transitions traversed:** T-20 … T-25 (any point of the receive path), T-64 as the write side.
- **Sufficient condition violated:** C-01 (p11, p12 or p13). Why it would be a wrong attribution: a byte with
  no witnessed origin, or with a witness from another read, is labelled by a row that never compared it.

## 3 What stops it
Bytes reach the comparison only through the one FrameReader path of the Channel that owns it and the C reader on that path calls no third-party parser, established by code reading and static tests; the remaining branch — a memory error of the project's C code on that path (transport.c, support.c) — is stopped only if that code is memory-safe, a stated requirement (engine-requirements row 175) whose proof this route does not have: it is assigned to prove 2.2, and the one-hour ASan/UBSan fuzz run that found no error is supplementary evidence for it within the limits section 5 states, with the body parse resting on the CPython runtime as a platform premise.

The slot is the remainder of the three C-01 cells. The closing property of PLAN §Follow-up plan after U has
two halves, and each branch of B(R-G2-11) needs one of them; the path half is established below, the memory
half is the requirement section 5 names and is not. The C reader read here is the one of engine commit 7b4ab727, which removed the jansson
parse of the body that the reader of commit 3ec67985 ran after the comparison (user approval 2026-10-19;

**The path half (code reading and static tests).** On the data channel Python obtains received bytes only
through receive_step's call of the Channel's FrameReader, which calls w2_frame_receive with a Python-owned

parsed only in Python (EV-265); a source-scan test with a negative control on the earlier transport.c holds

- D_11 ∧ ¬(q01 ∨ q02), a byte with no actual send origin. Every byte that reaches Python was written into

  counting, which holds at 7b4ab727); the one construction of a VerifiedContext follows it (EV-172). A byte

- D_13 ∧ ¬(q05 ∨ q06 ∨ q07), a witness from another read, channel, generation or frame. The reader is bound
  to one fd and one socket cookie and dies on a change (EV-236); at the pin the kernel does not merge skbs

not that the code has none. It is supplementary evidence for the memory-safety requirement of section 5, not
that requirement's proof (M1 item 1, 2026-10-23).

**The body parse.** The body is parsed by CPython's standard-library json in the strict configuration the

No preservation row is relied on; rows T-21 … T-24 of this group's preservation file argue I under the

## 5 Disposition
**conditional on unbuilt requirements** — the path half is a conclusion on the frozen design, kernel
semantics where cited and the prototype's checked realization; the memory half rests on a requirement whose
proof is not made: engine-requirements row 175, the parser and the FrameReader must be memory-safe, which
for the project's C code on this path is assigned to prove 2.2 (input non-subversion, prove README §2.2). The
one-hour ASan/UBSan fuzz run (EV-267, EV-268) is supplementary evidence for that requirement, not its
discharge — a run on which no error appeared does not show that the remainder is empty (M1 item 1,
2026-10-23; before that date this route was counted supported on the fuzz run). Nothing here is a claim about
the deployed system, and the composed defence is not measured end to end.
- Unbuilt requirement (a stated requirement in the `[S]` sense of the table's preface; it has no registry row of
  its own, the requirement list being engine-requirements): the memory safety of transport.c and support.c on the
  receive path (row 175, "design decides how", unstated in the frozen design). When prove 2.2
  establishes it, this route is re-run under PLAN rule 4 and the fuzz run stays as its supplementary evidence.
- Premises that must hold: an intact kernel at the pinned tag (rendering, stamping and EV-88's per-return
  credential boundary; kernel receive-path defects such as EV-27 are R-G5-01); the CPython runtime that
  executes the engine, its standard-library json included, runs the code as written — a platform premise
  for the body parse, which the design chooses and whose strict configuration is realized (receive.py:107–123,
  EV-272), and which the fuzz does not check; the single executor (AA-01); configuration: all three branches
  on the agent ↔ engine leg. The production seccomp allow-set S2 (P2b, `[S]`) is not needed for this cut: the
  receive path rejects whatever the agent's sends deliver.
