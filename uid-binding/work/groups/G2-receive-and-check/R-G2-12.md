# R-G2-12 — An accepted observation violates translation/decoding fidelity outside the identified alias/ancillary/ABI cases; its concrete cause remains unresolved.

## 1 What the adversary does
An accepted observation violates translation/decoding fidelity outside the identified alias/ancillary/ABI cases; its concrete cause remains unresolved.

## 2 How it would produce false attribution
- **Nature of the slot.** This is the C-03 refinement slot of 02 U-02: the explicit remainders of the
  translation cells. It holds every history in which the rendering r is not defined and injective on the
  relevant kernel uids (p31) by a cause other than an unmapped, invalid or sentinel alias (q11, R-G5-05 —
  the C3 failure), or in which the decoded value differs from the rendering of the stamp (p32) with the
  ancillary present and intact (not q12, R-G2-03) and the decode neither of the wrong ABI, nor from stale
  storage, nor a pid lookup (not q13, R-G2-06).
  B(R-G2-12) = (D_31 ∧ ¬q11) ∨ (D_32 ∧ ¬(q12 ∨ q13)).
- **What would have to be true for it to be a route:** two distinct kernel uids render to one number in the
  engine's namespace without that number being a sentinel — which under the identity map of the initial
  namespace has no mechanism in the frozen text and under a partial map is the overflow alias, hence q11;
  or the value put into the control message differs from the skb's stamp through a kernel-side cause — the
  historical shape is CVE-2012-3520, a Netlink path that skipped the invalid marking (EV-35 note), which is
  a kernel defect and so the N1 class; or the engine decodes correctly from an intact control message that
  the kernel filled from another skb's stamp (again kernel-side). The adversary's part is to send with a
  chosen uid, pid or timing that makes the misrendering land on a row's expectation. Configuration: all
  three branches under the common abstraction (agent ↔ engine leg).
- **Transitions traversed:** T-21 (the rendering), T-22, T-23 (the decode), T-24; T-67 as the configuration
  input.
- **Sufficient condition violated:** C-03 (p31 or p32). Why it would be a wrong attribution: the number
  compared at T-23 does not stand for the sender's kernel uid, so equality with e_r no longer implies the
  sender's uid is u_r.

## 3 What stops it
The engine runs under the identity map, checked at every start by the product entry's self-check, which refuses service otherwise, and this is the closing property of R-G2-12 in PLAN §Follow-up plan after U, established on the development host by the integration run's positive and refusal cases and a code reading of the check.

The slot is the remainder of the two translation cells. The design statement behind the property is C3's
start-up self-check (conn E-01, EV-33); it is now realized and checked.

**The check itself.** The engine reads uid_map, overflowuid, overflowgid, ptrace_scope and the KSM switch
and hands them to the spawner's C parser, which accepts only the single uid_map line 0 0 4294967295 and
positive overflow values; any other reading raises StartupRefused, and build() runs the check before the
catalogs are loaded and the control endpoint is used (EV-165; read again for this file at startup.py:61–72,
support.c:218–227 and main.py:37–74). In the integration run the production entry recorded the identity map
before serving, all 31 cases with a startup field recorded the same map (EV-163), and under a one-line
non-identity map the same entry refused service with exit code 3 (EV-164).

**How the property empties each branch.**
- D_31 ∧ ¬q11, the rendering undefined or not injective by a cause other than an unmapped, invalid or
  sentinel alias. The kernel renders every uid through the receiver's namespace map (EV-01, EV-13). A
  serving engine has a single extent covering every valid uid, so every kernel uid an agent can hold has a
  mapping and the rendering is defined and injective on all of them; a partial or other map stops the
  engine before it serves (EV-164, EV-165). What would remain is a kernel-side defect in the rendering
  (the historical shape CVE-2018-18955, fixed at the pin; EV-21 note), which is the N1 class (R-G5-01).
- D_32 ∧ ¬(q12 ∨ q13), the decoded value differs from the rendering with the ancillary present and intact
  and the decode of the right ABI. The engine's decode is a byte copy of the one SCM_CREDENTIALS payload of
  the current call's fresh control buffer into a struct ucred and an unsigned uid_t comparison (EV-171,
  EV-237); the expected value crosses the FFI as an unsigned 32-bit value and the observed one does not
  cross at all (EV-169). Nothing stands between the kernel's rendering and the compared value, so a
  difference needs the kernel to fill the control message from something other than the stamp of the skb
  whose bytes it returns (EV-13, EV-88), as CVE-2012-3520 did on a Netlink path (EV-35 note): kernel-side,
  hence N1.
- After start-up. A process changes user namespace only by unshare or setns. The engine package and the
  sandbox C code contain no setns (EV-235), and a text search for this file found no unshare and no
  CLONE_NEWUSER outside the agent's seccomp policy (policy.c); the package's only direct libc calls are
  openat2 and prctl (proposed row below). A later move to a partially mapped namespace would in any case
  render foreign uids as the overflow value, which the reader rejects (EV-171): that is q11, not this slot.

**The half the check does not show.** The self-check shows that the engine's own namespace has the identity
map, not that this namespace is the initial one (EV-163 note; val row 256). C3 and S13 require the initial
namespace; that half is a deployment premise of engine-requirements §8, recorded for the development host
only, and goes in section 5's premises, not among the items.

No preservation row is relied on; rows T-21 and T-23 argue I under C3 and the pinned rendering, and this file
argues that the histories outside them are empty within the premises and limits stated.
